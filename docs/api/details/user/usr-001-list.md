# USR-001 利用者一覧取得

## 1. 概要

登録済みの利用者一覧を取得する。

ポートフォリオ確認者が、
複数の資産状況や目的達成判定のパターンを
短時間で確認できるようにするために使用する。

---

## 2. ユースケース

利用者は、
画面表示時に利用者一覧を取得する。

取得した利用者の中から、
操作対象となる利用者を選択する。

フロントエンドは、
選択された利用者IDを共通状態として保持し、
以降の利用者依存APIへ
`X-User-Id`ヘッダーとして付与する。

---

## 3. エンドポイント

```http
GET /api/v1/users
```

---

## 4. HTTPメソッド

```http
GET
```

本APIは、
登録済み利用者を参照するのみであり、
データの登録、更新および削除は行わない。

---

## 5. 認証・利用者の扱い

Phase1では、
認証機能を実装しない。

本APIは、
操作対象となる利用者を選択する前に呼び出すため、
`X-User-Id`ヘッダーを必須としない。

本API以外の利用者依存APIでは、
原則として`X-User-Id`ヘッダーを必須とする。

---

## 6. パスパラメータ

なし。

---

## 7. クエリパラメータ

なし。

Phase1では、
登録される利用者数が少ないことを前提とし、
ページネーション、
検索、
絞り込みおよび並び替え指定は提供しない。

---

## 8. リクエストヘッダー

### 8.1 必須ヘッダー

なし。

### 8.2 共通ヘッダー

API共通方針で定める共通ヘッダーを使用する。

例：

```http
Accept: application/json
```

`X-User-Id`は指定しない。

指定された場合も、
本APIの検索条件には使用しない。

---

## 9. リクエストボディ

なし。

---

## 10. バリデーション

パスパラメータ、
クエリパラメータおよび
リクエストボディを受け取らないため、
項目単位のバリデーションは行わない。

共通ヘッダーやHTTPリクエスト形式に問題がある場合は、
API共通方針に従ってエラーを返却する。

---

## 11. 業務ルール

- あらかじめ登録された利用者のみ取得対象とする。
- 論理削除された利用者は取得対象としない。
- 利用者の新規登録、編集、無効化および削除は提供しない。
- メールアドレスなど、利用者切替画面に不要な情報は返却しない。
- 開発者本人の実データを含む利用者は、ポートフォリオ用ステージング環境へ登録しない。
- 利用者一覧の取得は、現在選択中の利用者に依存しない。
- 利用者の表示順は、フロントエンド側で暗黙に変更せず、APIが返却する順序を使用する。
- Phase1では、利用者IDの昇順で返却する。

---

## 12. 処理フロー

```text
リクエスト受付
    ↓
リクエストID生成
    ↓
未削除の利用者を取得
    ↓
利用者IDの昇順に並び替え
    ↓
APIレスポンス用の形式へ変換
    ↓
正常レスポンス返却
```

---

## 13. トランザクション境界

参照処理のみであるため、
明示的なデータベーストランザクションは使用しない。

---

## 14. 排他制御

参照処理のみであるため、
排他制御は行わない。

---

## 15. 成功レスポンス

### 15.1 HTTPステータス

```http
200 OK
```

### 15.2 レスポンスボディ

登録済み利用者を
`data`配列で返却する。

```json
{
  "data": [
    {
      "id": "1",
      "name": "標準ケース",
      "description": "資産情報と手取り収入が登録済みの基本的な利用者です。"
    },
    {
      "id": "2",
      "name": "達成困難ケース",
      "description": "目的達成後の残余資金が不足する利用者です。"
    },
    {
      "id": "3",
      "name": "判定不可ケース",
      "description": "手取り収入が不足しており、目的達成判定を実行できない利用者です。"
    }
  ]
}
```

---

## 16. レスポンス項目

| 項目 | 型 | NULL | 説明 |
|---|---|:---:|---|
| `data` | array | × | 利用者一覧 |
| `data[].id` | string | × | 利用者ID |
| `data[].name` | string | × | 利用者の表示名 |
| `data[].description` | string | ○ | デモシナリオの説明 |

### 16.1 IDの扱い

利用者IDは、
API共通方針に従い文字列として返却する。

```json
{
  "id": "1"
}
```

データベースでは`bigint`として保持するが、
APIレスポンスでは文字列へ変換する。

### 16.2 description

`description`は、
利用者がどのような確認シナリオを持つかを
ポートフォリオ確認者へ説明するために使用する。

説明を設定しない利用者では、
`null`を返却する。

```json
{
  "id": "4",
  "name": "CSV確認ケース",
  "description": null
}
```

空文字は返却しない。

---

## 17. データが存在しない場合

登録済み利用者が存在しない場合も、
API処理自体は正常終了とする。

```http
200 OK
```

```json
{
  "data": []
}
```

利用者が存在しないことは、
特定リソースの不存在ではなく、
一覧の検索結果が0件であるため、
`404 Not Found`は返却しない。

ただし、
ステージング環境では少なくとも1件の利用者を
初期データとして登録する。

---

## 18. エラーレスポンス

異常時は、
API共通方針で定めた共通エラーレスポンス形式を使用する。

例：

```json
{
  "error": {
    "code": "INTERNAL_SERVER_ERROR",
    "message": "システムエラーが発生しました。",
    "details": [],
    "requestId": "01JABCDEFGHJKMNPQRSTVWXYZ"
  }
}
```

---

## 19. HTTPステータス

| HTTPステータス | 条件 |
|---:|---|
| `200 OK` | 利用者一覧の取得に成功した |
| `400 Bad Request` | HTTPリクエスト形式が不正である |
| `500 Internal Server Error` | 想定外のサーバーエラーが発生した |

本APIでは、
利用者IDを指定しないため、
以下のエラーは発生しない。

- `USER_CONTEXT_REQUIRED`
- `INVALID_USER_ID`
- `USER_NOT_FOUND`

---

## 20. エラーコード

| エラーコード | HTTPステータス | 条件 | 再試行 |
|---|---:|---|:---:|
| `INVALID_REQUEST` | 400 | HTTPリクエスト形式が不正である | × |
| `INTERNAL_SERVER_ERROR` | 500 | 想定外のサーバーエラーが発生した | ○ |

エラーコードの正式な定義は、
[エラーコード一覧](../error-codes.md)に従う。

---

## 21. 冪等性

本APIは参照処理であり、
同一条件で複数回実行してもデータを変更しない。

登録済み利用者に変更がない限り、
同一の結果を返却する。

---

## 22. キャッシュ

Phase1では、
HTTPキャッシュ制御やアプリケーションキャッシュは導入しない。

利用者数が少なく、
取得頻度による性能問題が想定されないためである。

将来、
利用者情報の取得負荷が問題となった場合に再検討する。

---

## 23. 関連テーブル

### users

利用者一覧の取得元となる。

使用する主なカラムは、
以下とする。

| カラム | 用途 |
|---|---|
| `id` | 利用者ID |
| `name` | 表示名 |
| `deleted_at` | 論理削除判定 |

デモシナリオの説明をどこに保持するかは、
テーブル定義で明示する必要がある。

現行の`users`テーブルに
`description`カラムが存在しない場合は、
次のいずれかを採用する。

1. `users.description`を追加する
2. デモシナリオ説明を設定ファイルまたは初期データ定義で管理する
3. Phase1のレスポンスから`description`を除外する

API契約として`description`を返却する場合は、
永続化または設定上の取得元を確定させる。

  - 利用者切替

  - 登録済みの複数利用者

## 25. テスト観点

### 25.1 正常系

- 登録済み利用者を取得できること
- 複数の利用者を取得できること
- 利用者IDが文字列で返却されること
- 利用者IDの昇順で返却されること
- `data`が配列で返却されること
- `X-User-Id`を指定しなくても取得できること
- メールアドレスがレスポンスへ含まれないこと
- `deleted_at`など内部管理項目がレスポンスへ含まれないこと

### 25.2 データなし

- 未削除の利用者が存在しない場合に`200 OK`となること
- 未削除の利用者が存在しない場合に`data: []`となること

### 25.3 論理削除

- 論理削除済み利用者が一覧へ含まれないこと
- 未削除利用者のみ取得されること

### 25.4 ヘッダー

- `X-User-Id`なしで取得できること
- `X-User-Id`を指定しても検索結果がそのIDに限定されないこと

### 25.5 レスポンス契約

- JSONフィールド名がcamelCaseであること
- IDがstringとして返却されること
- `description`未設定時に`null`となること
- `description`未設定時に空文字を返さないこと
- 共通レスポンス形式に従っていること

### 25.6 異常系

- 想定外の例外発生時に`500 Internal Server Error`となること
- 共通エラーレスポンス形式で返却されること
- エラーレスポンスおよびログに同じリクエストIDが記録されること
- スタックトレースやSQLなどの内部情報がレスポンスへ含まれないこと

## 26. Laravel実装方針

### 26.1 Action

HTTPリクエストを受け付け、
利用者一覧取得のユースケースを呼び出す。

本APIでは、
リクエストボディ、
パスパラメータ、
クエリパラメータおよび
利用者コンテキストを受け取らない。

Actionは、
UseCaseから受け取った処理結果を
Responderへ渡す。

利用者の取得条件、
並び替え、
業務ルールおよび
レスポンス生成処理は、
Actionへ直接記述しない。

### 26.2 UseCase

利用者一覧取得の
ユースケース処理を担当する。

主な処理は、
以下とする。

- Queryを呼び出して利用者一覧を取得する
- 取得結果をResponderへ渡せる形式で返却する

本APIでは、
利用者一覧の取得以外の業務処理を行わない。

利用者の登録、
更新、
無効化および削除は行わない。

### 26.３ Query

未削除の利用者を
利用者IDの昇順で取得する。

LaravelのSoftDeletesを使用する場合、
通常のEloquentクエリによって
論理削除済みの利用者を取得対象から除外する。

取得対象の主なカラムは、
以下とする。

- id
- name
- description

メールアドレスなど、
利用者切替画面で使用しない情報は取得しない。

取得例：
```php
User::query()
    ->select([
        'id',
        'name',
        'description',
    ])
    ->orderBy('id')
    ->get();
```

### 26.4 Responder

UseCaseから受け取った処理結果を、
API共通方針に従った
HTTPレスポンスへ変換する。

正常終了時は、
200 OKとともに
利用者一覧をdata配列で返却する。

利用者が存在しない場合も、
200 OKと空配列を返却する。

```json
{
  "data": []
}
```

エラー発生時は、
共通エラーレスポンス形式に従って返却する。

### 26.5 API Resource

データベースカラムを直接返却せず、
API Resourceを利用して
APIレスポンス形式へ変換する。

利用者IDは、
API共通方針に従い
文字列として返却する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'name' => $this->name,
    'description' => $this->description,
];
```

API Resourceは、
Responderから利用する。

### 26.6 Middleware
本APIは、
利用者を選択する前に呼び出すため、
利用者コンテキストを設定する
ミドルウェアの対象外とする。

以下の共通ミドルウェアは適用する。

- リクエストID生成
- JSONリクエスト・レスポンスの共通処理
- 共通例外処理
- ログコンテキスト設定
X-User-Idが指定されていた場合も、
本APIの取得条件には使用しない。

export type user = {

## 28. 設計上の補足

### 28.1 利用者切替APIを提供しない理由

利用者切替は、
サーバー上のリソースを変更する処理ではない。

フロントエンドが操作対象の利用者IDを変更し、
APIリクエストごとに明示することで実現する。

そのため、
以下のようなAPIは提供しない。

```http
POST /api/v1/users/{userId}/switch
```

### 28.2 usersテーブルのemail

`users.email`は、
利用者一覧取得APIでは使用しない。

Phase1では認証を実装しないため、
APIレスポンスにも含めない。

### 28.3 descriptionの設計

利用者切替画面でデモ内容を理解しやすくするには、
`description`を返却する価値がある。

ただし、現在のテーブル定義に存在しない場合は、
API詳細設計を確定する前に保存先を決める。

採用案としては、
`users`テーブルへ以下を追加する方法が最も単純である。

```text
description varchar(255) NULL
```

利用者固有の説明であり、
表示名と同様に利用者へ属する情報であるため、
Phase1では`users`テーブルに保持してよい。

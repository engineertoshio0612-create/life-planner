# HLD-003 保有商品詳細取得

## 1. 概要

操作対象となる利用者に帰属する
保有商品の詳細情報を取得する。

本APIは、
保有商品の編集画面表示および
詳細情報の確認に利用する。

---

## 2. ユースケース

利用者は、
登録済みの保有商品の詳細情報を確認する。

以下の情報を取得する。

- 保有商品名
- 商品種別
- 所属資産口座
- 利用開始年月
- 備考
- 利用状態

---

## 3. エンドポイント

```http
GET /api/v1/holding-assets/{holdingAssetId}
```

---

## 4. HTTPメソッド

```http
GET
```

本APIは、
保有商品の参照のみを行う。

---

## 5. 認証・利用者の扱い

Phase1では、
認証機能を実装しない。

操作対象となる利用者は、
`X-User-Id`
リクエストヘッダーで指定する。

```http
X-User-Id: 1
```

指定された利用者に帰属する
保有商品のみ取得できる。

他の利用者の保有商品は取得できない。

---

## 6. パスパラメータ

| パラメータ | 型 | 必須 | 説明 |
|---|---|:---:|---|
| holdingAssetId | string | ○ | 保有商品ID |

---

## 7. クエリパラメータ

なし。

---

## 8. リクエストヘッダー

### 8.1 必須ヘッダー

| ヘッダー名 | 必須 | 説明 |
|---|:---:|---|
| X-User-Id | ○ | 操作対象利用者 |
| Accept | ○ | application/json |

リクエスト例

```http
GET /api/v1/holding-assets/15
Accept: application/json
X-User-Id: 1
```

---

## 9. リクエストボディ

なし。

---

## 10. バリデーション

### 10.1 X-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

---

### 10.2 holdingAssetId

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された保有商品が存在すること
- 指定された保有商品が操作対象利用者に帰属すること

他利用者の保有商品を指定した場合は、
存在しないものとして扱う。

## 11. 業務ルール

- 指定された利用者に帰属する保有商品のみ取得する。
- 他の利用者に帰属する保有商品は取得できない。
- 利用中および無効化済みの保有商品を取得できる。
- 保有商品の所属資産口座情報も取得する。
- 保有商品の商品種別および利用状態を返却する。
- データベース内部カラムは公開しない。

---

## 12. 処理フロー

```text
リクエスト受付
    ↓
リクエストID生成
    ↓
X-User-Id検証
    ↓
操作対象利用者の特定
    ↓
holdingAssetId検証
    ↓
保有商品の取得
    ↓
利用者境界の確認
    ↓
所属資産口座の取得
    ↓
API Resourceへ変換
    ↓
正常レスポンス返却
```

---

## 13. トランザクション境界

参照処理のみであるため、
明示的なデータベーストランザクションは使用しない。

保有商品および所属資産口座は、
1回のAPI処理内で取得する。

---

## 14. 排他制御

参照処理のみであるため、
排他制御は行わない。

API実行中に保有商品または所属資産口座が更新された場合は、
取得時点の情報を返却する。

Phase1では、
厳密なスナップショット整合性は保証しない。

## 18. HTTPステータス

| HTTPステータス | 条件 |
|---:|---|
| `200 OK` | 保有商品の取得に成功した |
| `400 Bad Request` | 利用者IDまたは保有商品IDの形式が不正である |
| `404 Not Found` | 指定された利用者または保有商品が存在しない |
| `500 Internal Server Error` | 想定外のサーバーエラーが発生した |

### 18.1 404の扱い

他の利用者に帰属する保有商品を指定した場合も、
存在しないものとして扱い、
`404 Not Found`を返却する。

---

## 19. エラーコード

| エラーコード | HTTPステータス | 条件 | 再試行 |
|---|---:|---|:---:|
| `USER_CONTEXT_REQUIRED` | 400 | `X-User-Id`が指定されていない | × |
| `INVALID_USER_ID` | 400 | `X-User-Id`の形式が不正である | × |
| `USER_NOT_FOUND` | 404 | 指定された利用者が存在しない | × |
| `INVALID_HOLDING_ASSET_ID` | 400 | 保有商品IDの形式が不正である | × |
| `HOLDING_ASSET_NOT_FOUND` | 404 | 保有商品が存在しない、または利用者境界外である | × |
| `INTERNAL_SERVER_ERROR` | 500 | 想定外のサーバーエラーが発生した | ○ |

エラーコードの正式な定義は、
「error-codes.md」に従う。

## 20. 冪等性

本APIは参照処理であるため、
同一条件で複数回実行しても
データを変更しない。

保有商品に変更がない限り、
同一のレスポンスを返却する。

## 22. 関連する機能要件

- `5.1 概要`
  - 保有商品は商品単位で月末評価額を管理するための基礎情報となる
- `5.3 編集`
  - 保有商品名、商品種別および備考を編集できる
  - 所属資産口座および利用開始年月は通常の編集対象としない
- `5.4 商品種別`
  - 保有商品の分類として商品種別を保持する
- `5.5 所属資産口座`
  - 保有商品は必ず1つの資産口座に所属する
- `5.7 無効化`
  - 無効化済みの保有商品も過去の履歴では参照できる
- `5.8 一覧表示`
  - 保有商品名、商品種別、所属資産口座、利用開始年月および利用状態を表示する

## 23. テスト観点

### 23.1 正常系

- 利用中の保有商品を取得できること
- 無効化済みの保有商品を取得できること
- 保有商品名が返却されること
- 商品種別が返却されること
- 所属資産口座IDが返却されること
- 所属資産口座名が返却されること
- 利用開始年月が返却されること
- 備考が返却されること
- 利用状態が返却されること
- 保有商品IDが文字列で返却されること
- 所属資産口座IDが文字列で返却されること

### 23.2 利用者境界

- 操作対象利用者に帰属する保有商品を取得できること
- 他の利用者に帰属する保有商品を取得できないこと
- 他の利用者に帰属する保有商品を指定した場合に`404 Not Found`となること
- 同じ保有商品IDが他利用者のデータとして誤って返却されないこと

### 23.3 利用状態

- `deleted_at`が`NULL`の場合に`isEnabled`が`true`となること
- `deleted_at`が設定されている場合に`isEnabled`が`false`となること
- `deletedAt`がレスポンスへ含まれないこと

### 23.4 所属資産口座

- 所属資産口座名を取得できること
- 所属資産口座が無効化済みでも資産口座名を取得できること
- 所属資産口座の利用状態がレスポンスへ含まれないこと
- 保有商品と所属資産口座の関連が正しいこと

### 23.5 備考

- 備考が登録されている場合に文字列で返却されること
- 備考が登録されていない場合に`null`で返却されること
- 備考未登録時に空文字を返さないこと

### 23.6 ヘッダー

- `X-User-Id`が指定されていない場合にエラーとなること
- `X-User-Id`の形式が不正な場合にエラーとなること
- 存在しない利用者IDの場合にエラーとなること
- 論理削除済み利用者IDの場合にエラーとなること

### 23.7 パスパラメータ

- 正しい保有商品IDで取得できること
- 保有商品IDの形式が不正な場合にエラーとなること
- 存在しない保有商品IDの場合に`404 Not Found`となること
- 無効化済みの保有商品IDでも取得できること

### 23.8 レスポンス契約

- 共通レスポンス形式に従っていること
- JSONフィールド名がcamelCaseであること
- `userId`がレスポンスへ含まれないこと
- `createdAt`がレスポンスへ含まれないこと
- `updatedAt`がレスポンスへ含まれないこと
- `deletedAt`がレスポンスへ含まれないこと
- データベースの数値コードがそのまま公開されないこと
- `data`がオブジェクトとして返却されること

### 23.9 異常系

- 想定外の例外発生時に`500 Internal Server Error`となること
- 共通エラーレスポンス形式で返却されること
- エラーレスポンスとログに同じリクエストIDが記録されること
- SQLやスタックトレースなどの内部情報がレスポンスへ含まれないこと

## 24. Laravel実装方針

### 24.1 Action

HTTPリクエストを受け付け、保有商品IDおよび利用者コンテキストを取得する。

保有商品詳細取得UseCaseを呼び出し、処理結果をResponderへ渡す。

保有商品の検索条件、利用者境界の判定、所属資産口座の取得およびレスポンス生成処理は、Actionへ直接記述しない。

---

### 24.2 UseCase

保有商品詳細取得のユースケース処理を担当する。

主な処理は、以下とする。

- 操作対象利用者を受け取る
- 保有商品IDを受け取る
- 操作対象利用者に帰属する保有商品を取得する
- 所属資産口座を取得する
- 取得結果をResponderへ返却する

利用者境界外の保有商品が指定された場合は、対象が存在しないものとして扱う。

---

### 24.3 Query

操作対象利用者に帰属する保有商品を取得する。

無効化済み保有商品も詳細表示の対象とするため、Laravel SoftDeletesを使用する場合は、`withTrashed()`を利用する。

取得時は、所属資産口座を同時に取得する。

取得例：

```php
HoldingAsset::query()
    ->withTrashed()
    ->with([
        'assetAccount' => fn ($query) => $query->withTrashed(),
    ])
    ->where('id', $holdingAssetId)
    ->where('user_id', $userId)
    ->first();
```

保有商品が取得できない場合は、`HOLDING_ASSET_NOT_FOUND` として扱う。

所属資産口座についても、他利用者のデータが誤って紐づかないよう、リレーションおよび外部キー制約で整合性を保証する。

### 24.4 Responder

UseCaseから受け取った処理結果を、API共通方針に従ったHTTPレスポンスへ変換する。

正常終了時は、`200 OK` とともに保有商品詳細を `data` オブジェクトで返却する。

対象が存在しない場合は、共通エラーレスポンス形式で `404 Not Found` を返却する。

### 24.5 API Resource

データベースカラムを直接返却せず、API Resourceを利用してレスポンス形式へ変換する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'assetAccountId' => (string) $this->asset_account_id,
    'assetAccountName' => $this->assetAccount->name,
    'name' => $this->name,
    'productType' => $this->productType->value,
    'startYearMonth' => $this->start_year_month,
    'memo' => $this->memo,
    'isEnabled' => $this->deleted_at === null,
];
```

API Resourceは、Responderから利用する。

### 24.6 Middleware

以下の共通ミドルウェアを適用する。

- 利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

利用者コンテキスト設定ミドルウェアでは、`X-User-Id` を検証し、操作対象利用者を特定する。

---

```typescript
export type ProductType =
```

## 26. 設計上の補足

### 26.1 無効化済み保有商品を取得対象とする理由

無効化済み保有商品は、過去の商品別月末評価額および目的達成判定履歴との関係を保持する。

そのため、一覧表示および詳細表示では取得対象とする。

新しい商品別月末評価額の登録対象にはしない。

### 26.2 所属資産口座名を返却する理由

保有商品の詳細画面および編集画面では、所属する資産口座名を表示する必要がある。

`assetAccountId` のみを返却すると、画面表示のために別途資産口座APIを呼び出す必要がある。

Phase1では、詳細取得APIで `assetAccountName` も返却し、フロントエンドのAPI呼び出しを増やさない方針とする。

### 26.3 所属資産口座の利用状態を返却しない理由

Phase1の保有商品詳細画面では、所属資産口座名を表示できれば十分である。

所属資産口座の利用状態まで返却すると、本APIの責務およびレスポンス項目が増える。

そのため、`assetAccountEnabled` は返却しない。

所属資産口座の利用状態を表示する要件が追加された場合に、レスポンスへの追加を再検討する。

### 26.4 他利用者の保有商品を404として扱う理由

他の利用者に帰属する保有商品を指定した場合に、権限エラーとして返却すると、指定した保有商品が存在することを推測できる。

Phase1では認証を実装しないが、利用者境界を意識したAPI設計とするため、利用者境界外の保有商品は存在しないものとして扱う。

### 26.5 キャッシュを採用しない理由

Phase1では、保有商品の詳細取得頻度およびデータ量が少ない。

キャッシュを導入すると、更新・無効化時のキャッシュ破棄処理が必要となり、実装が複雑になる。

性能上の効果よりも実装負荷が大きいため、Phase1ではキャッシュを採用しない。

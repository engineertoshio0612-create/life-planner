# 手取り収入API

## 1. 概要

手取り収入APIは、
利用者が対象年月ごとの手取り収入を管理するためのAPIである。

手取り収入は、
目的達成判定における
平均手取り収入の算出に利用する。

Phase1では、
対象年月ごとに1件の手取り収入を登録できる。

手取り収入は、
対象年月単位で管理し、
現在の手取り収入ではなく、
対象年月時点の実績値を記録する。

手取り収入は論理削除を行わず、
登録後は更新によって内容を修正する。

収入が存在しない対象年月は、
削除ではなく、
金額を`0円`として管理する。

---

## 2. 対象API

| API ID | API名 | 概要 |
|---|---|---|
| INC-001 | 手取り収入一覧取得 | 対象年月ごとの手取り収入一覧を取得する。 |
| INC-002 | 手取り収入登録 | 対象年月の手取り収入を登録する。 |
| INC-003 | 手取り収入詳細取得 | 指定した手取り収入の詳細を取得する。 |
| INC-004 | 手取り収入更新 | 手取り収入および備考を更新する。 |
| INC-005 | 平均手取り収入取得 | 指定した判定対象年月以前の連続する3か月の平均手取り収入を取得する。 |

---

# INC-001 手取り収入一覧取得

## 1. 概要

操作対象となる利用者に登録された
手取り収入一覧を取得する。

手取り収入は、
対象年月単位で管理する。

一覧取得では、
対象年月ごとの手取り収入、
備考および対象年月を取得できる。

本APIは、
手取り収入一覧画面および
平均手取り収入の確認時に利用する。

---

## 2. ユースケース

利用者は、
登録済みの手取り収入を一覧で確認する。

例えば、
以下のような場合に使用する。

- 手取り収入一覧を表示する
- 対象年月ごとの登録内容を確認する
- 編集対象を選択する
- 平均手取り収入算出前に入力内容を確認する

---

## 3. エンドポイント

```http
GET /api/v1/net-incomes
```

---

## 4. HTTPメソッド

```http
GET
```

本APIは、
手取り収入一覧を取得する。

データの登録、
更新、
削除および状態変更は行わない。

---

## 5. 認証・利用者の扱い

Phase1では、
認証機能を実装しない。

操作対象となる利用者は、
`X-User-Id`リクエストヘッダーで指定する。

```http
X-User-Id: 1
```

指定された利用者に登録された
手取り収入のみ取得する。

他の利用者の手取り収入は取得できない。

---

### 11.1 X-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

---

### 11.2 page

`page`が指定された場合は、
以下を検証する。

- 整数であること
- 1以上であること

未指定の場合は、
API共通方針で定めたデフォルト値を使用する。

---

### 11.3 perPage

`perPage`が指定された場合は、
以下を検証する。

- 整数であること
- 1以上であること
- API共通方針で定めた最大件数以下であること

未指定の場合は、
API共通方針で定めたデフォルト値を使用する。

---

### 11.4 sort

`sort`が指定された場合は、
以下を検証する。

- 文字列であること
- 指定可能な並び順であること

指定可能な値は、
以下とする。

| 値 | 説明 |
|---|---|
| `targetYearMonth` | 対象年月 |

未指定の場合は、
`targetYearMonth`を使用する。

---

### 11.5 order

`order`が指定された場合は、
以下を検証する。

- 文字列であること
- 以下のいずれかであること

| 値 | 説明 |
|---|---|
| `asc` | 昇順 |
| `desc` | 降順 |

未指定の場合は、
`desc`を使用する。

## 12. 業務ルール

- 操作対象利用者に帰属する手取り収入のみ取得する。
- 他の利用者の手取り収入は取得しない。
- 手取り収入は対象年月ごとに1件のみ存在する。
- 手取り収入は対象年月の昇順または降順で取得する。
- 並び順はクエリパラメータで指定できる。
- 対象年月が同一の手取り収入を複数登録することはできない。
- 金額が`0円`であっても有効な手取り収入として扱う。
- 手取り収入は論理削除を行わない。
- 手取り収入一覧には、登録済みデータのみ含める。

```

## 24. テスト観点

### 24.1 正常系

- 手取り収入一覧を取得できること
- 手取り収入が1件の場合でも取得できること
- 手取り収入が複数件の場合でも取得できること
- 対象年月降順で取得できること
- 対象年月昇順で取得できること
- 金額が0円の手取り収入も取得できること
- 備考が未設定でも取得できること
- `200 OK`で返却されること

### 24.2 利用者境界

- 操作対象利用者の手取り収入のみ取得できること
- 他の利用者の手取り収入を取得できないこと
- 他利用者のデータがレスポンスへ含まれないこと

### 24.3 ページネーション

- 1ページ目を取得できること
- 指定したページを取得できること
- `perPage`どおりの件数で取得できること
- 最終ページを超えた場合は空配列を返却すること
- `meta`がAPI共通方針どおり返却されること

### 24.4 並び順

- `order=asc`で対象年月昇順となること
- `order=desc`で対象年月降順となること
- `order`未指定時は降順となること

### 24.5 データなし

- 手取り収入が未登録の場合でも正常終了すること
- `data`が空配列で返却されること
- `meta.total`が0となること

### 24.6 パラメータ

- `page`が不正な場合にエラーとなること
- `perPage`が不正な場合にエラーとなること
- `order`が不正な場合にエラーとなること

### 24.7 ヘッダー

- `X-User-Id`未指定でエラーとなること
- `X-User-Id`形式不正でエラーとなること
- 存在しない利用者IDでエラーとなること
- 論理削除済み利用者でエラーとなること

### 24.8 レスポンス契約

- JSONフィールド名がcamelCaseであること
- 手取り収入IDが文字列で返却されること
- 対象年月が`YYYY-MM`形式で返却されること
- 金額が整数で返却されること
- `memo`がNULLを許容すること
- `userId`がレスポンスへ含まれないこと
- `createdAt`がレスポンスへ含まれないこと
- `updatedAt`がレスポンスへ含まれないこと
- `data`が配列で返却されること
- `meta`がAPI共通方針どおり返却されること

### 24.9 異常系

- 想定外の例外発生時に`500 Internal Server Error`となること
- 共通エラーレスポンス形式で返却されること
- エラーレスポンスとログに同じリクエストIDが記録されること
- SQLやスタックトレースなどの内部情報がレスポンスへ含まれないこと

## 25. Laravel実装方針

### 25.1 Action

HTTPリクエストを受け付け、
ページネーション条件、
並び順および
利用者コンテキストを取得する。

Form Requestまたは入力用DTOを利用して
クエリパラメータを受け取り、
手取り収入一覧取得UseCaseを呼び出す。

UseCaseから受け取った処理結果を、
Responderへ渡す。

検索条件、
並び替え、
ページネーション処理および
レスポンス生成処理は、
Actionへ直接記述しない。

---

### 25.2 UseCase

手取り収入一覧取得の
ユースケース処理を担当する。

主な処理は、
以下とする。

- 操作対象利用者を受け取る
- ページ番号を受け取る
- 1ページ当たりの取得件数を受け取る
- 対象年月の並び順を受け取る
- Queryを呼び出して手取り収入一覧を取得する
- 取得結果とページネーション情報を返却する

本APIは参照処理のみであるため、
データの登録および更新は行わない。

---

### 25.3 Form Request / DTO

クエリパラメータの形式および
単項目バリデーションを担当する。

主な検証対象は、
以下とする。

- `page`
- `perPage`
- `order`

未指定の場合は、
以下の値を使用する。

- `page`
  - `1`
- `perPage`
  - API共通方針で定めた既定値
- `order`
  - `desc`

操作対象利用者の存在確認は、
利用者コンテキスト設定ミドルウェアで行う。

---

### 25.4 Query

操作対象利用者に帰属する
手取り収入一覧を取得する。

取得条件には、
必ず操作対象利用者IDを含める。

```php
NetIncome::query()
    ->where('user_id', $userId)
    ->orderBy(
        'target_year_month',
        $order,
    )
    ->paginate(
        perPage: $perPage,
        page: $page,
    );

---取得対象となる主なカラムは、以下とする。

- `id`
- `target_year_month`
- `amount`
- `memo`

利用者ID、登録日時および更新日時など、レスポンスに使用しない項目は必要に応じて取得対象から除外する。

手取り収入は論理削除を採用しないため、SoftDeletesに関する検索条件は使用しない。

### 25.5 Responder

UseCaseから受け取った一覧取得結果を、API共通方針に従ったHTTPレスポンスへ変換する。

正常終了時は、`200 OK` とともに手取り収入一覧を `data` 配列で返却する。

ページネーション情報は、`meta` オブジェクトとして返却する。

手取り収入が存在しない場合も、`200 OK` と空配列を返却する。

```json
{
  "data": [],
  "meta": {
    "currentPage": 1,
    "perPage": 20,
    "total": 0,
    "lastPage": 0
  }
}
```

エラー発生時は、共通エラーレスポンス形式へ変換する。

### 25.6 API Resource

データベースカラムを直接返却せず、API Resourceを利用してレスポンス形式へ変換する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'targetYearMonth' => $this->target_year_month,
    'amount' => $this->amount,
    'memo' => $this->memo,
];
```

手取り収入IDは、API共通方針に従って文字列として返却する。

金額は、日本円の整数値として返却する。

API Resourceは、Responderから利用する。

### 25.7 Middleware

以下の共通ミドルウェアを適用する。

- 利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

利用者コンテキスト設定ミドルウェアでは、`X-User-Id` を検証し、操作対象利用者を特定する。

## 26. React・TypeScriptでの利用

クエリパラメータの型は、以下とする。

```typescript
export type NetIncomeOrder = 'asc' | 'desc';

export type GetNetIncomesQuery = {
  page?: number;
  perPage?: number;
  order?: NetIncomeOrder;
};
```

手取り収入一覧項目の型は、以下とする。

```typescript
export type NetIncomeListItem = {
  id: string;
  targetYearMonth: string;
  amount: number;
  memo: string | null;
};
```

ページネーション情報の型は、以下とする。

```typescript
export type PaginationMeta = {
  currentPage: number;
  perPage: number;
  total: number;
  lastPage: number;
};
```

レスポンス型は、以下とする。

```typescript
export type NetIncomeListResponse = {
  data: NetIncomeListItem[];
  meta: PaginationMeta;
};
```

API呼び出し例は、以下とする。

```typescript
const response =
  await apiClient.get<NetIncomeListResponse>(
    '/api/v1/net-incomes',
    {
      params: {
        page: 1,
        perPage: 20,
        order: 'desc',
      },
    },
  );
```

一覧画面では、対象年月の降順を既定とし、新しい手取り収入から表示する。

取得結果が0件の場合は、エラー画面を表示せず、手取り収入が未登録であることを示す空状態を表示する。

金額が0の場合も、未登録とは区別して表示する。

```text
レコードなし
    → 未入力

amount = 0
    → 手取り収入0円
```

編集画面へ遷移する場合は、対象行の `id` を利用して INC-003 手取り収入詳細取得APIを呼び出す。

## 27. 設計上の補足

### 27.1 ページネーションを採用する理由

手取り収入は、対象年月ごとに継続して登録するため、利用期間に応じて件数が増加する。

Phase1時点では件数が少ないものの、長期間利用した場合でも一覧取得件数が無制限にならないよう、ページネーションを採用する。

ページネーション方式は、API共通方針に従う。

### 27.2 並び替え項目を対象年月に限定する理由

Phase1の一覧表示では、対象年月順で手取り収入を確認できれば十分である。

金額順、登録日時順および更新日時順による並び替えは提供しない。

並び替え対象を限定することで、API仕様およびフロントエンド実装を簡潔に保つ。

### 27.3 対象年月降順を既定とする理由

利用者が確認する可能性が高いのは、直近の手取り収入である。

そのため、`order` が指定されていない場合は、対象年月の降順で返却する。

古い対象年月から確認する必要がある場合は、`order=asc` を指定する。

### 27.4 金額0円を一覧へ含める理由

金額が0円の手取り収入は、未入力ではなく、対象年月の手取り収入が発生しなかったことを示す有効な業務データである。

そのため、金額が0円であっても一覧取得の対象から除外しない。

これにより、以下を明確に区別できる。

```text
対象年月のレコードが存在しない
    → 未入力

対象年月のレコードが存在し、
amountが0
    → 手取り収入なし
```

### 27.5 論理削除を採用しない理由

手取り収入は、登録内容に誤りがある場合、同一レコードを更新して修正する。

手取り収入が存在しない対象年月は、金額を0円として登録する。

そのため、取消状態や無効化状態を管理する必要がなく、`deleted_at` による論理削除を採用しない。

### 27.6 登録日時と更新日時を返却しない理由

一覧画面で必要となる情報は、対象年月、手取り収入額および備考である。

登録日時および更新日時は、Phase1の画面表示や業務判断には使用しない。

そのため、APIレスポンスへ含めない。

将来、更新履歴や最終更新日時を表示する要件が追加された場合に、レスポンスへの追加を再検討する。

### 27.7 平均手取り収入を本APIで返却しない理由

平均手取り収入は、単純な一覧データではなく、判定対象年月以前の連続する3か月を用いて算出する業務上の計算結果である。

そのため、一覧取得APIのレスポンスには含めず、INC-005 平均手取り収入取得APIで提供する。

これにより、一覧取得と平均値算出の責務を分離する。

# INC-002 手取り収入登録

## 1. 概要

操作対象となる利用者に対して、
対象年月の手取り収入を新規登録する。

手取り収入は、
対象年月ごとに1件のみ登録できる。

対象年月に手取り収入が発生しなかった場合は、
未登録のままにせず、
金額を`0円`として登録する。

登録した手取り収入は、
平均手取り収入の算出および
目的達成判定に利用する。

---

## 2. ユースケース

利用者は、
対象年月の手取り収入実績を登録する。

例えば、
以下のような場合に使用する。

- 当月の手取り収入を登録する
- 過去の対象年月の手取り収入を登録する
- 手取り収入がなかった対象年月を0円として登録する
- 平均手取り収入の算出に必要な実績値を登録する

登録内容に誤りがある場合は、
新しいレコードを登録せず、
INC-004 手取り収入更新APIで修正する。

---

## 3. エンドポイント

```http
POST /api/v1/net-incomes
```

指定された利用者の手取り収入として登録する。

リクエストボディでは、利用者IDを受け付けない。

## 10. リクエスト項目

| 項目 | 型 | 必須 | NULL | 説明 |
|---|---|:---:|:---:|---|
| `targetYearMonth` | string | ○ | × | 対象年月（YYYY-MM形式） |

| `memo` | string | × | ○ | 備考 |

### 10.1 targetYearMonth

手取り収入を記録する対象年月を指定する。

形式は、`YYYY-MM` とする。

```json
{
  "targetYearMonth": "2026-08"
}
```

同一利用者について、同じ対象年月の手取り収入を複数登録することはできない。

### 10.2 amount

対象年月の手取り収入金額を、日本円の整数値で指定する。

小数は受け付けない。

```json
{
  "amount": 0
}
```

負の金額は指定できない。

### 10.3 memo

手取り収入に関する任意の備考を指定する。

未入力の場合は、`null` として扱う。

```json
{
  "memo": null
}
```

空文字または空白文字のみが指定された場合は、`null` へ正規化する。

## 12. バリデーション

### 12.1 X-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

### 12.2 リクエストボディ

以下を検証する。

- JSONオブジェクトであること
- 必須項目が指定されていること
- 定義されていない項目が含まれていないこと
- 更新対象外項目が含まれていないこと

空のJSONオブジェクトは、バリデーションエラーとする。

```json
{}
```

### 12.3 targetYearMonth

以下を検証する。

- 必須であること
- 文字列であること
- `null` でないこと
- `YYYY-MM` 形式であること
- 実在する年月であること

以下は、不正な値として扱う。

- `2026-8`
- `2026/08`
- `2026-13`
- `202608`

### 12.4 amount

以下を検証する。

- 必須であること
- 整数であること
- `null` でないこと
- `0` 以上であること
- テーブル定義で許容する金額範囲内であること

以下は、不正な値として扱う。

- `-1`
- `325000.5`
- `"325000"`

`0` は、有効な手取り収入金額として受け付ける。

### 12.5 memo

`memo` が指定された場合は、以下を検証する。

- 文字列または `null` であること
- テーブル定義で定めた最大文字数以内であること

空文字または空白文字のみの場合は、`null` へ正規化する。

### 12.6 対象年月の重複

同一利用者について、指定された対象年月の手取り収入がすでに登録されていないことを検証する。

以下の組み合わせで、重複を判定する。

- `user_id`
- `target_year_month`

同じ対象年月の手取り収入が存在する場合は、重複エラーとする。

登録済みデータを修正する場合は、INC-004 手取り収入更新APIを使用する。

## 13. 業務ルール

- 操作対象利用者の手取り収入として登録する。
- 手取り収入は対象年月ごとに1件のみ登録できる。
- 同一利用者について、同一対象年月の手取り収入を重複登録できない。
- 手取り収入が発生しなかった対象年月は、金額を`0円`として登録する。
- 手取り収入は対象年月単位で管理する。
- 手取り収入は平均手取り収入の算出に利用する。
- 登録後に内容を変更する場合は、INC-004 手取り収入更新APIを使用する。
- 手取り収入は論理削除を行わない。

## 16. 排他制御

同一利用者について、
同一対象年月へ同時登録された場合は、
データベースのUNIQUE制約により
重複登録を防止する。

対象制約は、
以下とする。

```text

target_year_month
```

UNIQUE制約違反となった場合は、
業務エラーへ変換し、
重複登録エラーを返却する。

## 22. 冪等性

本APIはPOSTによる新規登録APIであるため、
冪等ではない。

同一リクエストを複数回送信した場合は、
2回目以降は同一対象年月の重複登録となり、
`409 Conflict`を返却する。

Phase1では、
冪等性キー（Idempotency-Key）は採用しない。

同一対象年月への二重登録は、
業務ルールおよびデータベースのUNIQUE制約によって防止する。

## 26. Laravel実装方針

### 26.1 Action

HTTPリクエストを受け付け、
入力値および利用者コンテキストを取得する。

Form Requestまたは入力用DTOから
登録内容を受け取り、
手取り収入登録UseCaseを呼び出す。

UseCaseから受け取った処理結果を、
Responderへ渡す。

以下の処理は、
Actionへ直接記述しない。

- 入力値の単項目バリデーション
- 対象年月の重複確認
- 手取り収入の登録処理
- トランザクション制御
- レスポンス生成処理

---

### 26.2 UseCase

手取り収入登録の
ユースケース処理を担当する。

主な処理は、
以下とする。

- 操作対象利用者を受け取る
- 登録内容を受け取る
- 同一対象年月の登録有無を確認する
- 手取り収入を登録する
- 登録結果を返却する

登録処理は、
データベーストランザクション内で実行する。

同一利用者について、
同一対象年月の手取り収入がすでに存在する場合は、
`NET_INCOME_ALREADY_EXISTS`として扱う。

---

### 26.3 Form Request / DTO

入力値の形式および
単項目バリデーションを担当する。

主な検証対象は、
以下とする。

- `targetYearMonth`
- `amount`
- `memo`

Form Requestでは、
以下を検証する。

- 必須項目
- データ型
- NULL可否
- 文字数
- 数値範囲
- 対象年月の形式
- 未定義項目の有無

同一対象年月の登録有無など、
データベースの状態に依存する業務ルールは、
Form Requestへ記述しない。

検証済みの入力値は、
登録用DTOへ変換してUseCaseへ渡す。

DTOの例：

```php
final readonly class CreateNetIncomeInput

    }

```

## 26.4 Query

## 26.5 Repository

手取り収入の永続化を担当する。

Repositoryは、UseCaseから受け取った利用者IDおよび登録内容を使用して、`net_incomes` へ新しいレコードを登録する。

登録例：

```php
$netIncome = NetIncome::query()->create([
    'user_id' => $userId,
    'target_year_month' => $input->targetYearMonth,
    'amount' => $input->amount,
    'memo' => $input->memo,
]);
```

以下の項目は、クライアントから受け取らない。

- `id`
- `user_id`
- `created_at`
- `updated_at`

`user_id` は、利用者コンテキストから設定する。

`id`、`created_at` および `updated_at` は、データベースまたはLaravelによって自動設定する。

---

## 26.6 トランザクション

以下の処理を、1つのデータベーストランザクション内で実行する。

- 対象年月の重複確認
- 手取り収入の登録

実装例：

```php
$netIncome = DB::transaction(
    function () use ($userId, $input): NetIncome {
        if ($this->query->existsByUserAndYearMonth(
            $userId,
            $input->targetYearMonth,
        )) {
            throw new NetIncomeAlreadyExistsException();
        }

        return $this->repository->create(
            $userId,
            $input,
        );
    },
);
```

処理途中で例外が発生した場合は、登録内容をロールバックする。

同時登録によってUNIQUE制約違反が発生した場合は、内部例外をそのまま返却せず、`NET_INCOME_ALREADY_EXISTS` へ変換する。

---

## 26.7 Responder

UseCaseから受け取った登録結果を、API共通方針に従ったHTTPレスポンスへ変換する。

正常終了時は、`201 Created` とともに登録した手取り収入を `data` オブジェクトで返却する。

対象年月の重複、バリデーションエラーまたは予期しない例外が発生した場合は、共通エラーレスポンス形式へ変換する。

Responderは、業務ルールの判定やデータベース操作を行わない。

---

## 26.8 API Resource

データベースカラムを直接返却せず、API Resourceを利用してAPIレスポンス形式へ変換する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'targetYearMonth' => $this->target_year_month,
    'amount' => $this->amount,
    'memo' => $this->memo,
];
```

手取り収入IDは、API共通方針に従って文字列として返却する。

金額は、日本円の整数値として返却する。

以下の項目は、レスポンスへ含めない。

- `userId`
- `createdAt`
- `updatedAt`

API Resourceは、Responderから利用する。

---

## 26.9 Middleware

以下の共通ミドルウェアを適用する。

- 利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

利用者コンテキスト設定ミドルウェアでは、`X-User-Id` を検証し、操作対象利用者を特定する。

Action以降の処理では、検証済みの利用者コンテキストを使用する。

---

## 26.10 例外変換

LaravelおよびPostgreSQLの内部例外は、そのままAPIレスポンスへ公開しない。

主な例外変換は、以下とする。

| 内部状態 | 独自エラーコード |
|---|---|
| 同一対象年月が登録済み | `NET_INCOME_ALREADY_EXISTS` |
| 入力値不正 | `VALIDATION_ERROR` |
| 利用者未指定 | `USER_CONTEXT_REQUIRED` |
| 利用者ID形式不正 | `INVALID_USER_ID` |
| 利用者不存在 | `USER_NOT_FOUND` |
| 想定外例外 | `INTERNAL_SERVER_ERROR` |

UNIQUE制約違反については、対象となった制約を判別し、`NET_INCOME_ALREADY_EXISTS` へ変換する。

SQL、スタックトレースおよび内部例外メッセージは、APIレスポンスへ含めない。

---## 28. 設計上の補足

### 28.1 POSTを採用する理由

手取り収入登録は、
新しい手取り収入リソースを作成する操作である。

そのため、
HTTPメソッドには
`POST`を採用する。

```http
POST /api/v1/net-incomes
```

---

### 28.2 対象年月単位で管理する理由

手取り収入は、
現在の収入ではなく、
対象年月時点の実績値を記録する。

対象年月ごとに管理することで、
将来の平均手取り収入算出、
目的達成判定および
過去データの再現性を維持できる。

---

### 28.3 同一対象年月を重複登録できない理由

同一利用者について、
同一対象年月の手取り収入は
1件のみ管理する。

複数件登録できるようにすると、
平均手取り収入の算出基準が曖昧になり、
業務ルールが複雑になる。

そのため、
以下の組み合わせで
UNIQUE制約を設ける。

```text
user_id
target_year_month
```

---

### 28.4 手取り収入がない場合は0円で登録する理由

対象年月に手取り収入が発生しなかった場合も、
対象年月の実績として管理する。

レコードを登録しない場合と
区別できるようにするため、
金額を`0円`として登録する。

これにより、
以下を明確に区別できる。

```text
レコードなし
    → 未入力

amount = 0
    → 手取り収入なし
```

---

### 28.5 論理削除を採用しない理由

手取り収入は、
履歴管理ではなく、
対象年月ごとの確定した実績値を管理する。

登録内容に誤りがある場合は、
同一レコードを更新して修正する。

そのため、
論理削除および取消状態は採用しない。

---

### 28.6 平均手取り収入を登録時に更新しない理由

本APIでは、
平均手取り収入を保存しない。

平均手取り収入は、
判定対象年月以前の連続する3か月の手取り収入から
都度算出する。

そのため、
登録APIでは
平均値の更新処理を行わない。

---

### 28.7 判定履歴を登録しない理由

手取り収入登録は、
目的達成判定とは独立した業務である。

本APIでは、
判定履歴を作成しない。

判定履歴は、
目的達成判定API実行時のみ登録する。

---

### 28.8 201 Createdを返却する理由

登録成功時は、
新しいリソースが作成されたことを示すため、
`201 Created`を返却する。

登録後のリソースも返却することで、
フロントエンドは
再取得せずに一覧や詳細画面を更新できる。

---

### 28.9 冪等性キーを採用しない理由

Phase1では、
Idempotency-Keyを採用しない。

同一対象年月への重複登録は、
業務ルールおよび
データベースのUNIQUE制約で防止する。

決済APIのような
通信再送対策は
Phase1では不要と判断した。

# INC-003 手取り収入詳細取得

## 1. 概要

操作対象となる利用者に登録された
指定の手取り収入を取得する。

手取り収入は、
対象年月単位で管理する。

詳細取得では、
対象年月、
手取り収入金額および
備考を取得できる。

本APIは、
手取り収入編集画面の初期表示および
登録内容の確認時に利用する。

---

## 2. ユースケース

利用者は、
登録済みの手取り収入の詳細を確認する。

例えば、
以下のような場合に使用する。

- 手取り収入編集画面を表示する
- 登録済み内容を確認する
- 手取り収入登録内容を参照する

対象データが存在しない場合は、
エラーを返却する。

---

## 3. エンドポイント

```http
GET /api/v1/net-incomes/{netIncomeId}
```

---

## 4. HTTPメソッド

```http
GET
```

本APIは、
指定した手取り収入を取得する。

データの登録、
更新および削除は行わない。

---

## 5. 認証・利用者の扱い

Phase1では、
認証機能を実装しない。

操作対象となる利用者は、
`X-User-Id`リクエストヘッダーで指定する。

```http
X-User-Id: 1
```

指定された利用者に登録された
手取り収入のみ取得できる。

他の利用者に登録された
手取り収入は取得できない。

利用者IDは、
リクエストボディまたは
パスパラメータでは受け付けない。

```

## 11. バリデーション

### 11.1 X-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

### 11.2 netIncomeId

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された手取り収入が存在すること
- 指定された手取り収入が操作対象利用者に帰属すること

他の利用者に帰属する手取り収入を指定した場合は、存在しないものとして扱う。

### 11.3 データ取得条件

手取り収入を取得する際は、以下を検索条件に含める。

```text
id = netIncomeId
かつ
user_id = 操作対象利用者ID
```

手取り収入IDだけで取得してはならない。

例えば、以下のような取得は行わない。

```php
NetIncome::findOrFail($netIncomeId);
```

操作対象利用者IDを含めて取得する。

```php
NetIncome::query()
    ->where('id', $netIncomeId)
    ->where('user_id', $userId)
    ->first();
```

取得できない場合は、`NET_INCOME_NOT_FOUND` として扱う。

---

## 12. 業務ルール

- 操作対象利用者に帰属する手取り収入のみ取得する。
- 他の利用者の手取り収入は取得できない。
- 手取り収入は対象年月ごとに1件のみ存在する。
- 手取り収入は対象年月単位で管理する。
- 手取り収入が0円であっても有効なデータとして取得する。
- 手取り収入は論理削除を行わない。
- 手取り収入の詳細取得では、平均手取り収入の算出は行わない。

## 19. HTTPステータス

| HTTPステータス | 条件 |
|---|---|
| `200 OK` | 手取り収入の取得に成功した |
| `400 Bad Request` | 利用者IDまたは手取り収入IDの形式が不正である |
| `404 Not Found` | 指定された利用者または手取り収入が存在しない |
| `500 Internal Server Error` | 想定外のサーバーエラーが発生した |

### 19.1 404の扱い

以下の場合は、`404 Not Found` を返却する。

- 指定された利用者が存在しない
- 指定された手取り収入が存在しない
- 指定された手取り収入が他の利用者に帰属する

他の利用者に帰属する手取り収入についても、対象の存在を推測できないようにするため、存在しないものとして扱う。

### 19.2 データなしとの違い

一覧取得APIでは、取得結果が0件の場合も `200 OK` と空配列を返却する。

本APIは、特定の手取り収入を指定して取得するため、対象が存在しない場合は `404 Not Found` を返却する。

## 24. テスト観点

### 24.1 正常系

- 指定した手取り収入を取得できること
- 金額が0円でも取得できること
- 備考が未設定でも取得できること
- 備考が設定されている場合も取得できること
- `200 OK`で返却されること

### 24.2 利用者境界

- 操作対象利用者の手取り収入のみ取得できること
- 他の利用者の手取り収入は取得できないこと
- 他利用者のデータがレスポンスへ含まれないこと

### 24.3 手取り収入ID

- 存在する手取り収入IDを指定すると取得できること
- 存在しない手取り収入IDを指定すると404となること
- 他利用者の手取り収入IDを指定すると404となること
- 手取り収入ID形式不正で400となること

### 24.4 ヘッダー

- `X-User-Id`未指定でエラーとなること
- 利用者ID形式不正でエラーとなること
- 存在しない利用者IDでエラーとなること
- 論理削除済み利用者でエラーとなること

### 24.5 レスポンス契約

- JSONフィールド名がcamelCaseであること
- 手取り収入IDが文字列で返却されること
- 対象年月が`YYYY-MM`形式で返却されること
- 金額が整数で返却されること
- `memo`がNULLを許容すること
- `userId`がレスポンスへ含まれないこと
- `createdAt`がレスポンスへ含まれないこと
- `updatedAt`がレスポンスへ含まれないこと
- `data`オブジェクトで返却されること

### 24.6 異常系

- 想定外の例外で`500 Internal Server Error`となること
- 共通エラーレスポンス形式で返却されること
- エラーレスポンスとログに同じリクエストIDが記録されること
- SQLやスタックトレースなどの内部情報がレスポンスへ含まれないこと

---

## 25. Laravel実装方針

### 25.1 Action

HTTPリクエストを受け付け、
パスパラメータおよび
利用者コンテキストを取得する。

手取り収入詳細取得UseCaseを呼び出し、
取得結果をResponderへ渡す。

以下の処理は、
Actionへ直接記述しない。

- 利用者境界の判定
- 手取り収入取得処理
- レスポンス生成処理

---

### 25.2 UseCase

手取り収入詳細取得の
ユースケース処理を担当する。

主な処理は、
以下とする。

- 操作対象利用者を受け取る
- 手取り収入IDを受け取る
- 手取り収入を取得する
- 取得結果を返却する

指定された手取り収入が存在しない場合、
または操作対象利用者に帰属しない場合は、
`NET_INCOME_NOT_FOUND`として扱う。

---

### 25.3 Query

操作対象利用者に帰属する
手取り収入を取得する。

取得条件には、
必ず操作対象利用者IDを含める。

取得例：

```php
$netIncome = NetIncome::query()
    ->where('id', $netIncomeId)
    ->where('user_id', $userId)
    ->first();
```

以下の取得は行わない。

```php
NetIncome::find($netIncomeId);
```

取得できなかった場合は、
`NET_INCOME_NOT_FOUND`として扱う。

論理削除を採用しないため、
SoftDeletesに関する検索条件は使用しない。

---

### 25.4 Responder

UseCaseから受け取った
手取り収入を、
API共通方針に従った
HTTPレスポンスへ変換する。

正常終了時は、
`200 OK`とともに
`data`オブジェクトで返却する。

対象が存在しない場合は、
共通エラーレスポンス形式へ変換する。

---

### 25.5 API Resource

データベースカラムを直接返却せず、
API Resourceを利用して
レスポンス形式へ変換する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'targetYearMonth' => $this->target_year_month,
    'amount' => $this->amount,
    'memo' => $this->memo,
];
```

以下の項目は、
レスポンスへ含めない。

- `userId`
- `createdAt`
- `updatedAt`

API Resourceは、
Responderから利用する。

---

### 25.6 Middleware

以下の共通ミドルウェアを適用する。

- 利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

利用者コンテキスト設定ミドルウェアでは、
`X-User-Id`を検証し、
操作対象利用者を特定する。

Action以降の処理では、
検証済みの利用者コンテキストを使用する。

---

### 25.7 例外変換

LaravelおよびPostgreSQLの内部例外は、
そのままAPIレスポンスへ公開しない。

主な例外変換は、
以下とする。

| 内部状態 | 独自エラーコード |
|---|---|
| 利用者未指定 | `USER_CONTEXT_REQUIRED` |
| 利用者ID形式不正 | `INVALID_USER_ID` |
| 利用者不存在 | `USER_NOT_FOUND` |
| 手取り収入ID形式不正 | `INVALID_NET_INCOME_ID` |
| 手取り収入不存在 | `NET_INCOME_NOT_FOUND` |
| 想定外例外 | `INTERNAL_SERVER_ERROR` |

SQL、
スタックトレースおよび
内部例外メッセージは、
APIレスポンスへ含めない。

## 27. 設計上の補足

### 27.1 詳細取得APIを分離した理由

一覧取得APIでは、
画面表示に必要な最小限の情報のみ返却する。

編集画面では、
対象となる1件の手取り収入のみ取得できれば十分であるため、
詳細取得APIを分離した。

---

### 27.2 利用者境界を検索条件へ含める理由

手取り収入IDのみで取得すると、
他の利用者のデータへアクセスできる可能性がある。

そのため、
以下を検索条件とする。

```text
id
+
user_id
```

これにより、
利用者境界を保証する。

---

### 27.3 404 Not Foundを返却する理由

以下の場合は、
いずれも対象が存在しないものとして扱う。

- 指定した手取り収入が存在しない
- 他の利用者に帰属する手取り収入を指定した

これにより、
他利用者のデータの存在有無を推測できないようにする。

---

### 27.4 平均手取り収入を返却しない理由

平均手取り収入は、
業務上の計算結果であり、
手取り収入詳細そのものではない。

そのため、
本APIでは返却しない。

平均手取り収入が必要な場合は、
INC-005 平均手取り収入取得APIを利用する。

---

### 27.5 更新可否を返却しない理由

Phase1では、
取得した手取り収入は
すべて更新可能である。

更新可否を示す
`editable`などのフラグは返却しない。

将来、
更新不可となる業務ルールが追加された場合に、
レスポンス項目の追加を検討する。

# INC-004 手取り収入更新

## 1. 概要

操作対象となる利用者に登録された
手取り収入を更新する。

更新できる項目は、
対象年月、
手取り収入金額および
備考とする。

更新後の手取り収入は、
平均手取り収入の算出および
目的達成判定に利用する。

---

## 2. ユースケース

利用者は、
登録済みの手取り収入を修正する。

例えば、
以下のような場合に使用する。

- 手取り収入金額を修正する
- 対象年月を修正する
- 備考を追加・変更する
- 手取り収入がなかった対象年月を0円へ修正する

更新対象が存在しない場合は、
エラーを返却する。

---

## 3. エンドポイント

```http
PATCH /api/v1/net-incomes/{netIncomeId}
```

---

## 4. HTTPメソッド

```http
PATCH
```

本APIは、
指定した手取り収入の一部項目を更新する。

更新対象は、
業務上変更可能な項目のみとする。

---

## 5. 認証・利用者の扱い

Phase1では、
認証機能を実装しない。

操作対象となる利用者は、
`X-User-Id`リクエストヘッダーで指定する。

```http
X-User-Id: 1
```

指定された利用者に登録された
手取り収入のみ更新できる。

他の利用者に登録された
手取り収入は更新できない。

利用者IDは、
リクエストボディまたは
パスパラメータでは受け付けない。

---

## 6. パスパラメータ

| パラメータ | 型 | 必須 | 説明 |
|---|---|:---:|---|
| `netIncomeId` | string | ○ | 更新対象となる手取り収入ID |

---

## 7. クエリパラメータ

なし。

---

## 8. リクエストヘッダー

### 8.1 必須ヘッダー

| ヘッダー名 | 必須 | 説明 |
|---|:---:|---|
| `X-User-Id` | ○ | 操作対象となる利用者ID |
| `Content-Type` | ○ | `application/json`を指定する |
| `Accept` | ○ | `application/json`を指定する |

リクエスト例

```http
PATCH /api/v1/net-incomes/15
Content-Type: application/json
Accept: application/json
X-User-Id: 1
```

---

## 9. リクエストボディ

```json
{
  "targetYearMonth": "2026-08",
  "amount": 330000,
  "memo": "残業代を修正"
}
```

手取り収入が発生しなかった場合は、
`amount`へ`0`を指定する。

```json
{
  "targetYearMonth": "2026-08",
  "amount": 0,
  "memo": "休職により収入なし"
}
```

---

## 10. リクエスト項目

| 項目 | 型 | 必須 | NULL | 説明 |
|---|---|:---:|:---:|---|
| `targetYearMonth` | string | ○ | × | 対象年月（YYYY-MM） |
| `amount` | integer | ○ | × | 手取り収入金額（円） |
| `memo` | string | × | ○ | 備考 |

---

### 10.1 targetYearMonth

更新後の対象年月を指定する。

形式は、
`YYYY-MM`とする。

```json
{
  "targetYearMonth": "2026-08"
}
```

更新後の対象年月について、
同一利用者に同じ対象年月の
手取り収入が存在する場合は更新できない。

---

### 10.2 amount

更新後の手取り収入金額を指定する。

日本円の整数値とする。

手取り収入がない場合は、
`0`を指定する。

```json
{
  "amount": 0
}
```

負の値および小数は指定できない。

---

### 10.3 memo

更新後の備考を指定する。

未入力の場合は、
`null`として扱う。

```json
{
  "memo": null
}
```

空文字または空白文字のみの場合は、
`null`へ正規化する。

---

## 11. 更新対象外項目

以下の項目は、
本APIでは更新できない。

- `id`
- `userId`
- `createdAt`
- `updatedAt`

これらの項目がリクエストへ含まれる場合は、
バリデーションエラーとする。

---

## 12. バリデーション

### 12.1 X-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

---

### 12.2 netIncomeId

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された手取り収入が存在すること
- 指定された手取り収入が操作対象利用者に帰属すること

他の利用者に帰属する手取り収入を指定した場合は、
存在しないものとして扱う。

---

### 12.3 リクエストボディ

以下を検証する。

- JSONオブジェクトであること
- 必須項目が指定されていること
- 定義されていない項目が含まれていないこと
- 更新対象外項目が含まれていないこと

空のJSONオブジェクトは、
バリデーションエラーとする。

```json
{}
```

---

### 12.4 targetYearMonth

以下を検証する。

- 必須であること
- 文字列であること
- `null`でないこと
- `YYYY-MM`形式であること
- 実在する年月であること

以下は、
不正な値として扱う。

```text
2026-8
2026/08
2026-13
202608
```

---

### 12.5 amount

以下を検証する。

- 必須であること
- 整数であること
- `null`でないこと
- 0以上であること
- テーブル定義で許容する金額範囲内であること

以下は、
不正な値として扱う。

```text
-1
325000.5
"325000"
```

`0`は、
有効な手取り収入金額として受け付ける。

---

### 12.6 memo

`memo`が指定された場合は、
以下を検証する。

- 文字列または`null`であること
- テーブル定義で定めた最大文字数以内であること

空文字または空白文字のみの場合は、
`null`へ正規化する。

---

### 12.7 対象年月の重複

更新後の対象年月について、
同一利用者にすでに登録済みの
手取り収入が存在しないことを検証する。

重複判定は、
更新対象レコード自身を除外して行う。

以下の組み合わせで判定する。

```text
user_id
target_year_month
```

重複が存在する場合は、
`NET_INCOME_ALREADY_EXISTS`を返却する。

---

## 13. 業務ルール

- 操作対象利用者に帰属する手取り収入のみ更新できる。
- 他の利用者に帰属する手取り収入は更新できない。
- 手取り収入は対象年月ごとに1件のみ管理する。
- 更新後の対象年月について、同一利用者に同じ対象年月の手取り収入が存在する場合は更新できない。
- 手取り収入が発生しなかった対象年月は、金額を`0円`として更新する。
- 手取り収入は対象年月単位で管理する。
- 更新後の手取り収入は、平均手取り収入の算出および目的達成判定で利用する。
- 手取り収入は論理削除を行わない。

---

## 14. 処理フロー

```text
リクエスト受付
    ↓
リクエストID生成
    ↓
X-User-Id検証
    ↓
手取り収入ID検証
    ↓
入力値検証
    ↓
対象年月重複確認
    ↓
手取り収入更新
    ↓
更新結果取得
    ↓
APIレスポンス形式へ変換
    ↓
200 OK返却
```

## 15. トランザクション境界

以下を、
1つのデータベーストランザクション内で実行する。

- 更新対象の存在確認
- 更新後対象年月の重複確認
- 手取り収入更新

途中で例外が発生した場合は、
ロールバックする。

---

## 16. 排他制御

同一手取り収入へ同時更新が行われた場合は、
最後にコミットされた更新内容を採用する。

更新後対象年月について、
同一利用者に重複が発生する場合は、
データベースのUNIQUE制約により更新を防止する。

対象制約は、
以下とする。

```text
user_id
target_year_month
```

UNIQUE制約違反となった場合は、
業務エラーへ変換し、
`NET_INCOME_ALREADY_EXISTS`を返却する。

## 20. HTTPステータス

| HTTPステータス | 条件 |
|---:|---|
| `200 OK` | 手取り収入の更新に成功した |
| `400 Bad Request` | 利用者IDまたは手取り収入IDの形式が不正である |
| `404 Not Found` | 指定された利用者または手取り収入が存在しない |
| `409 Conflict` | 更新後の対象年月が重複している |
| `422 Unprocessable Entity` | 入力値が不正である |
| `500 Internal Server Error` | 想定外のサーバーエラーが発生した |

---

### 20.1 404の扱い

以下の場合は、
`404 Not Found`を返却する。

- 指定された利用者が存在しない
- 指定された手取り収入が存在しない
- 指定された手取り収入が他の利用者に帰属する

他の利用者に帰属する手取り収入についても、
対象の存在を推測できないようにするため、
存在しないものとして扱う。

---

### 20.2 409の扱い

以下の場合は、
`409 Conflict`を返却する。

- 更新後の対象年月が、
  同一利用者の既存データと重複する

入力値自体は正しいが、
現在のリソース状態と競合して更新できないため、
`409 Conflict`を返却する。

| `INVALID_USER_ID` | 400 | 利用者IDの形式が不正である | × |
| `USER_NOT_FOUND` | 404 | 指定された利用者が存在しない | × |
| `INVALID_NET_INCOME_ID` | 400 | 手取り収入IDの形式が不正である | × |
| `NET_INCOME_NOT_FOUND` | 404 | 指定された手取り収入が存在しない、または利用者境界外である | × |
| `NET_INCOME_ALREADY_EXISTS` | 409 | 更新後の対象年月が重複している | × |
| `VALIDATION_ERROR` | 422 | 入力値が不正である | × |
| `INTERNAL_SERVER_ERROR` | 500 | 想定外のサーバーエラーが発生した | ○ |

エラーコードの正式な定義は、
`error-codes.md`に従う。

## 22. 冪等性

本APIは
HTTP PATCHを使用する。

同一リクエストを複数回実行した場合、
更新後の状態が変わらなければ、
結果は同一となる。

そのため、
本APIは実質的に冪等として扱う。

ただし、
更新後の対象年月が
他のデータと重複する場合は、
`409 Conflict`を返却する。

Phase1では、
ETagやIf-Matchによる
楽観ロックは採用しない。

### 23.1 net_incomes

使用する主なカラムは、
以下とする。

| カラム | 用途 |
|---|---|
| `id` | 手取り収入ID |
| `user_id` | 利用者境界 |
| `target_year_month` | 対象年月 |
| `amount` | 手取り収入金額 |
| `memo` | 備考 |
| `updated_at` | 更新日時 |

本APIでは、

更新対象は、
以下とする。

- `target_year_month`
- `amount`
- `memo`

以下の項目は更新しない。

- `id`
- `user_id`
- `created_at`

論理削除を採用しないため、
`deleted_at`は存在しない。

## 25. テスト観点

### 25.1 正常系

- 手取り収入を更新できること
- 対象年月を更新できること
- 手取り収入金額を更新できること
- 備考を更新できること
- 金額を0円へ更新できること
- 備考をNULLへ更新できること
- `200 OK`で返却されること

### 25.2 利用者境界

- 操作対象利用者の手取り収入のみ更新できること
- 他利用者の手取り収入は更新できないこと
- 他利用者のデータが更新されないこと

### 25.3 手取り収入ID

- 手取り収入ID形式不正で400となること

### 25.4 対象年月

- 対象年月を変更できること

- 更新対象自身と同じ対象年月の場合は更新できること
- `YYYY-MM`形式以外は422となること

### 25.5 手取り収入金額

- 正常な整数値へ更新できること
- 0円へ更新できること
- 負数で422となること
- 小数で422となること
- 最大値超過で422となること

### 25.6 備考

- 備考を更新できること
- 備考をNULLへ更新できること
- 最大文字数以内なら更新できること
- 最大文字数超過で422となること
- 空文字がNULLへ正規化されること

### 25.7 リクエストボディ

- 必須項目不足で422となること
- 未定義項目指定で422となること

- `createdAt`指定で422となること

- 論理削除済み利用者で404となること

### 25.9 トランザクション

- 更新途中で例外が発生した場合はロールバックされること
- 重複更新時は更新されないこと

### 25.10 同時更新

- 同時更新時にデータ整合性が維持されること
- UNIQUE制約違反時は409となること
- 想定外例外へ変換されないこと

### 25.11 レスポンス契約

- JSONフィールド名がcamelCaseであること
- 手取り収入IDが文字列で返却されること
- 対象年月が`YYYY-MM`形式で返却されること
- 金額が整数で返却されること
- `memo`がNULLを許容すること
- `userId`がレスポンスへ含まれないこと
- `createdAt`がレスポンスへ含まれないこと
- `updatedAt`がレスポンスへ含まれないこと
- `data`オブジェクトで返却されること

### 25.12 異常系

- 想定外の例外で`500 Internal Server Error`となること
- 共通エラーレスポンス形式で返却されること
- エラーレスポンスとログで同じリクエストIDが記録されること
- SQLやスタックトレースなどの内部情報がレスポンスへ含まれないこと

## 26.4 Query

更新対象となる手取り収入を取得する。

取得条件には、必ず手取り収入IDおよび操作対象利用者IDを含める。

## 26.6 トランザクション

以下の処理を、1つのデータベーストランザクション内で実行する。

- 更新対象の取得
- 更新後対象年月の重複確認
- 手取り収入の更新

実装例：

```php
$netIncome = DB::transaction(
    function () use (
        $userId,
        $netIncomeId,
        $input,
    ): NetIncome {
        $netIncome = $this->query->findByUserAndId(
            $userId,
            $netIncomeId,
        );

        if ($netIncome === null) {
            throw new NetIncomeNotFoundException();
        }

        if ($this->query->existsByUserAndYearMonthExcludingId(
            $userId,
            $input->targetYearMonth,
            $netIncomeId,
        )) {
            throw new NetIncomeAlreadyExistsException();
        }

        return $this->repository->update(
            $netIncome,
            $input,
        );
    },
);
```

処理途中で例外が発生した場合は、更新内容をロールバックする。

同時更新によってUNIQUE制約違反が発生した場合は、内部例外をそのまま返却せず、`NET_INCOME_ALREADY_EXISTS` へ変換する。

UseCaseから受け取った更新結果を、API共通方針に従ったHTTPレスポンスへ変換する。

  amount: 330000,
  memo: null,

フロントエンドでも、送信前に空文字を `null` へ変換してよい。

```typescript
const normalizedMemo =
  form.memo.trim() === ''
    ? null
    : form.memo.trim();

```typescript
const targetYearMonth = '2026-08';

対象年月を変更した場合は、他の手取り収入との重複によって `NET_INCOME_ALREADY_EXISTS` が返却される可能性がある。

### 27.4 エラー表示

バリデーションエラーでは、`error.details` の `field` を利用して入力項目ごとにエラーメッセージを表示する。

想定するフィールドは、以下とする。

- `targetYearMonth`
- `amount`
- `memo`

```typescript
if (

  === 'NET_INCOME_ALREADY_EXISTS'

  setFieldError(
    'targetYearMonth',
    '指定した対象年月の手取り収入はすでに登録されています。',

```

`NET_INCOME_NOT_FOUND` が返却された場合は、一覧画面へ戻し、対象データが存在しないことを表示する。

### 27.5 更新中の画面制御

更新リクエスト送信中は、二重送信を防止するため、更新ボタンを非活性にする。

更新完了後またはエラー発生後に、操作可能な状態へ戻す。

Phase1では、冪等性キーは使用しない。

同一リクエストが二重送信された場合でも、最終状態は同じとなるが、不要なAPI呼び出しを防ぐためフロントエンドでも二重送信を抑止する。

## 28. 設計上の補足

### 28.1 PATCHを採用する理由

本APIは、既存の手取り収入リソースを更新するため、`PATCH` を採用する。

```http
PATCH /api/v1/net-incomes/{netIncomeId}
```

現時点では、`targetYearMonth` および `amount` を必須としているが、リソース全体を置き換える操作ではない。

利用者ID、手取り収入ID、登録日時などは変更せず、業務上更新可能な項目のみ変更する。

### 28.2 対象年月を更新可能とする理由

手取り収入を誤った対象年月へ登録した場合に、新しいレコードを作り直さず、既存レコードの対象年月を修正できるようにする。

更新後の対象年月についても、同一利用者内で1件のみというルールを維持する。

対象年月を変更しても、手取り収入IDは変更しない。

### 28.3 手取り収入IDを維持する理由

本APIは、既存の手取り収入を修正する操作である。

対象年月や金額を変更しても、同じ業務データの訂正として扱うため、手取り収入IDは変更しない。

これにより、更新前後で同一レコードとして追跡できる。

### 28.4 論理削除を採用しない理由

手取り収入は、対象年月ごとの実績値を管理する。

誤登録は更新によって修正し、手取り収入がなかった場合は金額を0円として管理する。

そのため、取消状態または無効化状態を設けず、論理削除も採用しない。

### 28.5 更新後の平均手取り収入を保存しない理由

手取り収入を更新しても、平均手取り収入を別途保存または更新しない。

平均手取り収入は、INC-005 平均手取り収入取得APIまたは目的達成判定時に、最新の手取り収入から都度算出する。

これにより、手取り収入と保存済み平均値の不整合を防止する。

### 28.6 保存済み判定履歴を変更しない理由

手取り収入を更新しても、過去に保存された目的達成判定履歴は変更しない。

判定履歴は、判定実行時点の入力値および計算結果を保持するスナップショットとして扱う。

更新後の手取り収入を反映した結果が必要な場合は、目的達成判定を再実行し、新しい判定履歴を作成する。

### 28.7 Last Write Winsを採用する理由

Phase1では、同一手取り収入を複数人が同時編集する可能性が低い。

楽観ロックやETagを導入すると、実装およびフロントエンドの制御が複雑になる。

そのため、同時更新時は最後に完了した更新を採用するLast Write Wins方式とする。

将来、複数利用者による同時編集が増えた場合は、`updated_at` またはバージョン番号を使用した楽観ロックを再検討する。

### 28.8 同一内容の更新を正常終了とする理由

更新内容が現在値と同じ場合も、エラーとはせず、`200 OK` を返却する。

同一内容であることを理由に特別な業務エラーを設ける必要がなく、クライアント側の処理を単純にできるためである。

# INC-005 平均手取り収入取得

## 1. 概要

操作対象となる利用者について、
指定した判定対象年月以前の
連続する3か月の手取り収入から
平均手取り収入を算出して取得する。

平均手取り収入は、
目的達成判定で使用する
業務上の計算結果であり、
データベースへ保存しない。

取得時点の手取り収入をもとに、
都度算出する。

---

## 2. ユースケース

利用者は、
目的達成判定に使用される
平均手取り収入を確認する。

例えば、
以下のような場合に使用する。

- 目的達成判定画面を表示する
- 判定対象となる平均手取り収入を確認する
- 判定ロジックの入力値を確認する

平均手取り収入を算出できない場合は、
業務ルールに従ったレスポンスを返却する。

```

登録、
更新および削除は行わない。

## 10. リクエスト項目

| 1 | `2026-05` |
| 2 | `2026-06` |
| 3 | `2026-07` |

## 11. バリデーション

### 11.1 X-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

### 11.2 targetYearMonth

以下を検証する。

- 指定されていること
- 文字列であること
- `null` でないこと
- `YYYY-MM` 形式であること
- 実在する年月であること

以下は、不正な値として扱う。

- `2026-8`
- `2026/08`
- `2026-13`
- `202608`

### 11.3 未定義クエリパラメータ

本APIで受け付けるクエリパラメータは、`targetYearMonth` のみとする。

未定義のクエリパラメータが指定された場合は、バリデーションエラーとする。

例えば、以下のリクエストは受け付けない。

```http

```

Phase1では、平均算出期間をクライアントから変更する機能は提供しない。

### 11.4 算出対象年月

指定された判定対象年月から、直前の連続する3か月を算出する。

算出した各対象年月について、操作対象利用者の手取り収入が1件ずつ登録されていることを確認する。

金額が0円の手取り収入は、登録済みの有効なデータとして扱う。

以下の場合は、平均手取り収入を算出できない。

- 算出対象となる3か月のうち、1か月以上のレコードが存在しない
- 対象年月の連続性を満たす3件のデータを取得できない

データ不足は、入力形式の不正ではなく、平均手取り収入を算出できない業務状態として扱う。

具体的なエラーコードおよびHTTPステータスは、後続のエラーレスポンスで定義する。

### 11.5 0円の扱い

手取り収入額が0円の対象年月も、平均値の算出対象へ含める。

例えば、以下の3か月が登録されている場合は、平均手取り収入を算出できる。

| 対象年月 | 手取り収入 |
|---|---:|
| `2026-05` | 300,000円 |
| `2026-06` | 0円 |
| `2026-07` | 330,000円 |

`0円` は未入力ではないため、データ不足として扱わない。

## 12. 業務ルール

- 操作対象利用者の手取り収入のみを算出対象とする。
- 平均手取り収入は、指定した判定対象年月より前の連続する3か月を対象として算出する。
- 判定対象年月自身の手取り収入は算出対象に含めない。
- 算出対象期間に登録された手取り収入がすべて存在する場合のみ平均値を返却する。
- 手取り収入が0円であっても有効な業務データとして平均値の算出対象に含める。
- 平均手取り収入はデータベースへ保存しない。
- 平均手取り収入は取得時点のデータから都度算出する。
- 算出対象データが不足している場合は、平均手取り収入を返却しない。

## 25. Laravel実装方針

### 25.1 Action

HTTPリクエストを受け付け、

### 25.2 UseCase

平均手取り収入取得の
ユースケース処理を担当する。

主な処理は、
以下とする。

## 25.4 対象年月の計算

判定対象年月から、直前の連続する3か月を算出する。

例えば、判定対象年月が `2026-08` の場合は、以下を算出対象とする。

- `2026-05`
- `2026-06`
- `2026-07`

年月の加減算は、文字列の切り出しや数値の直接加算ではなく、年月を扱える値オブジェクトまたは日付ライブラリを利用する。

Laravel実装では、Carbonを利用する場合でも、年月計算をActionやQueryへ分散させず、専用の値オブジェクトまたはDomain Serviceへ集約する。

値オブジェクトの例：

```php
final readonly class YearMonth
{
    public function __construct(
        public int $year,
        public int $month,
    ) {
    }

    public static function fromString(string $value): self
    {
        [$year, $month] = array_map(
            'intval',
            explode('-', $value),
        );

        return new self($year, $month);
    }

    public function subtractMonths(int $months): self
    {
        $date = CarbonImmutable::create(
            $this->year,
            $this->month,
            1,
        )->subMonthsNoOverflow($months);

        return new self(
            $date->year,
            $date->month,
        );
    }

    public function toString(): string
    {
        return sprintf(
            '%04d-%02d',
            $this->year,
            $this->month,
        );
    }
}
```

## 25.5 Query

操作対象利用者について、算出対象となる3か月の手取り収入を取得する。

検索条件には、必ず操作対象利用者IDを含める。

取得例：

```php
$netIncomes = NetIncome::query()
    ->where('user_id', $userId)
    ->whereIn(
        'target_year_month',
        $calculatedMonths,
    )
    ->orderBy('target_year_month')
    ->get([
        'target_year_month',
        'amount',
    ]);
```

取得対象となるカラムは、以下とする。

- `target_year_month`
- `amount`

以下の項目は、平均値の算出に使用しないため取得不要とする。

- `id`
- `memo`
- `created_at`
- `updated_at`

取得件数が3件であることだけでなく、必要な3か月がすべて揃っていることを確認する。

例えば、意図しないデータを含む3件が取得された場合でも、算出対象年月との一致を検証する。

## 25.6 Domain Service

平均手取り収入の算出を担当する。

Domain Serviceは、算出対象となる3か月の手取り収入金額を受け取り、平均値を返却する。

例：

```php
final class AverageNetIncomeCalculator
{
    /**
     * @param list<int> $amounts
     */
    public function calculate(array $amounts): int
    {
        if (count($amounts) !== 3) {
            throw new InvalidArgumentException(
                '平均手取り収入の算出には3件の金額が必要です。',
            );
        }

        return intdiv(
            array_sum($amounts),
            count($amounts),
        );
    }
}
```

平均値の端数処理は、機能要件またはAPI設計で定めたルールに従う。

現時点で端数処理が未確定の場合は、`intdiv()` による切り捨てを暗黙に採用せず、以下のいずれを採用するか確定してから実装する。

- 切り捨て
- 四捨五入
- 切り上げ

計算ロジックをUseCaseやResponderへ直接記述しない。

---

## 25.7 データ不足の判定

Queryから取得した結果について、算出対象となる3か月がすべて登録されていることを確認する。

確認対象は、以下とする。

- 取得件数が3件であること
- 取得した対象年月が算出対象年月と完全に一致すること
- 同一対象年月のデータが重複していないこと

金額が0円のデータは、登録済みの有効なデータとして扱う。

以下の場合は、`NET_INCOME_DATA_INSUFFICIENT` を発生させる。

- 算出対象のうち1か月以上が未登録である
- 必要な3か月と取得結果の対象年月が一致しない
- 連続する3か月のデータを取得できない

例：

```php
$actualMonths = $netIncomes
    ->pluck('target_year_month')
    ->all();

if ($actualMonths !== $calculatedMonths) {
    throw new NetIncomeDataInsufficientException(
        requiredMonths: $calculatedMonths,
        actualMonths: $actualMonths,
    );
}
```

## 25.8 トランザクション

本APIは参照処理のみであるため、明示的なデータベーストランザクションは使用しない。

手取り収入の取得および平均手取り収入の算出によって、データベースの状態を変更しない。

Phase1では、算出処理中の厳密なスナップショット分離は保証しない。

## 25.9 Responder

UseCaseから受け取った算出結果を、API共通方針に従ったHTTPレスポンスへ変換する。

正常終了時は、`200 OK` とともに以下を `data` オブジェクトで返却する。

- 判定対象年月
- 平均手取り収入
- 算出対象年月一覧

データ不足の場合は、`422 Unprocessable Entity` および `NET_INCOME_DATA_INSUFFICIENT` へ変換する。

Responderは、算出対象年月の決定や平均値の計算を行わない。

## 25.10 API Resource

計算結果をAPIレスポンス形式へ変換する。

Eloquent Modelを直接返却するAPIではないため、算出結果用のDTOまたはResourceを使用する。

算出結果DTOの例：

```php
final readonly class AverageNetIncomeResult
{
    /**
     * @param list<string> $calculatedMonths
     */
    public function __construct(
        public string $targetYearMonth,
        public int $averageAmount,
        public array $calculatedMonths,
    ) {
    }
}
```

Resourceの変換例：

```php
return [
    'targetYearMonth' => $this->targetYearMonth,
    'averageAmount' => $this->averageAmount,
    'calculatedMonths' => $this->calculatedMonths,
];
```

`calculatedMonths` は、古い対象年月から新しい対象年月の順で返却する。

```json
{
  "calculatedMonths": [
    "2026-05",
    "2026-06",
    "2026-07"
  ]
}
```

## 25.12 例外変換

LaravelおよびPostgreSQLの内部例外は、そのままAPIレスポンスへ公開しない。

主な例外変換は、以下とする。

| 内部状態 | 独自エラーコード |
|---|---|
| 利用者未指定 | `USER_CONTEXT_REQUIRED` |
| 利用者ID形式不正 | `INVALID_USER_ID` |
| 利用者不存在 | `USER_NOT_FOUND` |
| 判定対象年月の形式不正 | `INVALID_TARGET_YEAR_MONTH` |
| 算出対象データ不足 | `NET_INCOME_DATA_INSUFFICIENT` |
| 想定外例外 | `INTERNAL_SERVER_ERROR` |

SQL、スタックトレースおよび内部例外メッセージは、APIレスポンスへ含めない。

データ不足例外には、ログ調査に必要な範囲で以下の情報を記録する。

- 操作対象利用者ID
- 判定対象年月
- 必要な算出対象年月
- 実際に取得できた対象年月
- リクエストID

手取り収入金額などの業務データを不要にエラーログへ出力しない。

## 26. React・TypeScriptでの利用

クエリパラメータの型は、
以下とする。

```ts
export type GetAverageNetIncomeQuery = {
  targetYearMonth: string;
};
```

---

レスポンス型は、以下とする。

```typescript
export type AverageNetIncome = {
  targetYearMonth: string;
  averageAmount: number;
  calculatedMonths: [
    string,
    string,
    string,
  ];
};

export type AverageNetIncomeResponse = {
  data: AverageNetIncome;
};
```

`calculatedMonths` は、平均手取り収入の算出対象となった連続する3か月を、古い対象年月から順に保持する。

API呼び出し例は、以下とする。

```typescript
const response =
  await apiClient.get<AverageNetIncomeResponse>(
    '/api/v1/net-incomes/average',
    {
      params: {
        targetYearMonth: '2026-08',
      },
    },
  );
```

取得結果の例は、以下とする。

```json
{
  "data": {
    "targetYearMonth": "2026-08",
    "averageAmount": 310000,
    "calculatedMonths": [
      "2026-05",
      "2026-06",
      "2026-07"
    ]
  }
}
```

取得した平均手取り収入は、以下の画面表示に利用する。

* 目的達成判定画面
* 判定前の入力値確認
* 平均手取り収入の計算根拠表示

### 26.1 targetYearMonthの扱い

`targetYearMonth` は、API共通方針に従い `YYYY-MM` 形式で送信する。

```typescript
const targetYearMonth = '2026-08';
```

対象年月は、日付ではなく年月を表す業務値として扱う。

JavaScriptの `Date` オブジェクトへ不必要に変換せず、原則として文字列で保持する。

フロントエンドで年月の加減算が必要な場合も、文字列の切り出しや月部分への直接加算は行わない。

### 26.2 averageAmountの扱い

`averageAmount` は、日本円の整数値として扱う。

フロントエンドでは再計算せず、APIが返却した値を表示および目的達成判定画面の確認用に使用する。

```typescript
const formattedAverageAmount =
  new Intl.NumberFormat('ja-JP', {
    style: 'currency',
    currency: 'JPY',
    maximumFractionDigits: 0,
  }).format(response.data.averageAmount);
```

平均値の端数処理は、バックエンドの業務ルールに従う。

フロントエンド独自の切り捨て、切り上げまたは四捨五入は行わない。

### 26.3 calculatedMonthsの扱い

`calculatedMonths` は、平均手取り収入の算出根拠として画面へ表示できる。

表示例：

```text
算出対象：
2026-05、2026-06、2026-07
```

フロントエンドでは、`targetYearMonth` から対象年月を再計算せず、APIが返却した `calculatedMonths` を使用する。

これにより、バックエンドとフロントエンドで対象年月の計算結果がずれることを防止する。

### 26.4 データ不足時の扱い

算出対象となる3か月のデータが不足している場合は、`NET_INCOME_DATA_INSUFFICIENT` が返却される。

フロントエンドでは、システムエラーとして扱わず、平均手取り収入を算出できない業務状態として表示する。

表示例：

```text
平均手取り収入を算出できません。

判定対象年月より前の連続する3か月について、
手取り収入を入力してください。
```

不足している対象年月を画面へ具体的に表示する場合は、将来、エラーレスポンスへ不足年月を含めることを検討する。

Phase1では、共通メッセージを表示し、手取り収入一覧または登録画面へ遷移できるようにする。

### 26.5 ローディング表示

平均手取り収入の取得中は、計算結果が確定していないことを示すローディング表示を行う。

取得中に、直前に取得した別の判定対象年月の平均値を現在の結果として表示しない。

判定対象年月を変更した場合は、以前の取得結果をいったん破棄するか、新しい取得が完了するまで計算中であることを明示する。

### 26.6 エラー表示

入力値に問題がある場合は、`error.details` の `field` を利用して対象年月の入力欄へエラーを表示する。

想定するフィールドは、以下とする。

* `targetYearMonth`

エラーコードごとの基本的な扱いは、以下とする。

| エラーコード                         | フロントエンドの扱い         |
| ------------------------------ | ------------------ |
| `INVALID_TARGET_YEAR_MONTH`    | 対象年月入力欄へ形式エラーを表示する |
| `NET_INCOME_DATA_INSUFFICIENT` | データ不足の案内を表示する      |
| `USER_NOT_FOUND`          | 利用者選択画面へ戻す       |
| `INTERNAL_SERVER_ERROR`        | 共通エラー表示を行う         |

## 27. 設計上の補足

### 27.1 独立した集計APIとして提供する理由

平均手取り収入は、手取り収入レコードそのものではなく、複数月のデータから求める業務上の計算結果である。

そのため、手取り収入一覧取得APIの追加項目として返却せず、独立したAPIとして提供する。

```http
GET /api/v1/net-incomes/average
```

これにより、以下の責務を分離できる。

* 手取り収入一覧の取得
* 特定の判定対象年月に対する平均値の算出

### 27.2 判定対象年月を必須とする理由

平均手取り収入の算出対象は、判定対象年月によって変わる。

そのため、API実行時の現在年月を暗黙に使用せず、`targetYearMonth` を必須とする。

これにより、過去または将来の判定対象年月についても、同じルールで再現可能な計算結果を取得できる。

### 27.3 判定対象年月自身を含めない理由

平均手取り収入は、判定対象年月より前に確定している連続する3か月の実績から算出する。

判定対象年月自身の手取り収入を含めると、判定時点で未入力または未確定の値に依存する可能性がある。

そのため、判定対象年月自身は算出対象へ含めない。

### 27.4 連続する3か月に限定する理由

直近の収入状況を目的達成判定へ反映するため、判定対象年月直前の連続する3か月を使用する。

任意の3件や、登録済みデータの直近3件を使用すると、未入力月を飛ばして平均値を算出する可能性がある。

そのため、対象年月の連続性を必須とする。

### 27.5 0円を算出対象に含める理由

手取り収入が0円のレコードは、未入力ではなく、対象年月に収入がなかったことを示す実績値である。

そのため、平均手取り収入の算出対象へ含める。

```text
レコードなし
    → データ不足

amount = 0
    → 算出対象となる有効な実績値
```

### 27.6 平均手取り収入を保存しない理由

平均手取り収入は、基礎となる手取り収入から算出可能な派生値である。

データベースへ保存すると、手取り収入の更新後に保存済み平均値との不整合が発生する可能性がある。

そのため、取得時点の手取り収入をもとに都度算出する。

### 27.7 calculatedMonthsを返却する理由

平均手取り収入だけを返却すると、どの対象年月を計算に使用したかをクライアントから確認できない。

そのため、計算根拠として `calculatedMonths` を返却する。

これにより、以下が容易になる。

* 画面上での計算根拠表示
* デバッグ
* APIテスト
* 判定対象年月の計算誤りの検知

### 27.8 各月の金額を返却しない理由

本APIの責務は、平均手取り収入およびその算出対象年月を返却することである。

各月の手取り収入金額は、手取り収入一覧取得APIで確認できる。

そのため、Phase1では本APIのレスポンスへ各月の個別金額を含めない。

計算過程の詳細表示が必要になった場合は、レスポンス拡張を再検討する。

### 27.9 データ不足を422とする理由

データ不足時も、`targetYearMonth` の形式やリクエスト構造自体は正しい。

しかし、平均手取り収入を算出するための業務上の成立条件を満たしていない。

そのため、`404 Not Found` や `400 Bad Request` ではなく、`422 Unprocessable Entity` を返却する。

### 27.10 データ不足時に平均値を返さない理由

1か月または2か月分だけで暫定平均を算出すると、「直前の連続する3か月を使用する」という業務ルールと異なる結果になる。

不足月を0円として補完することも、実際に収入がなかった場合と未入力の場合を混同するため行わない。

したがって、3か月分が揃っていない場合は、平均手取り収入を返却しない。

### 27.11 端数処理をバックエンドへ集約する理由

3か月の合計金額が3で割り切れない場合、平均手取り収入には端数が発生する。

端数処理をフロントエンドへ委ねると、画面やクライアントごとに結果が異なる可能性がある。

そのため、端数処理はバックエンドのDomain Serviceへ集約する。

採用する端数処理方法は、機能要件およびAPI仕様へ明記し、Laravel実装とReact表示で統一する。

端数処理方法が未決定の間は、切り捨て、四捨五入または切り上げのいずれかを暗黙に採用しない。

### 27.12 キャッシュを採用しない理由

平均手取り収入は、3件の手取り収入を取得して行う小規模な計算である。

Phase1では、キャッシュを導入する性能上の効果よりも、手取り収入更新時のキャッシュ無効化処理による複雑さの方が大きい。

そのため、HTTPキャッシュおよびアプリケーションキャッシュは採用しない。

### 27.13 目的達成判定APIとの関係

本APIは、利用者が平均手取り収入を事前確認するための参照APIである。

目的達成判定APIは、クライアントから渡された `averageAmount` をそのまま信頼して使用しない。

判定実行時は、バックエンド側で同じ算出ロジックを使用し、平均手取り収入を再計算する。

これにより、クライアントによる値の改変や、表示後に手取り収入が更新された場合の不整合を防止する。

平均手取り収入の計算処理は、本APIと目的達成判定APIから同じDomain Serviceを利用する。

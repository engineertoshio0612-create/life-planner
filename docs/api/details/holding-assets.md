# 保有商品API詳細設計

## 1. 概要

本書では、
保有商品APIに関する詳細仕様を定義する。

保有商品APIでは、
商品単位で管理する資産口座に属する
保有商品の取得、登録、更新および無効化を行う。

保有商品は、
月末資産管理および目的達成判定の基礎情報となる。

保有商品の登録対象は、
商品単位で管理する資産口座に限定する。

---

## 2. 対象API

| API ID | API名 | HTTPメソッド | URL |
|---|---|---|---|
| HLD-001 | 保有商品一覧取得 | GET | `/api/v1/holding-assets` |
| HLD-002 | 保有商品登録 | POST | `/api/v1/holding-assets` |
| HLD-003 | 保有商品詳細取得 | GET | `/api/v1/holding-assets/{holdingAssetId}` |
| HLD-004 | 保有商品更新 | PATCH | `/api/v1/holding-assets/{holdingAssetId}` |
| HLD-005 | 保有商品無効化 | PATCH | `/api/v1/holding-assets/{holdingAssetId}` |

# HLD-001 保有商品一覧取得

## 1. 概要

操作対象となるデモ利用者に帰属する
保有商品の一覧を取得する。

利用中の保有商品だけでなく、
無効化された保有商品も取得対象とする。

保有商品ごとに、
所属する資産口座および現在の利用状態を返却する。

---

## 2. ユースケース

利用者は、
登録済みの保有商品を一覧で確認する。

一覧では、
以下の情報を確認できる。

- 保有商品名
- 所属する資産口座
- 利用開始年月
- 利用状態

無効化された保有商品も表示し、
利用中の保有商品と区別できるようにする。

---

## 3. エンドポイント

```http
GET /api/v1/holding-assets
```

---

## 4. HTTPメソッド

```http
GET
```

本APIは、
保有商品の参照のみを行う。

---

## 5. 認証・利用者の扱い

Phase1では、
認証機能を実装しない。

操作対象となるデモ利用者は、
`X-Demo-User-Id`
リクエストヘッダーで指定する。

```http
X-Demo-User-Id: 1
```

指定された利用者に帰属する
保有商品のみ取得する。

- 並び順変更
- ページネーション

## 10. バリデーション

以下を検証する。

- X-Demo-User-Idが指定されていること
- X-Demo-User-Idが正しい形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

---

## 11. 業務ルール

- 指定された利用者の保有商品のみ取得する。
- 他利用者の保有商品は取得しない。
- 利用中および無効化済み保有商品を取得する。
- 商品単位で管理する資産口座に属する保有商品のみ取得する。
- 無効化済み保有商品は利用状態が判別できる形式で返却する。
- 利用中の保有商品を先に表示する。
- 同一利用状態では商品名の昇順で表示する。
- 保有商品の所属資産口座も返却する。
- データベース内部カラムは公開しない。

---

## 12. 表示順

保有商品は、
以下の順序で表示する。

1. 利用中
2. 無効化済み
3. 商品名昇順

利用状態は、
`holding_assets.deleted_at`
から判定する。

# HLD-002 保有商品登録

## 1. 概要

操作対象となるデモ利用者の資産口座に、
保有商品を新規登録する。

保有商品を登録できるのは、
残高記録単位が「商品単位」であり、
対象年月時点で有効な資産口座のみとする。

---

## 2. ユースケース

利用者は、
商品単位で資産を管理する資産口座に対して、
保有商品を登録する。

登録した保有商品は、
商品別月末評価額の登録対象として使用する。

利用者は、
以下の情報を入力する。

- 保有商品名
- 商品種別
- 所属資産口座
- 利用開始年月
- 備考

## 10. リクエスト項目

| 項目 | 型 | 必須 | NULL | 説明 |
|------|----|:---:|:---:|------|
| assetAccountId | string | ○ | × | 所属する資産口座ID |
| name | string | ○ | × | 保有商品名 |
| productType | string | ○ | × | 商品種別 |
| startYearMonth | string | ○ | × | 利用開始年月（YYYY-MM形式） |
| memo | string | × | ○ | 備考 |

### 10.1 assetAccountId

保有商品が所属する資産口座IDを指定する。

指定できるのは、以下をすべて満たす資産口座とする。

- 操作対象利用者に帰属していること
- 論理削除されていないこと
- 残高記録単位が商品単位であること
- 利用開始年月が保有商品の利用開始年月以前であること

### 10.2 name

利用者が保有商品を識別するための名称を指定する。

同一資産口座内では、同じ名称の利用中の保有商品を重複登録できない。

### 10.3 productType

商品の分類を指定する。

想定する値は以下のとおりとする。

| 値 | 意味 |
|----|------|
| `INVESTMENT_TRUST` | 投資信託 |
| `DOMESTIC_STOCK` | 国内株 |
| `FOREIGN_STOCK` | 外国株 |
| `ETF` | ETF |
| `DEPOSIT` | 預金 |
| `BOND` | 債券 |
| `OTHER` | その他 |

商品種別は、商品別の集計および表示に使用する。

### 10.4 startYearMonth

保有商品を保有開始した対象年月を指定する。

形式は `YYYY-MM` とする。

所属資産口座の利用開始年月より前の年月は指定できない。

### 10.5 memo

保有商品に関する任意の備考を指定する。

未入力の場合は `null` として扱う。

空文字が指定された場合は、`null` へ正規化する。

## 11. バリデーション

### 11.1 assetAccountId

- 必須であること
- API共通方針で定めたID形式であること
- 指定された資産口座が存在すること
- 指定された資産口座が操作対象利用者に帰属すること
- 指定された資産口座が論理削除されていないこと

### 11.2 name

- 必須であること
- 文字列であること
- 空文字または空白文字のみでないこと
- テーブル定義で定めた最大文字数以内であること

### 11.3 productType

- 必須であること
- 定義された商品種別のいずれかであること

### 11.4 startYearMonth

- 必須であること
- `YYYY-MM` 形式であること
- 実在する年月であること

### 11.5 memo

- 文字列または `null` であること
- テーブル定義で定めた最大文字数以内であること

---

## 12. 業務ルール

- 操作対象利用者に帰属する資産口座にのみ登録できる。
- 残高記録単位が商品単位の資産口座にのみ登録できる。
- 口座単位で管理する資産口座には登録できない。
- 無効化済みの資産口座には登録できない。
- 所属資産口座の利用開始年月より前を、保有商品の利用開始年月として指定できない。
- 同一資産口座内に、同じ名称の利用中の保有商品を重複登録できない。
- 他の資産口座に同じ名称の保有商品が存在する場合は登録できる。
- 他の利用者に同じ名称の保有商品が存在する場合は登録できる。
- 商品種別は所属資産口座の資産種別や利用可能資産区分と連動しない。
- 登録時点では商品別月末評価額を作成しない。
- 登録した保有商品は、利用開始年月以降の商品別月末評価額の登録対象となる。

---

## 13. 重複判定

重複判定は、以下の組み合わせで行う。

- `asset_account_id`
- `name`
- `deleted_at`

同一資産口座に、同じ名称の利用中の保有商品が存在する場合は、重複エラーとする。

無効化済みの保有商品と同じ名称で再度登録する場合は、新しい保有商品として登録できる。

新しく登録した保有商品には、新しい保有商品IDを採番する。

過去の商品別月末評価額は、無効化済みの旧保有商品IDとの関連を保持する。

## 15. トランザクション境界

保有商品の登録処理は、データベーストランザクション内で実行する。

処理途中でエラーが発生した場合は、登録内容をロールバックする。

本APIで更新する主なテーブルは、`holding_assets` のみである。

ただし、重複確認から登録までの間に別のリクエストが同じ保有商品を登録する可能性があるため、データベースの一意制約を最終的な整合性保証として使用する。

---

## 16. 排他制御

Phase1では、明示的な行ロックは行わない。

同時登録による重複は、アプリケーションによる事前確認とデータベースの一意制約によって防止する。

データベースの一意制約違反が発生した場合は、同一名称の保有商品がすでに登録されているものとして扱う。

## 20. HTTPステータス

| HTTPステータス | 条件 |
|----------------|------|
| `201 Created` | 保有商品の登録に成功した |
| `400 Bad Request` | 利用者IDが未指定、または形式が不正である |
| `404 Not Found` | 指定された利用者または資産口座が存在しない |
| `409 Conflict` | 同一資産口座内に同名の保有商品が存在する |
| `422 Unprocessable Entity` | 入力値または業務ルールに違反している |
| `500 Internal Server Error` | 想定外のサーバーエラーが発生した |

### 20.1 404の扱い

他の利用者に帰属する資産口座を指定した場合も、指定された資産口座が存在しない場合と同様に `404 Not Found` を返却する。

他の利用者に資産口座が存在することをレスポンスから推測できないようにするためである。

### 20.2 409と422の使い分け

同一資産口座内の商品名重複は、既存リソースとの競合であるため、`409 Conflict` を返却する。

以下のような業務ルール違反は、`422 Unprocessable Entity` を返却する。

- 口座単位の資産口座を指定した
- 無効化済みの資産口座を指定した
- 保有商品の利用開始年月が資産口座の利用開始年月より前である

エラーコードの正式な定義は、エラーコード一覧に従う。

## 25. テスト観点

### 25.1 正常系

- 必須項目を指定して保有商品を登録できること
- 備考を指定せず登録できること
- 登録結果が `201 Created` で返却されること
- 登録した保有商品が `data` オブジェクトで返却されること
- IDが文字列で返却されること
- `isEnabled` が `true` で返却されること
- 商品種別がAPI用の列挙値で返却されること

### 25.2 利用者境界

- 操作対象利用者の資産口座へ登録できること
- 他の利用者の資産口座へ登録できないこと
- 他の利用者の資産口座を指定した場合に `404 Not Found` となること
- 登録された `user_id` が操作対象利用者と一致すること

### 25.3 所属資産口座

- 商品単位の資産口座へ登録できること
- 口座単位の資産口座へ登録できないこと
- 無効化済み資産口座へ登録できないこと
- 存在しない資産口座へ登録できないこと
- 所属資産口座の利用開始年月と同じ年月を指定できること
- 所属資産口座の利用開始年月より前を指定できないこと

### 25.4 重複

- 同一資産口座内に同名の利用中商品を登録できないこと
- 別の資産口座には同名商品を登録できること
- 別の利用者には同名商品を登録できること
- 無効化済み商品と同名の商品を新しい商品として登録できること
- 同時登録時もデータベース制約によって重複を防止できること

### 25.5 バリデーション

- `assetAccountId` が必須であること
- `name` が必須であること
- `productType` が必須であること
- `startYearMonth` が必須であること
- 商品名の最大文字数を超える場合にエラーとなること
- 未定義の商品種別でエラーとなること
- 不正な年月形式でエラーとなること
- 存在しない年月でエラーとなること
- 備考の最大文字数を超える場合にエラーとなること

### 25.6 トランザクション

- 登録途中で例外が発生した場合にロールバックされること
- エラー時に保有商品が登録されないこと

### 25.7 レスポンス契約

- JSONフィールド名が `camelCase` であること
- `userId` がレスポンスに含まれないこと
- `deletedAt` がレスポンスに含まれないこと
- データベースの数値コードをそのまま公開しないこと
- 備考未入力時に `memo` が `null` となること

### 25.8 異常系

- 想定外の例外発生時に `500 Internal Server Error` となること
- 共通エラーレスポンス形式で返却されること
- エラーレスポンスとログに同じリクエストIDが記録されること
- SQLやスタックトレースがレスポンスに含まれないこと

## 26. Laravel実装方針

### 26.1 Action

HTTPリクエストを受け付け、入力値およびデモ利用者コンテキストを取得する。

Form Requestまたは入力用DTOを利用して入力値を受け取り、保有商品登録UseCaseを呼び出す。

UseCaseから受け取った処理結果をResponderへ渡す。

業務ルール、重複判定、データ登録処理およびレスポンス生成処理は、Actionへ直接記述しない。

### 26.2 UseCase

保有商品登録のユースケース処理を担当する。

主な処理は以下とする。

- 操作対象利用者の受け取り
- 所属資産口座の取得
- 利用者境界の確認
- 資産口座の利用状態確認
- 残高記録単位の確認
- 利用開始年月の整合性確認
- 同名保有商品の重複確認
- 保有商品の登録
- 登録結果の返却

登録処理は、データベーストランザクション内で実行する。

### 26.3 Form Request / DTO

入力値の形式および単項目バリデーションを担当する。

主な検証対象は以下とする。

- `assetAccountId`
- `name`
- `productType`
- `startYearMonth`
- `memo`

資産口座の利用状態や残高記録単位など、データベースの状態に依存する業務ルールはForm Requestへ記述しない。

### 26.4 Query / Repository

所属資産口座の取得、同名保有商品の存在確認および保有商品の永続化を担当する。

資産口座を取得する場合は、必ず操作対象利用者IDを検索条件へ含める。

```php
AssetAccount::query()
    ->where('id', $assetAccountId)
    ->where('user_id', $demoUserId)
    ->first();
```

論理削除済み資産口座は、通常の取得対象としない。

重複確認では、同一資産口座内の未削除の保有商品のみを対象とする。

### 26.5 Responder

UseCaseから受け取った登録結果を、API共通方針に従ったHTTPレスポンスへ変換する。

正常終了時は、`201 Created` とともに登録した保有商品を返却する。

エラー発生時は、共通エラーレスポンス形式へ変換する。

### 26.6 API Resource

データベースカラムを直接返却せず、API Resourceを利用してレスポンス形式へ変換する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'assetAccountId' => (string) $this->asset_account_id,
    'assetAccountName' => $this->assetAccount->name,
    'name' => $this->name,
    'productType' => $this->productType->value,
    'startYearMonth' => $this->start_year_month,
    'memo' => $this->memo,
    'isEnabled' => $this->deleted_at === null,
];
```

API Resourceは、Responderから利用する。

### 26.7 Middleware

以下の共通ミドルウェアを適用する。

- デモ利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

## 28. 設計上の補足

### 28.1 商品種別と資産口座種別

商品種別は、保有商品の分類および集計に使用する。

資産口座の資産種別や利用可能資産区分とは独立した項目とする。

商品種別によって、利用可能資産区分を自動的に変更しない。

### 28.2 所属資産口座を変更可能項目としない理由

保有商品の所属資産口座は、過去の商品別月末評価額に影響する。

登録後に所属資産口座を変更すると、過去の資産状況の意味が変わる可能性がある。

そのため、所属資産口座の変更が必要な場合は、既存の保有商品を無効化し、新しい保有商品として登録する。

### 28.3 無効化済み商品と同名で再登録できる理由

無効化済み保有商品は、過去の商品別月末評価額との関連を保持する必要がある。

同じ商品を再度保有した場合は、旧保有商品を再有効化せず、新しい保有商品として登録する。

これにより、過去の保有期間と新しい保有期間を異なる保有商品IDで識別できる。

### 28.4 冪等性キーを採用しない理由

Phase1では、同時利用およびリクエスト再送が限定的である。

商品名の重複制約によって実質的な二重登録を防止できるため、冪等性キーは採用しない。

- 所属資産口座IDが返却されること
- 所属資産口座名が返却されること
- 利用開始年月が返却されること
- 備考が返却されること
- 利用状態が返却されること
- 保有商品IDが文字列で返却されること
- 所属資産口座IDが文字列で返却されること

### 23.2 利用者境界

- 操作対象利用者に帰属する保有商品を取得できること
- 他の利用者に帰属する保有商品を取得できないこと
- 他の利用者に帰属する保有商品を指定した場合に`404 Not Found`となること
- 同じ保有商品IDが他利用者のデータとして誤って返却されないこと

### 23.3 利用状態

- `deleted_at`が`NULL`の場合に`isEnabled`が`true`となること
- `deleted_at`が設定されている場合に`isEnabled`が`false`となること
- `deletedAt`がレスポンスへ含まれないこと

### 23.4 所属資産口座

- 所属資産口座名を取得できること
- 所属資産口座が無効化済みでも資産口座名を取得できること
- 所属資産口座の利用状態がレスポンスへ含まれないこと
- 保有商品と所属資産口座の関連が正しいこと

### 23.5 備考

- 備考が登録されている場合に文字列で返却されること
- 備考が登録されていない場合に`null`で返却されること
- 備考未登録時に空文字を返さないこと

### 23.6 ヘッダー

- `X-Demo-User-Id`が指定されていない場合にエラーとなること
- `X-Demo-User-Id`の形式が不正な場合にエラーとなること
- 存在しない利用者IDの場合にエラーとなること
- 論理削除済み利用者IDの場合にエラーとなること

### 23.7 パスパラメータ

- 正しい保有商品IDで取得できること
- 保有商品IDの形式が不正な場合にエラーとなること
- 存在しない保有商品IDの場合に`404 Not Found`となること
- 無効化済みの保有商品IDでも取得できること

### 23.8 レスポンス契約

- 共通レスポンス形式に従っていること
- JSONフィールド名がcamelCaseであること
- `userId`がレスポンスへ含まれないこと
- `createdAt`がレスポンスへ含まれないこと
- `updatedAt`がレスポンスへ含まれないこと
- `deletedAt`がレスポンスへ含まれないこと
- データベースの数値コードがそのまま公開されないこと
- `data`がオブジェクトとして返却されること

### 23.9 異常系

- 想定外の例外発生時に`500 Internal Server Error`となること
- 共通エラーレスポンス形式で返却されること
- エラーレスポンスとログに同じリクエストIDが記録されること
- SQLやスタックトレースなどの内部情報がレスポンスへ含まれないこと

## 24. Laravel実装方針

### 24.1 Action

HTTPリクエストを受け付け、保有商品IDおよびデモ利用者コンテキストを取得する。

保有商品詳細取得UseCaseを呼び出し、処理結果をResponderへ渡す。

保有商品の検索条件、利用者境界の判定、所属資産口座の取得およびレスポンス生成処理は、Actionへ直接記述しない。

---

### 24.2 UseCase

保有商品詳細取得のユースケース処理を担当する。

主な処理は、以下とする。

- 操作対象利用者を受け取る
- 保有商品IDを受け取る
- 操作対象利用者に帰属する保有商品を取得する
- 所属資産口座を取得する
- 取得結果をResponderへ返却する

利用者境界外の保有商品が指定された場合は、対象が存在しないものとして扱う。

---

### 24.3 Query

操作対象利用者に帰属する保有商品を取得する。

無効化済み保有商品も詳細表示の対象とするため、Laravel SoftDeletesを使用する場合は、`withTrashed()`を利用する。

取得時は、所属資産口座を同時に取得する。

取得例：

```php
HoldingAsset::query()
    ->withTrashed()
    ->with([
        'assetAccount' => fn ($query) => $query->withTrashed(),
    ])
    ->where('id', $holdingAssetId)
    ->where('user_id', $demoUserId)
    ->first();
```

保有商品が取得できない場合は、`HOLDING_ASSET_NOT_FOUND` として扱う。

所属資産口座についても、他利用者のデータが誤って紐づかないよう、リレーションおよび外部キー制約で整合性を保証する。

### 24.4 Responder

UseCaseから受け取った処理結果を、API共通方針に従ったHTTPレスポンスへ変換する。

正常終了時は、`200 OK` とともに保有商品詳細を `data` オブジェクトで返却する。

対象が存在しない場合は、共通エラーレスポンス形式で `404 Not Found` を返却する。

### 24.5 API Resource

データベースカラムを直接返却せず、API Resourceを利用してレスポンス形式へ変換する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'assetAccountId' => (string) $this->asset_account_id,
    'assetAccountName' => $this->assetAccount->name,
    'name' => $this->name,
    'productType' => $this->productType->value,
    'startYearMonth' => $this->start_year_month,
    'memo' => $this->memo,
    'isEnabled' => $this->deleted_at === null,
];
```

API Resourceは、Responderから利用する。

### 24.6 Middleware

以下の共通ミドルウェアを適用する。

- デモ利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

デモ利用者コンテキスト設定ミドルウェアでは、`X-Demo-User-Id` を検証し、操作対象利用者を特定する。

## 26. 設計上の補足

### 26.1 無効化済み保有商品を取得対象とする理由

無効化済み保有商品は、過去の商品別月末評価額および目的達成判定履歴との関係を保持する。

そのため、一覧表示および詳細表示では取得対象とする。

新しい商品別月末評価額の登録対象にはしない。

### 26.2 所属資産口座名を返却する理由

保有商品の詳細画面および編集画面では、所属する資産口座名を表示する必要がある。

`assetAccountId` のみを返却すると、画面表示のために別途資産口座APIを呼び出す必要がある。

Phase1では、詳細取得APIで `assetAccountName` も返却し、フロントエンドのAPI呼び出しを増やさない方針とする。

### 26.3 所属資産口座の利用状態を返却しない理由

Phase1の保有商品詳細画面では、所属資産口座名を表示できれば十分である。

所属資産口座の利用状態まで返却すると、本APIの責務およびレスポンス項目が増える。

そのため、`assetAccountEnabled` は返却しない。

所属資産口座の利用状態を表示する要件が追加された場合に、レスポンスへの追加を再検討する。

### 26.4 他利用者の保有商品を404として扱う理由

他の利用者に帰属する保有商品を指定した場合に、権限エラーとして返却すると、指定した保有商品が存在することを推測できる。

Phase1では認証を実装しないが、利用者境界を意識したAPI設計とするため、利用者境界外の保有商品は存在しないものとして扱う。

### 26.5 キャッシュを採用しない理由

Phase1では、保有商品の詳細取得頻度およびデータ量が少ない。

キャッシュを導入すると、更新・無効化時のキャッシュ破棄処理が必要となり、実装が複雑になる。

性能上の効果よりも実装負荷が大きいため、Phase1ではキャッシュを採用しない。

# HLD-004 保有商品更新

## 1. 概要

操作対象となるデモ利用者に帰属する保有商品の更新可能な情報を変更する。

本APIでは、以下の項目を更新できる。

- 保有商品名
- 商品種別
- 備考

所属資産口座、利用開始年月および利用状態は、本APIの更新対象としない。

利用状態の変更は、HLD-005 保有商品無効化APIで行う。

---

## 2. ユースケース

利用者は、登録済みの保有商品について、名称、商品種別または備考を修正する。

例えば、以下のような場合に使用する。

- 保有商品名の表記を修正する
- 商品種別の登録誤りを修正する
- 備考を追加または変更する

所属資産口座を変更する場合は、既存の保有商品を無効化し、新しい保有商品として登録する。

---

## 3. エンドポイント

```http
PATCH /api/v1/holding-assets/{holdingAssetId}
```

---

## 4. HTTPメソッド

`PATCH`

本APIは、保有商品の一部項目を更新する。

更新対象として指定されなかった項目は、既存の値を維持する。

---

## 5. 認証・利用者の扱い

Phase1では、認証機能を実装しない。

操作対象となるデモ利用者は、`X-Demo-User-Id` リクエストヘッダーで指定する。

```http
X-Demo-User-Id: 1
```

指定された利用者に帰属する保有商品のみ更新できる。

他の利用者に帰属する保有商品は更新できない。

---

## 6. パスパラメータ

| パラメータ | 型 | 必須 | 説明 |
|---|---|:---:|---|
| holdingAssetId | string | ○ | 更新対象となる保有商品ID |

---

## 7. クエリパラメータ

なし。

---

## 8. リクエストヘッダー

### 8.1 必須ヘッダー

| ヘッダー名 | 必須 | 説明 |
|---|:---:|---|
| X-Demo-User-Id | ○ | 操作対象となるデモ利用者ID |
| Content-Type | ○ | `application/json` を指定する |
| Accept | ○ | `application/json` を指定する |

リクエスト例：

```http
PATCH /api/v1/holding-assets/15
Content-Type: application/json
Accept: application/json
X-Demo-User-Id: 1
```

---

## 9. リクエストボディ

更新する項目のみ指定する。

```json
{
  "name": "eMAXIS Slim 全世界株式（オール・カントリー）",
  "productType": "INVESTMENT_TRUST",
  "memo": "NISAつみたて投資枠"
}
```

備考を未設定へ戻す場合は、`null` を指定する。

```json
{
  "memo": null
}
```

---

## 10. リクエスト項目

| 項目 | 型 | 必須 | NULL | 説明 |
|---|---|:---:|:---:|---|
| name | string | × | × | 保有商品名 |
| productType | string | × | × | 商品種別 |
| memo | string | × | ○ | 備考 |

少なくとも1項目を指定する。

### 10.1 name

利用者が保有商品を識別するための名称を指定する。

同一資産口座内では、他の利用中保有商品と同じ名称へ変更できない。

現在の保有商品自身の名称は、重複判定から除外する。

### 10.2 productType

商品の分類を指定する。

指定できる値は、HLD-002 保有商品登録APIと同じ商品種別とする。

| 値 | 意味 |
|---|---|
| `INVESTMENT_TRUST` | 投資信託 |
| `DOMESTIC_STOCK` | 国内株 |
| `FOREIGN_STOCK` | 外国株 |
| `ETF` | ETF |
| `DEPOSIT` | 預金 |
| `BOND` | 債券 |
| `OTHER` | その他 |

商品種別を変更しても、所属資産口座、利用可能資産区分および過去の商品別月末評価額は変更しない。

### 10.3 memo

保有商品に関する任意の備考を指定する。

`null` を指定した場合は、備考を未設定へ変更する。

空文字が指定された場合は、`null` へ正規化する。

---

## 11. 更新対象外項目

以下の項目は、本APIでは更新できない。

- `assetAccountId`
- `startYearMonth`
- `isEnabled`
- `id`
- `userId`
- `createdAt`
- `updatedAt`
- `deletedAt`

更新対象外項目がリクエストへ含まれている場合は、バリデーションエラーとする。

所属資産口座の変更が必要な場合は、現在の保有商品を無効化し、新しい保有商品として登録する。

利用状態の変更は、HLD-005 保有商品無効化APIで行う。

---

## 12. バリデーション

### 12.1 X-Demo-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

### 12.2 holdingAssetId

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された保有商品が存在すること
- 指定された保有商品が操作対象利用者に帰属すること
- 指定された保有商品が利用中であること

他の利用者に帰属する保有商品を指定した場合は、存在しないものとして扱う。

無効化済みの保有商品は、本APIでは更新できない。

### 12.3 リクエストボディ

以下を検証する。

- JSONオブジェクトであること
- 更新可能な項目が1つ以上指定されていること
- 更新対象外項目が含まれていないこと

空のJSONオブジェクトは、バリデーションエラーとする。

```json
{}
```

### 12.4 name

`name` が指定された場合は、以下を検証する。

- 文字列であること
- `null` でないこと
- 空文字または空白文字のみでないこと
- テーブル定義で定めた最大文字数以内であること

同一資産口座内に、更新対象以外の同名かつ利用中の保有商品が存在する場合は、重複エラーとする。

### 12.5 productType

`productType` が指定された場合は、以下を検証する。

- 文字列であること
- `null` でないこと
- 定義された商品種別のいずれかであること

### 12.6 memo

`memo` が指定された場合は、以下を検証する。

- 文字列または `null` であること
- テーブル定義で定めた最大文字数以内であること

空文字および空白文字のみの場合は、`null` へ正規化する。

## 13. 業務ルール

- 操作対象利用者に帰属する保有商品のみ更新できる。
- 他の利用者に帰属する保有商品は更新できない。
- 無効化済みの保有商品は更新できない。
- 更新できる項目は、保有商品名、商品種別および備考のみとする。
- 所属資産口座は変更できない。
- 利用開始年月は変更できない。
- 利用状態は本APIでは変更できない。
- 保有商品名を変更する場合は、同一資産口座内の他の利用中保有商品と重複してはならない。
- 他の資産口座に同じ名称の保有商品が存在する場合は更新できる。
- 他の利用者に同じ名称の保有商品が存在する場合は更新できる。
- 商品種別を変更しても、所属資産口座および利用可能資産区分は変更しない。
- 商品種別を変更しても、過去の商品別月末評価額は変更しない。
- 備考へ `null` を指定した場合は、備考を未設定へ変更する。
- リクエストで指定されていない項目は、現在の値を維持する。
- 更新後も同じ保有商品IDを継続して使用する。

---

## 14. 重複判定

保有商品名の重複判定は、以下の条件で行う。

```text
asset_account_idが同一
かつ
nameが同一
かつ
deleted_atがNULL
かつ
idが更新対象の保有商品IDと異なる
```

更新対象の保有商品自身は、重複判定から除外する。

名称を変更しない場合は、現在の保有商品自身によって重複エラーにならないようにする。

同一資産口座内に、更新後の名称と同じ名称を持つ他の利用中保有商品が存在する場合は、重複エラーとする。

無効化済みの保有商品と同じ名称への変更は許可する。

## 15. 処理フロー

```text
リクエスト受付
    ↓
リクエストID生成
    ↓
X-Demo-User-Id検証
    ↓
操作対象利用者の特定
    ↓
holdingAssetId検証
    ↓
リクエストボディのバリデーション
    ↓
更新対象保有商品の取得
    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

```

## 16. トランザクション境界

保有商品の更新処理は、データベーストランザクション内で実行する。

処理途中でエラーが発生した場合は、更新内容をロールバックする。

本APIで更新するテーブルは、`holding_assets` のみとする。

重複確認から更新までの間に、別のリクエストによる更新が発生する可能性があるため、データベースの一意制約を最終的な整合性保証として使用する。

---

## 17. 排他制御

Phase1では、楽観ロック用のバージョン番号や明示的な行ロックは採用しない。

同一保有商品に対する更新が同時に実行された場合は、後から完了した更新内容が反映される可能性がある。

ただし、商品名の重複については、アプリケーションによる事前確認とデータベースの一意制約によって防止する。

将来、複数利用者による同時編集が増えた場合は、以下の方式を再検討する。

- 更新日時を利用した楽観ロック
- バージョン番号による楽観ロック
- `If-Match` および `ETag`
- 行ロック

| data.isEnabled | boolean | × | 利用状態 |

## 21. HTTPステータス

| HTTPステータス | 条件 |
|---|---|
| `200 OK` | 保有商品の更新に成功した |
| `400 Bad Request` | 利用者IDまたは保有商品IDの形式が不正である |
| `404 Not Found` | 指定された利用者または保有商品が存在しない |
| `409 Conflict` | 更新後の商品名が同一資産口座内の他の利用中保有商品と重複する |
| `422 Unprocessable Entity` | 入力値または業務ルールに違反している |
| `500 Internal Server Error` | 想定外のサーバーエラーが発生した |

### 21.1 404の扱い

他の利用者に帰属する保有商品を指定した場合も、指定された保有商品が存在しない場合と同様に `404 Not Found` を返却する。

### 21.2 409と422の使い分け

同一資産口座内の保有商品名重複は、既存リソースとの競合であるため、`409 Conflict` を返却する。

以下の場合は、リクエスト内容または業務ルールの違反として `422 Unprocessable Entity` を返却する。

- 空のJSONオブジェクトが指定された
- 更新対象外項目が指定された
- 無効化済みの保有商品を更新しようとした
- 未定義の商品種別が指定された
- 項目の形式や文字数が不正である

## 23. 冪等性

本APIは、同じ更新内容を複数回送信した場合に最終的なリソース状態が同じになるため、冪等である。

例えば、以下のリクエストを複数回送信しても、保有商品の最終状態は変わらない。

```json
{
  "memo": "NISAつみたて投資枠"
}
```

同一内容を再送した場合も、正常な更新として `200 OK` を返却する。

Phase1では、更新内容が現在値と同一である場合でも、特別なエラーや `204 No Content` は返却しない。

冪等性キーは使用しない。

## 25. 関連する機能要件

- `5.3 編集`
  - 保有商品名、商品種別および備考を編集できる
  - 所属資産口座および利用開始年月は通常の編集対象としない
- `5.4 商品種別`
  - 定義された商品種別へ変更できる
- `5.5 所属資産口座`
  - 保有商品は必ず1つの資産口座に所属する
- `5.6 所属資産口座の変更`
  - 月末評価額が登録されている保有商品の所属資産口座は変更できない
  - 所属資産口座を変更する場合は新しい保有商品として登録する
- `5.7 無効化`
  - 保有商品の無効化は更新とは別の業務操作として扱う
- `5.10 バリデーション`
  - 保有商品名の必須・文字数・重複を検証する
  - 商品種別は定義された値のみ許可する
- `5.11 業務ルール`
  - 所属資産口座の変更時は新しい保有商品として登録する
  - 過去の商品別月末評価額を現在値で更新しない

## 26. テスト観点

### 26.1 正常系

- 保有商品名のみ更新できること
- 商品種別のみ更新できること
- 備考のみ更新できること
- 複数の更新可能項目を同時に更新できること
- 指定していない項目は既存値を維持すること
- 備考へ`null`を指定して未設定へ変更できること
- 備考へ空文字を指定した場合に`null`へ正規化されること
- 更新後の保有商品が`200 OK`で返却されること
- 更新後も保有商品IDが変更されないこと
- 更新後も所属資産口座IDが変更されないこと
- 更新後も利用開始年月が変更されないこと
- 更新後も利用状態が変更されないこと

### 26.2 部分更新

- `name`だけを指定して更新できること
- `productType`だけを指定して更新できること
- `memo`だけを指定して更新できること
- リクエストに含まれない項目が`null`や初期値へ変更されないこと
- 同じ更新内容を複数回送信しても最終状態が同じになること

### 26.3 利用者境界

- 操作対象利用者に帰属する保有商品を更新できること
- 他の利用者に帰属する保有商品を更新できないこと
- 他の利用者の保有商品を指定した場合に`404 Not Found`となること
- 更新対象の`user_id`が変更されないこと

### 26.4 利用状態

- 利用中の保有商品を更新できること
- 無効化済みの保有商品を更新できないこと
- 無効化済み保有商品の更新時に`HOLDING_ASSET_DISABLED`となること
- 本APIで`isEnabled`を変更できないこと
- 本APIで`deleted_at`が変更されないこと

### 26.5 重複

- 現在と同じ名称で更新できること
- 同一資産口座内の他の利用中保有商品と同名へ変更できないこと
- 別の資産口座に同名商品が存在しても更新できること
- 別の利用者に同名商品が存在しても更新できること
- 無効化済み保有商品と同じ名称へ変更できること
- 同時更新時にデータベース制約によって重複を防止できること

### 26.6 更新対象外項目

- `assetAccountId`を指定した場合にバリデーションエラーとなること
- `startYearMonth`を指定した場合にバリデーションエラーとなること
- `isEnabled`を指定した場合にバリデーションエラーとなること
- `id`を指定した場合にバリデーションエラーとなること
- `userId`を指定した場合にバリデーションエラーとなること
- `deletedAt`を指定した場合にバリデーションエラーとなること

### 26.7 バリデーション

- 空のJSONオブジェクトでエラーとなること
- 保有商品名が`null`の場合にエラーとなること
- 保有商品名が空文字の場合にエラーとなること
- 保有商品名が空白文字のみの場合にエラーとなること
- 保有商品名の最大文字数を超える場合にエラーとなること
- 商品種別が`null`の場合にエラーとなること
- 未定義の商品種別でエラーとなること
- 備考の最大文字数を超える場合にエラーとなること
- リクエストボディがJSONオブジェクトでない場合にエラーとなること

### 26.8 パスパラメータ

- 正しい保有商品IDで更新できること
- 保有商品IDの形式が不正な場合にエラーとなること
- 存在しない保有商品IDの場合に`404 Not Found`となること

### 26.9 ヘッダー

- `X-Demo-User-Id`が指定されていない場合にエラーとなること
- `X-Demo-User-Id`の形式が不正な場合にエラーとなること
- 存在しない利用者IDの場合にエラーとなること
- 論理削除済み利用者IDの場合にエラーとなること

### 26.10 トランザクション

- 更新途中で例外が発生した場合にロールバックされること
- 重複エラー発生時に更新前の値が維持されること
- バリデーションエラー時にデータが変更されないこと

### 26.11 レスポンス契約

- JSONフィールド名がcamelCaseであること
- 保有商品IDが文字列で返却されること
- 所属資産口座IDが文字列で返却されること
- 所属資産口座名が返却されること
- `userId`がレスポンスへ含まれないこと
- `createdAt`がレスポンスへ含まれないこと
- `updatedAt`がレスポンスへ含まれないこと
- `deletedAt`がレスポンスへ含まれないこと
- データベースの数値コードがそのまま公開されないこと
- `data`がオブジェクトとして返却されること

### 26.12 異常系

- 想定外の例外発生時に`500 Internal Server Error`となること
- 共通エラーレスポンス形式で返却されること
- エラーレスポンスとログに同じリクエストIDが記録されること
- SQLやスタックトレースなどの内部情報がレスポンスへ含まれないこと

## 27. Laravel実装方針

### 27.1 Action

HTTPリクエストを受け付け、
保有商品ID、
更新内容および
デモ利用者コンテキストを取得する。

Form Requestまたは入力用DTOを利用して
更新内容を受け取り、
保有商品更新UseCaseを呼び出す。

UseCaseから受け取った処理結果を、
Responderへ渡す。

業務ルール、
利用者境界の判定、
重複判定、
更新処理および
レスポンス生成処理は、
Actionへ直接記述しない。

---

### 27.2 UseCase

保有商品更新の
ユースケース処理を担当する。

主な処理は、
以下とする。

- 操作対象利用者の受け取り
- 保有商品IDの受け取り
- 更新内容の受け取り
- 更新対象保有商品の取得
- 利用者境界の確認
- 保有商品の利用状態確認
- 更新対象外項目の確認
- 保有商品名の重複確認
- 指定された項目のみ更新
- 更新結果の返却

更新処理は、
データベーストランザクション内で実行する。

---

### 27.3 Form Request / DTO

入力値の形式および
単項目バリデーションを担当する。

主な検証対象は、
以下とする。

- `name`
- `productType`
- `memo`

更新可能な項目が
1つ以上指定されていることを検証する。

以下の更新対象外項目が含まれている場合は、
バリデーションエラーとする。

- `assetAccountId`
- `startYearMonth`
- `isEnabled`
- `id`
- `userId`
- `createdAt`
- `updatedAt`
- `deletedAt`

保有商品の利用状態や
商品名の重複など、
データベースの状態に依存する業務ルールは、
Form Requestへ記述しない。

---

### 27.4 Query / Repository

更新対象保有商品の取得、
同名保有商品の存在確認および
保有商品の更新を担当する。

保有商品を取得する場合は、
必ず操作対象利用者IDを検索条件へ含める。

```php
HoldingAsset::query()
    ->where('id', $holdingAssetId)
    ->where('user_id', $demoUserId)
    ->first();
```

通常の取得では、論理削除済み保有商品を対象外とする。

無効化済み保有商品かどうかを独自エラーとして判定する必要がある場合は、`withTrashed()` で取得した上で利用状態を確認する方法を採用できる。

重複確認では、以下の条件を使用する。

```php
HoldingAsset::query()
    ->where('asset_account_id', $holdingAsset->asset_account_id)
    ->where('name', $newName)
    ->whereKeyNot($holdingAsset->id)
    ->exists();
```

Laravel SoftDeletesを使用する場合、通常のクエリでは論理削除済み保有商品が重複確認から除外される。

更新時は、リクエストで指定された項目のみ変更する。

### 27.5 Responder

UseCaseから受け取った更新結果を、API共通方針に従ったHTTPレスポンスへ変換する。

正常終了時は、`200 OK` とともに更新後の保有商品を返却する。

対象が存在しない場合、無効化済みの場合、重複している場合またはバリデーションエラーの場合は、共通エラーレスポンス形式へ変換する。

### 27.6 API Resource

データベースカラムを直接返却せず、API Resourceを利用してレスポンス形式へ変換する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'assetAccountId' => (string) $this->asset_account_id,
    'assetAccountName' => $this->assetAccount->name,
    'name' => $this->name,
    'productType' => $this->productType->value,
    'startYearMonth' => $this->start_year_month,
    'memo' => $this->memo,
    'isEnabled' => $this->deleted_at === null,
];
```

API Resourceは、Responderから利用する。

更新後のレスポンス生成時は、所属資産口座を取得済みであることを保証する。

### 27.7 Middleware

以下の共通ミドルウェアを適用する。

- デモ利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

デモ利用者コンテキスト設定ミドルウェアでは、`X-Demo-User-Id` を検証し、操作対象利用者を特定する。

更新リクエスト型の例は、以下とする。

```typescript
export type ProductType =
  | 'INVESTMENT_TRUST'

  | 'FOREIGN_STOCK'
  | 'ETF'
  | 'DEPOSIT'
  | 'BOND'

  name?: string;
```

```typescript
export type HoldingAsset = {

  assetAccountName: string;

  startYearMonth: string;
  memo: string | null;
  isEnabled: boolean;
```

更新画面では、HLD-003 保有商品詳細取得APIのレスポンスを初期値として使用する。

利用者が変更した項目のみを更新リクエストへ含める。

- 所属資産口座
- 利用開始年月
- 利用状態

利用状態の変更は、HLD-005 保有商品無効化APIを使用する。

## 29. 設計上の補足

### 29.1 所属資産口座を変更できない理由

保有商品は、
所属資産口座との関係を前提として、
商品別月末評価額および
月末資産状況を管理する。

所属資産口座を変更すると、
過去の商品別月末評価額との整合性が失われる可能性がある。

そのため、
所属資産口座は更新対象としない。

所属資産口座を変更する必要がある場合は、
現在の保有商品を無効化し、
新しい保有商品として登録する。

---

### 29.2 利用開始年月を変更できない理由

利用開始年月は、
保有商品の利用開始時点を表す履歴情報である。

利用開始年月を変更すると、
対象年月ごとの資産状況や
商品別月末評価額との整合性が失われる可能性がある。

そのため、
利用開始年月は更新対象としない。

---

### 29.3 PATCHを採用する理由

本APIでは、
保有商品の一部項目のみ変更できれば十分である。

PUTのように
リソース全体を送信する方式ではなく、
変更対象のみ送信できるPATCHを採用する。

これにより、
不要なデータ送信を防ぎ、
フロントエンド実装も簡潔になる。

---

### 29.4 商品種別変更時の扱い

商品種別を変更しても、
保有商品IDは変更しない。

また、
所属資産口座、
利用可能資産区分、
過去の商品別月末評価額および
月末資産状況は変更しない。

商品種別は、
表示および集計で利用する分類情報として扱う。

---

### 29.5 部分更新を採用する理由

更新対象を限定することで、
誤更新を防止できる。

また、
React・TypeScriptからは
変更した項目のみ送信すればよく、
更新APIの利用が容易になる。

# HLD-005 保有商品無効化

## 1. 概要

操作対象となるデモ利用者に帰属する
利用中の保有商品を無効化する。

無効化した保有商品は、
無効化後の対象年月における
商品別月末評価額の登録対象としない。

過去の商品別月末評価額、
月末資産状況および
目的達成判定履歴は保持する。

保有商品は物理削除せず、
`deleted_at`による論理削除で無効化を表現する。

---

## 2. ユースケース

利用者は、
売却、解約または保有終了などにより、
今後利用しなくなった保有商品を無効化する。

例えば、
以下の場合に使用する。

- 投資信託を売却した
- 株式をすべて売却した
- 預金商品を解約した
- 今後の商品別月末評価額を登録しない

同じ保有商品を再度管理する場合は、
無効化した保有商品を再有効化せず、
新しい保有商品として登録する。

---

## 3. エンドポイント

```http
PATCH /api/v1/holding-assets/{holdingAssetId}
```

## 4. HTTPメソッド

`PATCH`

本APIは、保有商品の利用状態のみを変更する。

保有商品名、商品種別、所属資産口座、利用開始年月および備考は変更しない。

---

## 5. 認証・利用者の扱い

Phase1では、認証機能を実装しない。

操作対象となるデモ利用者は、`X-Demo-User-Id` リクエストヘッダーで指定する。

```http
X-Demo-User-Id: 1
```

指定された利用者に帰属する保有商品のみ無効化できる。

他の利用者に帰属する保有商品は、無効化できない。

---

## 10. リクエスト項目

| 項目 | 型 | 必須 | NULL | 説明 |
|---|---|:---:|:---:|---|
| `isEnabled` | boolean | ○ | × | 保有商品の利用状態。無効化時は `false` のみ指定可能 |

### 10.1 isEnabled

保有商品を無効化するため、`false` を指定する。

```json
{
  "isEnabled": false
}
```

Phase1では、無効化済み保有商品の再有効化を提供しない。

そのため、`true` は指定できない。

無効化済みの商品と同じ商品を再度管理する場合は、新しい保有商品として登録する。

---

## 11. 更新対象外項目

本APIでは、`isEnabled` 以外の項目を変更できない。

以下の項目は、更新対象外とする。

- `id`
- `assetAccountId`
- `assetAccountName`
- `name`
- `productType`
- `startYearMonth`
- `memo`
- `userId`
- `createdAt`
- `updatedAt`
- `deletedAt`

更新対象外項目がリクエストへ含まれている場合は、バリデーションエラーとする。

保有商品名、商品種別および備考の変更は、HLD-004 保有商品更新APIで行う。

## 12. バリデーション

### 12.1 X-Demo-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

### 12.2 holdingAssetId

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された保有商品が存在すること
- 指定された保有商品が操作対象利用者に帰属すること

他の利用者に帰属する保有商品を指定した場合は、存在しないものとして扱う。

### 12.3 リクエストボディ

以下を検証する。

- JSONオブジェクトであること
- `isEnabled` が指定されていること
- `isEnabled` 以外の項目が含まれていないこと

空のJSONオブジェクトは、バリデーションエラーとする。

```json
{}
```

### 12.4 isEnabled

以下を検証する。

- 必須であること
- `boolean` であること
- `null` でないこと
- `false` であること

以下の指定は、バリデーションエラーとする。

```json
{
  "isEnabled": true
}
```

Phase1では再有効化を提供しないため、`true` は受け付けない。

### 12.5 利用状態

対象となる保有商品の利用状態について、以下を検証する。

- 対象の保有商品が利用中であること
- `deleted_at` が `NULL` であること

すでに無効化済みの保有商品を指定した場合は、業務ルール違反として扱う。

無効化済みかどうかを明示的に判定する必要があるため、Laravel SoftDeletesを使用する場合は、`withTrashed()` で取得した上で `deleted_at` を確認する。

---

## 13. 業務ルール

- 操作対象利用者に帰属する保有商品のみ無効化できる。
- 他の利用者に帰属する保有商品は無効化できない。
- 利用中の保有商品のみ無効化できる。
- 無効化済みの保有商品は再度無効化できない。
- 保有商品名、商品種別、所属資産口座、利用開始年月および備考は変更しない。
- 保有商品の無効化は、論理削除（`deleted_at`の設定）によって行う。
- 無効化した保有商品は、無効化後の商品別月末評価額登録対象としない。
- 過去の商品別月末評価額、月末資産状況および目的達成判定履歴は保持する。
- 同じ商品を再度管理する場合は、新しい保有商品として登録する。
- 無効化した保有商品を再有効化しない。


## 15. トランザクション境界

保有商品の無効化処理は、
データベーストランザクション内で実行する。

処理途中で例外が発生した場合は、
論理削除をロールバックする。

本APIで更新するテーブルは、
`holding_assets`のみとする。

---

## 16. 排他制御

Phase1では、
明示的な行ロックおよび
楽観ロックは採用しない。

同一保有商品に対して
同時に無効化が実行された場合は、
先に無効化した結果を採用する。

後続処理では、
すでに無効化済みであることを検知し、
業務ルール違反として扱う。

## 20. HTTPステータス

| HTTPステータス | 条件 |
|---:|---|
| `200 OK` | 無効化成功 |
| `400 Bad Request` | 利用者IDまたは保有商品IDの形式が不正 |
| `404 Not Found` | 指定された利用者または保有商品が存在しない |
| `422 Unprocessable Entity` | 業務ルール違反 |
| `500 Internal Server Error` | 想定外のサーバーエラー |

### 20.1 404の扱い

他の利用者に帰属する保有商品を指定した場合も、
存在しないものとして扱い、
`404 Not Found`を返却する。

### 20.2 422の扱い

以下の場合は、
業務ルール違反として
`422 Unprocessable Entity`を返却する。

- すでに無効化済みである
- `isEnabled=true`を指定した
- 更新対象外項目が指定された

## 22. 冪等性

本APIは、
同一保有商品に対して
複数回無効化リクエストが送信された場合でも、
最終状態は同じとなる。

ただし、
Phase1では、
すでに無効化済みの保有商品に対する無効化は、
業務ルール違反として
`422 Unprocessable Entity`を返却する。

冪等性キーは採用しない。

  - 無効化済み保有商品も利用状態を識別して表示する
- `5.9 表示順`
  - 利用中の保有商品を無効化済み保有商品より先に表示する

  - 利用終了した保有商品も過去の資産履歴では表示する
  - 保有商品の評価額を対象年月ごとに管理する
  - 現在の状態によって過去データを更新しない

## 25. テスト観点

### 25.1 正常系

- 利用中の保有商品を無効化できること
- 無効化成功時に`200 OK`となること
- 無効化後の保有商品が`data`オブジェクトで返却されること
- 無効化後の`isEnabled`が`false`となること
- 保有商品IDが変更されないこと
- 所属資産口座IDが変更されないこと
- 保有商品名が変更されないこと
- 商品種別が変更されないこと
- 利用開始年月が変更されないこと
- 備考が変更されないこと
- `deleted_at`に無効化日時が設定されること
- `updated_at`が更新されること

### 25.2 利用者境界

- 操作対象利用者に帰属する保有商品を無効化できること
- 他の利用者に帰属する保有商品を無効化できないこと
- 他の利用者の保有商品を指定した場合に`404 Not Found`となること
- 無効化対象の`user_id`が変更されないこと
- 他利用者の保有商品へ影響しないこと

### 25.3 利用状態

- 利用中の保有商品を無効化できること
- すでに無効化済みの保有商品を再度無効化できないこと
- 無効化済み保有商品の再実行時に`HOLDING_ASSET_ALREADY_DISABLED`となること
- `isEnabled=true`を指定した場合にエラーとなること
- 本APIで再有効化できないこと

### 25.4 更新対象外項目

- `name`を指定した場合にバリデーションエラーとなること
- `productType`を指定した場合にバリデーションエラーとなること
- `assetAccountId`を指定した場合にバリデーションエラーとなること
- `startYearMonth`を指定した場合にバリデーションエラーとなること
- `memo`を指定した場合にバリデーションエラーとなること
- `id`を指定した場合にバリデーションエラーとなること
- `userId`を指定した場合にバリデーションエラーとなること
- `deletedAt`を直接指定した場合にバリデーションエラーとなること

### 25.5 リクエストボディ

- `isEnabled=false`で無効化できること
- `isEnabled`が未指定の場合にエラーとなること
- `isEnabled=null`の場合にエラーとなること
- `isEnabled`がboolean以外の場合にエラーとなること
- 空のJSONオブジェクトでエラーとなること
- JSONオブジェクト以外のリクエストでエラーとなること
- `isEnabled`以外の項目が含まれている場合にエラーとなること

### 25.6 パスパラメータ

- 正しい保有商品IDで無効化できること
- 保有商品IDの形式が不正な場合にエラーとなること
- 存在しない保有商品IDの場合に`404 Not Found`となること

### 25.7 ヘッダー

- `X-Demo-User-Id`が指定されていない場合にエラーとなること
- `X-Demo-User-Id`の形式が不正な場合にエラーとなること
- 存在しない利用者IDの場合にエラーとなること
- 論理削除済み利用者IDの場合にエラーとなること

### 25.8 履歴保持

- 保有商品を無効化しても過去の商品別月末評価額が削除されないこと
- 保有商品を無効化しても過去の月末資産状況が変更されないこと
- 保有商品を無効化しても保存済みの目的達成判定履歴が変更されないこと
- 無効化済み保有商品を一覧取得および詳細取得できること
- 無効化後の新しい対象年月では商品別月末評価額の登録対象外となること

### 25.9 トランザクション

- 無効化処理途中で例外が発生した場合にロールバックされること
- エラー発生時に`deleted_at`が設定されないこと
- バリデーションエラー時にデータが変更されないこと
- すでに無効化済みの場合にデータが再更新されないこと

### 25.10 同時実行

- 同一保有商品へ同時に無効化リクエストが送信された場合に、少なくとも1件だけが成功すること
- 後続のリクエストが無効化済みとして処理されること
- 同時実行によって他のカラムが変更されないこと

### 25.11 レスポンス契約

- JSONフィールド名がcamelCaseであること
- 保有商品IDが文字列で返却されること
- 所属資産口座IDが文字列で返却されること
- 所属資産口座名が返却されること
- `isEnabled`が`false`で返却されること
- `userId`がレスポンスへ含まれないこと
- `createdAt`がレスポンスへ含まれないこと
- `updatedAt`がレスポンスへ含まれないこと
- `deletedAt`がレスポンスへ含まれないこと
- データベースの内部情報がそのまま公開されないこと
- `data`がオブジェクトとして返却されること

### 25.12 異常系

- 想定外の例外発生時に`500 Internal Server Error`となること
- 共通エラーレスポンス形式で返却されること
- エラーレスポンスとログに同じリクエストIDが記録されること
- SQLやスタックトレースなどの内部情報がレスポンスへ含まれないこと

## 26. Laravel実装方針

### 26.1 Action

HTTPリクエストを受け付け、
保有商品ID、
無効化指示および
デモ利用者コンテキストを取得する。

Form Requestまたは入力用DTOを利用して
リクエスト内容を受け取り、
保有商品無効化UseCaseを呼び出す。

UseCaseから受け取った処理結果を、
Responderへ渡す。

利用者境界の判定、
利用状態の確認、
論理削除処理および
レスポンス生成処理は、
Actionへ直接記述しない。

---

### 26.2 UseCase

保有商品無効化の
ユースケース処理を担当する。

主な処理は、
以下とする。

- 操作対象利用者の受け取り
- 保有商品IDの受け取り
- 無効化指示の受け取り
- 無効化対象保有商品の取得
- 利用者境界の確認
- 現在の利用状態の確認
- 保有商品の論理削除
- 無効化後の保有商品の返却

無効化処理は、
データベーストランザクション内で実行する。

---

### 26.3 Form Request / DTO

入力値の形式および
単項目バリデーションを担当する。

主な検証対象は、
`isEnabled`とする。

以下を検証する。

- `isEnabled`が必須であること
- booleanであること
- `false`であること
- `isEnabled`以外の項目が含まれていないこと

保有商品が利用中かどうかなど、
データベースの状態に依存する業務ルールは、
Form Requestへ記述しない。

---

### 26.4 Query / Repository

無効化対象保有商品の取得および
論理削除を担当する。

すでに無効化済みかどうかを判定するため、
Laravel SoftDeletesを使用する場合は、
`withTrashed()`を利用する。

保有商品を取得する場合は、
必ず操作対象利用者IDを検索条件へ含める。

```php
HoldingAsset::query()
    ->withTrashed()
    ->where('id', $holdingAssetId)
    ->where('user_id', $demoUserId)
    ->first();
```

取得できない場合は、`HOLDING_ASSET_NOT_FOUND` として扱う。

`deleted_at` が設定済みの場合は、`HOLDING_ASSET_ALREADY_DISABLED` として扱う。

利用中の保有商品を無効化する場合は、LaravelのSoftDeletesを利用して論理削除する。

```php
$holdingAsset->delete();
```

物理削除を行う `forceDelete()` は使用しない。

### 26.5 Responder

UseCaseから受け取った無効化結果を、API共通方針に従ったHTTPレスポンスへ変換する。

正常終了時は、`200 OK` とともに無効化後の保有商品を返却する。

対象が存在しない場合、すでに無効化済みの場合またはバリデーションエラーの場合は、共通エラーレスポンス形式へ変換する。

### 26.6 API Resource

データベースカラムを直接返却せず、API Resourceを利用してレスポンス形式へ変換する。

論理削除後のモデルをレスポンスへ変換するため、所属資産口座を取得済みであることを保証する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'assetAccountId' => (string) $this->asset_account_id,
    'assetAccountName' => $this->assetAccount->name,
    'name' => $this->name,
    'productType' => $this->productType->value,
    'startYearMonth' => $this->start_year_month,
    'memo' => $this->memo,
    'isEnabled' => $this->deleted_at === null,
];
```

API Resourceは、Responderから利用する。

### 26.7 Middleware

以下の共通ミドルウェアを適用する。

- デモ利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

デモ利用者コンテキスト設定ミドルウェアでは、`X-Demo-User-Id` を検証し、操作対象利用者を特定する。

## 27. React・TypeScriptでの利用

無効化リクエスト型の例は、以下とする。

```typescript
export type DisableHoldingAssetRequest = {
  isEnabled: false;
};
```

`false` のリテラル型を使用することで、フロントエンドから `true` を誤送信できないようにする。

レスポンス型の例は、以下とする。

```typescript
export type ProductType =
  | 'INVESTMENT_TRUST'
  | 'DOMESTIC_STOCK'
  | 'FOREIGN_STOCK'
  | 'ETF'
  | 'DEPOSIT'
  | 'BOND'
  | 'OTHER';

export type DisabledHoldingAsset = {
  id: string;
  assetAccountId: string;
  assetAccountName: string;
  name: string;
  productType: ProductType;
  startYearMonth: string;
  memo: string | null;
  isEnabled: false;
};

export type DisableHoldingAssetResponse = {
  data: DisabledHoldingAsset;
};
```

無効化処理の実行前には、確認ダイアログを表示する。

確認内容には、少なくとも以下を含める。

- 無効化後は新しい商品別月末評価額を登録できないこと
- 過去の商品別月末評価額および判定履歴は保持されること
- Phase1では再有効化できないこと
- 同じ商品を再度管理する場合は新規登録が必要であること

リクエスト例：

```typescript
await apiClient.patch<DisableHoldingAssetResponse>(
  `/api/v1/holding-assets/${holdingAssetId}`,
  {
    isEnabled: false,
  },
);
```

無効化成功後は、以下のいずれかを行う。

- 一覧APIを再取得する
- フロントエンドの対象データの `isEnabled` を `false` へ更新する

無効化済み保有商品は、利用中の保有商品と区別して表示する。

無効化済み保有商品に対しては、編集および無効化操作を表示しない。

## 28. 設計上の補足

### 28.1 PATCHによる無効化を採用する理由

保有商品の無効化は、
リソースそのものを物理削除する処理ではなく、
利用状態を変更する業務操作である。

そのため、
`DELETE`ではなく、
`PATCH`による状態変更として表現する。

```http
PATCH /api/v1/holding-assets/{holdingAssetId}
```

```json
{
  "isEnabled": false
}
```

これにより、過去の商品別月末評価額や判定履歴を保持したまま、今後の利用対象から除外するという業務意図をAPI上でも明確に表現できる。

### 28.2 論理削除を採用する理由

保有商品は、過去の商品別月末評価額、月末資産状況および目的達成判定履歴から参照される。

物理削除すると、過去データとの関連を維持できなくなる可能性がある。

そのため、LaravelのSoftDeletesを利用し、`deleted_at` による論理削除で無効化を表現する。

無効化後も、保有商品IDおよび過去データとの関連は保持する。

### 28.3 再有効化を提供しない理由

Phase1では、無効化した保有商品の再有効化を提供しない。

同じ商品を再度保有した場合は、新しい保有商品として登録する。

これにより、以前の保有期間と新しい保有期間を別の保有商品IDで区別できる。

無効化済みの保有商品を再利用すると、過去の商品別月末評価額と新しい保有期間の評価額が同一の保有商品へ紐づき、保有期間の境界が不明確になる可能性がある。

### 28.4 無効化後の対象年月の扱い

無効化した保有商品は、無効化後の対象年月における商品別月末評価額の登録対象としない。

一方、無効化前の対象年月については、過去の商品別月末評価額および月末資産状況を引き続き参照できる。

保有商品の有効性は、現在の `deleted_at` だけでなく、利用開始年月および無効化時点を考慮して対象年月ごとに判定する。

### 28.5 過去履歴を変更しない理由

保有商品の無効化は、将来の利用対象から除外するための操作である。

無効化によって、以下の過去データは変更しない。

- 商品別月末評価額
- 月末資産状況
- 資産推移
- 保存済みの目的達成判定履歴

過去データは、記録時点の事実として保持する。

### 28.6 無効化済み保有商品を取得可能とする理由

無効化済みの保有商品も、一覧取得APIおよび詳細取得APIでは取得対象とする。

これは、過去の商品別月末評価額や判定履歴の内容を確認する際に、保有商品名や商品種別を参照できるようにするためである。

ただし、無効化済み保有商品に対しては、以下の操作を許可しない。

- 更新
- 再無効化
- 新しい商品別月末評価額の登録

### 28.7 すでに無効化済みの場合をエラーとする理由

本APIでは、すでに無効化済みの保有商品へ再度無効化リクエストが送信された場合、`HOLDING_ASSET_ALREADY_DISABLED` を返却する。

最終状態だけを見れば同じであるが、利用者に対して対象がすでに無効化済みであることを明示するためである。

これにより、画面状態の更新漏れや誤った再操作を検知しやすくする。

### 28.8 200 OKで無効化後のリソースを返す理由

無効化成功時は、`204 No Content` ではなく `200 OK` と無効化後の保有商品を返却する。

フロントエンドは、返却された `isEnabled: false` を利用して、一覧や詳細画面の状態を更新できる。

また、無効化後も保持される保有商品情報をレスポンスから確認できる。

Phase1では、フロントエンド実装の分かりやすさを優先し、無効化後のリソースを返却する方針とする。

### 28.9 所属資産口座を更新しない理由

保有商品の無効化は、保有商品の利用状態だけを変更する操作である。

所属資産口座の利用状態や資産口座そのものの情報は変更しない。

所属資産口座が利用中か無効化済みかにかかわらず、保有商品との過去の関連は保持する。

### 28.10 物理削除APIを提供しない理由

Phase1では、保有商品を物理削除するAPIを提供しない。

保有商品は、過去の資産情報と関連するため、物理削除による参照切れを防止する必要がある。

Laravel実装でも、`forceDelete()` は使用しない。

将来、運用上の理由から物理削除が必要になった場合は、既存履歴への影響を確認し、API共通方針および関連する設計書を見直す。

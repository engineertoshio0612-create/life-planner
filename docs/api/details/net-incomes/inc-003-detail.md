# INC-003 手取り収入詳細取得

## 1. 概要

操作対象となる利用者に登録された
指定の手取り収入を取得する。

手取り収入は、
対象年月単位で管理する。

詳細取得では、
対象年月、
手取り収入金額および
備考を取得できる。

本APIは、
手取り収入編集画面の初期表示および
登録内容の確認時に利用する。

---

## 2. ユースケース

利用者は、
登録済みの手取り収入の詳細を確認する。

例えば、
以下のような場合に使用する。

- 手取り収入編集画面を表示する
- 登録済み内容を確認する
- 手取り収入登録内容を参照する

対象データが存在しない場合は、
エラーを返却する。

---

## 3. エンドポイント

```http
GET /api/v1/net-incomes/{netIncomeId}
```

---

## 4. HTTPメソッド

```http
GET
```

本APIは、
指定した手取り収入を取得する。

データの登録、
更新および削除は行わない。

---

## 5. 認証・利用者の扱い

Phase1では、
認証機能を実装しない。

操作対象となる利用者は、
`X-User-Id`リクエストヘッダーで指定する。

```http
X-User-Id: 1
```

指定された利用者に登録された
手取り収入のみ取得できる。

他の利用者に登録された
手取り収入は取得できない。

利用者IDは、
リクエストボディまたは
パスパラメータでは受け付けない。

---

## 6. パスパラメータ

| パラメータ | 型 | 必須 | 説明 |
|---|---|:---:|---|
| `netIncomeId` | string | ○ | 取得対象となる手取り収入ID |

---

## 7. クエリパラメータ

なし。

---

## 8. リクエストヘッダー

### 8.1 必須ヘッダー

| ヘッダー名 | 必須 | 説明 |
|---|:---:|---|
| `X-User-Id` | ○ | 操作対象となる利用者ID |
| `Accept` | ○ | `application/json`を指定する |

リクエスト例：

```http
GET /api/v1/net-incomes/15
Accept: application/json
X-User-Id: 1
```

---

## 9. リクエストボディ

本APIはGETメソッドのため、リクエストボディを使用しない。

---

## 10. リクエスト項目

### 10.1 netIncomeId

取得対象となる手取り収入IDを指定する。

API共通方針に従い、IDは文字列として扱う。

```http
GET /api/v1/net-incomes/15
```

指定された手取り収入が操作対象利用者に帰属しない場合は、対象が存在しないものとして扱う。

---

## 11. バリデーション

### 11.1 X-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

### 11.2 netIncomeId

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された手取り収入が存在すること
- 指定された手取り収入が操作対象利用者に帰属すること

他の利用者に帰属する手取り収入を指定した場合は、存在しないものとして扱う。

### 11.3 データ取得条件

手取り収入を取得する際は、以下を検索条件に含める。

```text
id = netIncomeId
かつ
user_id = 操作対象利用者ID
```

手取り収入IDだけで取得してはならない。

例えば、以下のような取得は行わない。

```php
NetIncome::findOrFail($netIncomeId);
```

操作対象利用者IDを含めて取得する。

```php
NetIncome::query()
    ->where('id', $netIncomeId)
    ->where('user_id', $userId)
    ->first();
```

取得できない場合は、`NET_INCOME_NOT_FOUND` として扱う。

---

## 12. 業務ルール

- 操作対象利用者に帰属する手取り収入のみ取得する。
- 他の利用者の手取り収入は取得できない。
- 手取り収入は対象年月ごとに1件のみ存在する。
- 手取り収入は対象年月単位で管理する。
- 手取り収入が0円であっても有効なデータとして取得する。
- 手取り収入は論理削除を行わない。
- 手取り収入の詳細取得では、平均手取り収入の算出は行わない。

---

## 13. 処理フロー

```text
リクエスト受付
    ↓
リクエストID生成
    ↓
X-User-Id検証
    ↓
手取り収入ID検証
    ↓
操作対象利用者の手取り収入取得
    ↓
取得結果をAPIレスポンスへ変換
    ↓
200 OK返却
```

---

## 14. トランザクション境界

本APIは参照系APIであるため、
データベーストランザクションは開始しない。

取得処理のみ実行する。

---

## 15. 排他制御

本APIはデータを更新しないため、
排他制御は行わない。

取得中に別リクエストで
手取り収入が更新された場合は、
取得時点のデータを返却する。

## 18. エラーレスポンス

異常時は、
API共通方針で定めた
共通エラーレスポンス形式を使用する。

### 18.1 手取り収入が存在しない場合

指定された手取り収入が存在しない場合、
または他の利用者に帰属する手取り収入を指定した場合は、
`NET_INCOME_NOT_FOUND`を返却する。

```json
{
  "error": {
    "code": "NET_INCOME_NOT_FOUND",
    "message": "指定された手取り収入が見つかりません。",
    "details": [],
    "requestId": "01JABCDEFGHJKMNPQRSTVWXYZ"
  }
}

### 18.2 ID形式が不正な場合

手取り収入IDがAPI共通方針で定めた形式に一致しない場合は、`INVALID_NET_INCOME_ID` を返却する。

```json
{
  "error": {
    "code": "INVALID_NET_INCOME_ID",
    "message": "手取り収入IDの形式が不正です。",
    "details": [
      {
        "field": "netIncomeId",
        "reason": "invalidFormat",
        "message": "手取り収入IDの形式を確認してください。"
      }
    ],
    "requestId": "01JABCDEFGHJKMNPQRSTVWXYZ"
  }
}
```

## 19. HTTPステータス

| HTTPステータス | 条件 |
|---|---|
| `200 OK` | 手取り収入の取得に成功した |
| `400 Bad Request` | 利用者IDまたは手取り収入IDの形式が不正である |
| `404 Not Found` | 指定された利用者または手取り収入が存在しない |
| `500 Internal Server Error` | 想定外のサーバーエラーが発生した |

### 19.1 404の扱い

以下の場合は、`404 Not Found` を返却する。

- 指定された利用者が存在しない
- 指定された手取り収入が存在しない
- 指定された手取り収入が他の利用者に帰属する

他の利用者に帰属する手取り収入についても、対象の存在を推測できないようにするため、存在しないものとして扱う。

### 19.2 データなしとの違い

一覧取得APIでは、取得結果が0件の場合も `200 OK` と空配列を返却する。

本APIは、特定の手取り収入を指定して取得するため、対象が存在しない場合は `404 Not Found` を返却する。

---

## 20. エラーコード

| エラーコード | HTTPステータス | 条件 | 再試行 |
|---|---|---|:---:|
| `USER_CONTEXT_REQUIRED` | 400 | `X-User-Id` が指定されていない | × |
| `INVALID_USER_ID` | 400 | 利用者IDの形式が不正である | × |
| `USER_NOT_FOUND` | 404 | 指定された利用者が存在しない | × |
| `INVALID_NET_INCOME_ID` | 400 | 手取り収入IDの形式が不正である | × |
| `NET_INCOME_NOT_FOUND` | 404 | 指定された手取り収入が存在しない、または利用者境界外である | × |
| `INTERNAL_SERVER_ERROR` | 500 | 想定外のサーバーエラーが発生した | ○ |

エラーコードの正式な定義は、エラーコード一覧に従う。

---

## 21. 冪等性

本APIは参照系APIであるため、同一条件で複数回実行してもサーバー側の状態を変更しない。

手取り収入に変更がない限り、同一のレスポンスを返却する。

GETメソッドの性質に従い、本APIは冪等である。

## 24. テスト観点

### 24.1 正常系

- 指定した手取り収入を取得できること
- 金額が0円でも取得できること
- 備考が未設定でも取得できること
- 備考が設定されている場合も取得できること
- `200 OK`で返却されること

### 24.2 利用者境界

- 操作対象利用者の手取り収入のみ取得できること
- 他の利用者の手取り収入は取得できないこと
- 他利用者のデータがレスポンスへ含まれないこと

### 24.3 手取り収入ID

- 存在する手取り収入IDを指定すると取得できること
- 存在しない手取り収入IDを指定すると404となること
- 他利用者の手取り収入IDを指定すると404となること
- 手取り収入ID形式不正で400となること

### 24.4 ヘッダー

- `X-User-Id`未指定でエラーとなること
- 利用者ID形式不正でエラーとなること
- 存在しない利用者IDでエラーとなること
- 論理削除済み利用者でエラーとなること

### 24.5 レスポンス契約

- JSONフィールド名がcamelCaseであること
- 手取り収入IDが文字列で返却されること
- 対象年月が`YYYY-MM`形式で返却されること
- 金額が整数で返却されること
- `memo`がNULLを許容すること
- `userId`がレスポンスへ含まれないこと
- `createdAt`がレスポンスへ含まれないこと
- `updatedAt`がレスポンスへ含まれないこと
- `data`オブジェクトで返却されること

### 24.6 異常系

- 想定外の例外で`500 Internal Server Error`となること
- 共通エラーレスポンス形式で返却されること
- エラーレスポンスとログに同じリクエストIDが記録されること
- SQLやスタックトレースなどの内部情報がレスポンスへ含まれないこと

## 25. Laravel実装方針

### 25.1 Action

HTTPリクエストを受け付け、
パスパラメータおよび
利用者コンテキストを取得する。

手取り収入詳細取得UseCaseを呼び出し、
取得結果をResponderへ渡す。

以下の処理は、
Actionへ直接記述しない。

- 利用者境界の判定
- 手取り収入取得処理
- レスポンス生成処理

---

### 25.2 UseCase

手取り収入詳細取得の
ユースケース処理を担当する。

主な処理は、
以下とする。

- 操作対象利用者を受け取る
- 手取り収入IDを受け取る
- 手取り収入を取得する
- 取得結果を返却する

指定された手取り収入が存在しない場合、
または操作対象利用者に帰属しない場合は、
`NET_INCOME_NOT_FOUND`として扱う。

---

### 25.3 Query

操作対象利用者に帰属する
手取り収入を取得する。

取得条件には、
必ず操作対象利用者IDを含める。

取得例：

```php
$netIncome = NetIncome::query()
    ->where('id', $netIncomeId)
    ->where('user_id', $userId)
    ->first();
```

以下の取得は行わない。

```php
NetIncome::find($netIncomeId);
```

取得できなかった場合は、
`NET_INCOME_NOT_FOUND`として扱う。

論理削除を採用しないため、
SoftDeletesに関する検索条件は使用しない。

---

### 25.4 Responder

UseCaseから受け取った
手取り収入を、
API共通方針に従った
HTTPレスポンスへ変換する。

正常終了時は、
`200 OK`とともに
`data`オブジェクトで返却する。

対象が存在しない場合は、
共通エラーレスポンス形式へ変換する。

---

### 25.5 API Resource

データベースカラムを直接返却せず、
API Resourceを利用して
レスポンス形式へ変換する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'targetYearMonth' => $this->target_year_month,
    'amount' => $this->amount,
    'memo' => $this->memo,
];
```

以下の項目は、
レスポンスへ含めない。

- `userId`
- `createdAt`
- `updatedAt`

API Resourceは、
Responderから利用する。

---

### 25.6 Middleware

以下の共通ミドルウェアを適用する。

- 利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

利用者コンテキスト設定ミドルウェアでは、
`X-User-Id`を検証し、
操作対象利用者を特定する。

Action以降の処理では、
検証済みの利用者コンテキストを使用する。

---

### 25.7 例外変換

LaravelおよびPostgreSQLの内部例外は、
そのままAPIレスポンスへ公開しない。

主な例外変換は、
以下とする。

| 内部状態 | 独自エラーコード |
|---|---|
| 利用者未指定 | `USER_CONTEXT_REQUIRED` |
| 利用者ID形式不正 | `INVALID_USER_ID` |
| 利用者不存在 | `USER_NOT_FOUND` |
| 手取り収入ID形式不正 | `INVALID_NET_INCOME_ID` |
| 手取り収入不存在 | `NET_INCOME_NOT_FOUND` |
| 想定外例外 | `INTERNAL_SERVER_ERROR` |

SQL、
スタックトレースおよび
内部例外メッセージは、
APIレスポンスへ含めない。

---

## 26. React・TypeScriptでの利用

パスパラメータの型は、
以下とする。

```ts
export type GetNetIncomeDetailParams = {
  netIncomeId: string;

```

レスポンス型は、
以下とする。

```ts
export type NetIncomeDetailResponse = {

API呼び出し例は、
以下とする。

const response =
  await apiClient.get<NetIncomeDetailResponse>(

取得したデータは、
手取り収入編集画面の初期表示へ利用する。

取得できなかった場合は、
共通エラー画面または
エラーメッセージを表示する。

`amount`が`0`の場合も、
正常な業務データとして表示する。

`memo`が`null`の場合は、
空欄として表示する。

## 27. 設計上の補足

### 27.1 詳細取得APIを分離した理由

一覧取得APIでは、
画面表示に必要な最小限の情報のみ返却する。

編集画面では、
対象となる1件の手取り収入のみ取得できれば十分であるため、
詳細取得APIを分離した。

---

### 27.2 利用者境界を検索条件へ含める理由

手取り収入IDのみで取得すると、
他の利用者のデータへアクセスできる可能性がある。

そのため、
以下を検索条件とする。

```text
id
+
user_id
```

これにより、
利用者境界を保証する。

---

### 27.3 404 Not Foundを返却する理由

以下の場合は、
いずれも対象が存在しないものとして扱う。

- 指定した手取り収入が存在しない
- 他の利用者に帰属する手取り収入を指定した

これにより、
他利用者のデータの存在有無を推測できないようにする。

---

### 27.4 平均手取り収入を返却しない理由

平均手取り収入は、
業務上の計算結果であり、
手取り収入詳細そのものではない。

そのため、
本APIでは返却しない。

平均手取り収入が必要な場合は、
INC-005 平均手取り収入取得APIを利用する。

---

### 27.5 更新可否を返却しない理由

Phase1では、
取得した手取り収入は
すべて更新可能である。

更新可否を示す
`editable`などのフラグは返却しない。

将来、
更新不可となる業務ルールが追加された場合に、
レスポンス項目の追加を検討する。

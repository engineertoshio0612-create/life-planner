# INC-004 手取り収入更新

## 1. 概要

操作対象となる利用者に登録された
手取り収入を更新する。

更新できる項目は、
対象年月、
手取り収入金額および
備考とする。

更新後の手取り収入は、
平均手取り収入の算出および
目的達成判定に利用する。

---

## 2. ユースケース

利用者は、
登録済みの手取り収入を修正する。

例えば、
以下のような場合に使用する。

- 手取り収入金額を修正する
- 対象年月を修正する
- 備考を追加・変更する
- 手取り収入がなかった対象年月を0円へ修正する

更新対象が存在しない場合は、
エラーを返却する。

---

## 3. エンドポイント

```http
PATCH /api/v1/net-incomes/{netIncomeId}
```

---

## 4. HTTPメソッド

```http
PATCH
```

本APIは、
指定した手取り収入の一部項目を更新する。

更新対象は、
業務上変更可能な項目のみとする。

---

## 5. 認証・利用者の扱い

Phase1では、
認証機能を実装しない。

操作対象となる利用者は、
`X-User-Id`リクエストヘッダーで指定する。

```http
X-User-Id: 1
```

指定された利用者に登録された
手取り収入のみ更新できる。

他の利用者に登録された
手取り収入は更新できない。

利用者IDは、
リクエストボディまたは
パスパラメータでは受け付けない。

---

| パラメータ | 型 | 必須 | 説明 |
|---|---|:---:|---|
| `netIncomeId` | string | ○ | 更新対象となる手取り収入ID |

## 9. リクエストボディ

```json
{
  "targetYearMonth": "2026-08",
  "amount": 330000,
  "memo": "残業代を修正"
}
```

手取り収入が発生しなかった場合は、
`amount`へ`0`を指定する。

```json
{
  "targetYearMonth": "2026-08",
  "amount": 0,
  "memo": "休職により収入なし"
}
```

---

## 10. リクエスト項目

| 項目 | 型 | 必須 | NULL | 説明 |
|---|---|:---:|:---:|---|
| `targetYearMonth` | string | ○ | × | 対象年月（YYYY-MM） |
| `amount` | integer | ○ | × | 手取り収入金額（円） |
| `memo` | string | × | ○ | 備考 |

---

### 10.1 targetYearMonth

更新後の対象年月を指定する。

形式は、
`YYYY-MM`とする。

```json
{
  "targetYearMonth": "2026-08"
}
```

更新後の対象年月について、
同一利用者に同じ対象年月の
手取り収入が存在する場合は更新できない。

---

### 10.2 amount

更新後の手取り収入金額を指定する。

日本円の整数値とする。

手取り収入がない場合は、
`0`を指定する。

```json
{
  "amount": 0
}
```

負の値および小数は指定できない。

---

### 10.3 memo

更新後の備考を指定する。

未入力の場合は、
`null`として扱う。

```json
{
  "memo": null
}
```

空文字または空白文字のみの場合は、
`null`へ正規化する。

---

## 11. 更新対象外項目

以下の項目は、
本APIでは更新できない。

- `id`
- `userId`
- `createdAt`
- `updatedAt`

これらの項目がリクエストへ含まれる場合は、
バリデーションエラーとする。

---

## 12. バリデーション

### 12.1 X-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

---

### 12.2 netIncomeId

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された手取り収入が存在すること
- 指定された手取り収入が操作対象利用者に帰属すること

他の利用者に帰属する手取り収入を指定した場合は、
存在しないものとして扱う。

---

### 12.3 リクエストボディ

以下を検証する。

- JSONオブジェクトであること
- 必須項目が指定されていること
- 定義されていない項目が含まれていないこと
- 更新対象外項目が含まれていないこと

空のJSONオブジェクトは、
バリデーションエラーとする。

```json
{}
```

---

### 12.4 targetYearMonth

以下を検証する。

- 必須であること
- 文字列であること
- `null`でないこと
- `YYYY-MM`形式であること
- 実在する年月であること

以下は、
不正な値として扱う。

```text
2026-8
2026/08
2026-13
202608
```

---

### 12.5 amount

以下を検証する。

- 必須であること
- 整数であること
- `null`でないこと
- 0以上であること
- テーブル定義で許容する金額範囲内であること

以下は、
不正な値として扱う。

```text
-1
325000.5
"325000"
```

`0`は、
有効な手取り収入金額として受け付ける。

---

### 12.6 memo

`memo`が指定された場合は、
以下を検証する。

- 文字列または`null`であること
- テーブル定義で定めた最大文字数以内であること

空文字または空白文字のみの場合は、
`null`へ正規化する。

---

### 12.7 対象年月の重複

更新後の対象年月について、
同一利用者にすでに登録済みの
手取り収入が存在しないことを検証する。

重複判定は、
更新対象レコード自身を除外して行う。

以下の組み合わせで判定する。

```text
user_id
target_year_month
```

重複が存在する場合は、
`NET_INCOME_ALREADY_EXISTS`を返却する。

---

## 13. 業務ルール

- 操作対象利用者に帰属する手取り収入のみ更新できる。
- 他の利用者に帰属する手取り収入は更新できない。
- 手取り収入は対象年月ごとに1件のみ管理する。
- 更新後の対象年月について、同一利用者に同じ対象年月の手取り収入が存在する場合は更新できない。
- 手取り収入が発生しなかった対象年月は、金額を`0円`として更新する。
- 手取り収入は対象年月単位で管理する。
- 更新後の手取り収入は、平均手取り収入の算出および目的達成判定で利用する。
- 手取り収入は論理削除を行わない。

---

## 14. 処理フロー

```text
リクエスト受付
    ↓
リクエストID生成
    ↓
X-User-Id検証
    ↓
手取り収入ID検証
    ↓
入力値検証
    ↓
対象年月重複確認
    ↓
手取り収入更新
    ↓
更新結果取得
    ↓
APIレスポンス形式へ変換
    ↓
200 OK返却
```

---

## 15. トランザクション境界

以下を、
1つのデータベーストランザクション内で実行する。

- 更新対象の存在確認
- 更新後対象年月の重複確認
- 手取り収入更新

途中で例外が発生した場合は、
ロールバックする。

---

## 16. 排他制御

同一手取り収入へ同時更新が行われた場合は、
最後にコミットされた更新内容を採用する。

更新後対象年月について、
同一利用者に重複が発生する場合は、
データベースのUNIQUE制約により更新を防止する。

対象制約は、
以下とする。

```text
user_id
target_year_month
```

UNIQUE制約違反となった場合は、
業務エラーへ変換し、
`NET_INCOME_ALREADY_EXISTS`を返却する。

## 20. HTTPステータス

| HTTPステータス | 条件 |
|---:|---|
| `200 OK` | 手取り収入の更新に成功した |
| `400 Bad Request` | 利用者IDまたは手取り収入IDの形式が不正である |
| `404 Not Found` | 指定された利用者または手取り収入が存在しない |
| `409 Conflict` | 更新後の対象年月が重複している |
| `422 Unprocessable Entity` | 入力値が不正である |
| `500 Internal Server Error` | 想定外のサーバーエラーが発生した |

---

### 20.1 404の扱い

以下の場合は、
`404 Not Found`を返却する。

- 指定された利用者が存在しない
- 指定された手取り収入が存在しない
- 指定された手取り収入が他の利用者に帰属する

他の利用者に帰属する手取り収入についても、
対象の存在を推測できないようにするため、
存在しないものとして扱う。

---

### 20.2 409の扱い

以下の場合は、
`409 Conflict`を返却する。

- 更新後の対象年月が、
  同一利用者の既存データと重複する

入力値自体は正しいが、
現在のリソース状態と競合して更新できないため、
`409 Conflict`を返却する。

## 22. 冪等性

本APIは
HTTP PATCHを使用する。

同一リクエストを複数回実行した場合、
更新後の状態が変わらなければ、
結果は同一となる。

そのため、
本APIは実質的に冪等として扱う。

ただし、
更新後の対象年月が
他のデータと重複する場合は、
`409 Conflict`を返却する。

Phase1では、
ETagやIf-Matchによる
楽観ロックは採用しない。

## 25. 設計上の補足

### 25.1 PATCHを採用する理由

本APIは、既存の手取り収入リソースを更新するため、`PATCH` を採用する。

```http
PATCH /api/v1/net-incomes/{netIncomeId}
```

現時点では、`targetYearMonth` および `amount` を必須としているが、リソース全体を置き換える操作ではない。

利用者ID、手取り収入ID、登録日時などは変更せず、業務上更新可能な項目のみ変更する。

### 25.2 対象年月を更新可能とする理由

手取り収入を誤った対象年月へ登録した場合に、新しいレコードを作り直さず、既存レコードの対象年月を修正できるようにする。

更新後の対象年月についても、同一利用者内で1件のみというルールを維持する。

対象年月を変更しても、手取り収入IDは変更しない。

### 25.3 手取り収入IDを維持する理由

本APIは、既存の手取り収入を修正する操作である。

対象年月や金額を変更しても、同じ業務データの訂正として扱うため、手取り収入IDは変更しない。

これにより、更新前後で同一レコードとして追跡できる。

### 25.4 論理削除を採用しない理由

手取り収入は、対象年月ごとの実績値を管理する。

誤登録は更新によって修正し、手取り収入がなかった場合は金額を0円として管理する。

そのため、取消状態または無効化状態を設けず、論理削除も採用しない。

### 25.5 更新後の平均手取り収入を保存しない理由

手取り収入を更新しても、平均手取り収入を別途保存または更新しない。

平均手取り収入は、INC-005 平均手取り収入取得APIまたは目的達成判定時に、最新の手取り収入から都度算出する。

これにより、手取り収入と保存済み平均値の不整合を防止する。

### 25.6 保存済み判定履歴を変更しない理由

手取り収入を更新しても、過去に保存された目的達成判定履歴は変更しない。

判定履歴は、判定実行時点の入力値および計算結果を保持するスナップショットとして扱う。

更新後の手取り収入を反映した結果が必要な場合は、目的達成判定を再実行し、新しい判定履歴を作成する。

### 25.7 Last Write Winsを採用する理由

Phase1では、同一手取り収入を複数人が同時編集する可能性が低い。

楽観ロックやETagを導入すると、実装およびフロントエンドの制御が複雑になる。

そのため、同時更新時は最後に完了した更新を採用するLast Write Wins方式とする。

将来、複数利用者による同時編集が増えた場合は、`updated_at` またはバージョン番号を使用した楽観ロックを再検討する。

### 25.8 同一内容の更新を正常終了とする理由

更新内容が現在値と同じ場合も、エラーとはせず、`200 OK` を返却する。

同一内容であることを理由に特別な業務エラーを設ける必要がなく、クライアント側の処理を単純にできるためである。

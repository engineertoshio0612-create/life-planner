# INC-002 手取り収入登録

## 1. 概要

操作対象となる利用者に対して、
対象年月の手取り収入を新規登録する。

手取り収入は、
対象年月ごとに1件のみ登録できる。

対象年月に手取り収入が発生しなかった場合は、
未登録のままにせず、
金額を`0円`として登録する。

登録した手取り収入は、
平均手取り収入の算出および
目的達成判定に利用する。

---

## 2. ユースケース

利用者は、
対象年月の手取り収入実績を登録する。

例えば、
以下のような場合に使用する。

- 当月の手取り収入を登録する
- 過去の対象年月の手取り収入を登録する
- 手取り収入がなかった対象年月を0円として登録する
- 平均手取り収入の算出に必要な実績値を登録する

登録内容に誤りがある場合は、
新しいレコードを登録せず、
INC-004 手取り収入更新APIで修正する。

---

## 3. エンドポイント

```http
POST /api/v1/net-incomes
```

---

## 4. HTTPメソッド

`POST`

本APIは、新しい手取り収入リソースを作成する。

---

## 5. 認証・利用者の扱い

Phase1では、認証機能を実装しない。

操作対象となる利用者は、`X-User-Id` リクエストヘッダーで指定する。

```http
X-User-Id: 1
```

指定された利用者の手取り収入として登録する。

リクエストボディでは、利用者IDを受け付けない。

---

なし。

---

## 7. クエリパラメータ

なし。

## 8. リクエストヘッダー

### 8.1 必須ヘッダー

| ヘッダー名 | 必須 | 説明 |
|---|:---:|---|
| `X-User-Id` | ○ | 操作対象となる利用者ID |
| `Content-Type` | ○ | `application/json` を指定する |
| `Accept` | ○ | `application/json` を指定する |

リクエスト例：

```http
POST /api/v1/net-incomes
Content-Type: application/json
Accept: application/json
X-User-Id: 1
```

---

## 9. リクエストボディ

```json
{
  "targetYearMonth": "2026-08",
  "amount": 325000,
  "memo": "残業代を含む"
}
```

手取り収入が発生しなかった場合は、`amount` に `0` を指定する。

```json
{
  "targetYearMonth": "2026-08",
  "amount": 0,
  "memo": "休職により収入なし"
}
```

---

## 10. リクエスト項目

| 項目 | 型 | 必須 | NULL | 説明 |
|---|---|:---:|:---:|---|
| `targetYearMonth` | string | ○ | × | 対象年月（YYYY-MM形式） |
| `amount` | integer | ○ | × | 手取り収入金額（日本円の整数値） |
| `memo` | string | × | ○ | 備考 |

### 10.1 targetYearMonth

手取り収入を記録する対象年月を指定する。

形式は、`YYYY-MM` とする。

```json
{
  "targetYearMonth": "2026-08"
}
```

同一利用者について、同じ対象年月の手取り収入を複数登録することはできない。

### 10.2 amount

対象年月の手取り収入金額を、日本円の整数値で指定する。

小数は受け付けない。

手取り収入が発生しなかった場合は、`0` を指定する。

```json
{
  "amount": 0
}
```

負の金額は指定できない。

### 10.3 memo

手取り収入に関する任意の備考を指定する。

未入力の場合は、`null` として扱う。

```json
{
  "memo": null
}
```

空文字または空白文字のみが指定された場合は、`null` へ正規化する。

---

## 11. 更新対象外項目

以下の項目は、本APIのリクエストでは受け付けない。

- `id`
- `userId`
- `createdAt`
- `updatedAt`
- `deletedAt`

利用者IDは、`X-User-Id` から取得する。

更新対象外項目が含まれている場合は、バリデーションエラーとする。

---

## 12. バリデーション

### 12.1 X-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

### 12.2 リクエストボディ

以下を検証する。

- JSONオブジェクトであること
- 必須項目が指定されていること
- 定義されていない項目が含まれていないこと
- 更新対象外項目が含まれていないこと

空のJSONオブジェクトは、バリデーションエラーとする。

```json
{}
```

### 12.3 targetYearMonth

以下を検証する。

- 必須であること
- 文字列であること
- `null` でないこと
- `YYYY-MM` 形式であること
- 実在する年月であること

以下は、不正な値として扱う。

- `2026-8`
- `2026/08`
- `2026-13`
- `202608`

### 12.4 amount

以下を検証する。

- 必須であること
- 整数であること
- `null` でないこと
- `0` 以上であること
- テーブル定義で許容する金額範囲内であること

以下は、不正な値として扱う。

- `-1`
- `325000.5`
- `"325000"`

`0` は、有効な手取り収入金額として受け付ける。

### 12.5 memo

`memo` が指定された場合は、以下を検証する。

- 文字列または `null` であること
- テーブル定義で定めた最大文字数以内であること

空文字または空白文字のみの場合は、`null` へ正規化する。

### 12.6 対象年月の重複

同一利用者について、指定された対象年月の手取り収入がすでに登録されていないことを検証する。

以下の組み合わせで、重複を判定する。

- `user_id`
- `target_year_month`

同じ対象年月の手取り収入が存在する場合は、重複エラーとする。

登録済みデータを修正する場合は、INC-004 手取り収入更新APIを使用する。

## 13. 業務ルール

- 操作対象利用者の手取り収入として登録する。
- 手取り収入は対象年月ごとに1件のみ登録できる。
- 同一利用者について、同一対象年月の手取り収入を重複登録できない。
- 手取り収入が発生しなかった対象年月は、金額を`0円`として登録する。
- 手取り収入は対象年月単位で管理する。
- 手取り収入は平均手取り収入の算出に利用する。
- 登録後に内容を変更する場合は、INC-004 手取り収入更新APIを使用する。
- 手取り収入は論理削除を行わない。

---

## 14. 処理フロー

```text
リクエスト受付
    ↓
リクエストID生成
    ↓
X-User-Id検証
    ↓
入力値検証
    ↓
対象年月重複確認
    ↓
手取り収入登録
    ↓
登録結果取得
    ↓
APIレスポンス用形式へ変換
    ↓
201 Created返却
```

---

## 15. トランザクション境界

以下を1トランザクションで実行する。

- 対象年月重複確認
- 手取り収入登録

途中で例外が発生した場合は、
ロールバックする。

---

## 16. 排他制御

同一利用者について、
同一対象年月へ同時登録された場合は、
データベースのUNIQUE制約により
重複登録を防止する。

対象制約は、
以下とする。

```text
user_id
target_year_month
```

UNIQUE制約違反となった場合は、
業務エラーへ変換し、
重複登録エラーを返却する。

## 22. 冪等性

本APIはPOSTによる新規登録APIであるため、
冪等ではない。

同一リクエストを複数回送信した場合は、
2回目以降は同一対象年月の重複登録となり、
`409 Conflict`を返却する。

Phase1では、
冪等性キー（Idempotency-Key）は採用しない。

同一対象年月への二重登録は、
業務ルールおよびデータベースのUNIQUE制約によって防止する。

## 25. 設計上の補足

### 25.1 POSTを採用する理由

手取り収入登録は、
新しい手取り収入リソースを作成する操作である。

そのため、
HTTPメソッドには
`POST`を採用する。

```http
POST /api/v1/net-incomes
```

---

### 25.2 対象年月単位で管理する理由

手取り収入は、
現在の収入ではなく、
対象年月時点の実績値を記録する。

対象年月ごとに管理することで、
将来の平均手取り収入算出、
目的達成判定および
過去データの再現性を維持できる。

---

### 25.3 同一対象年月を重複登録できない理由

同一利用者について、
同一対象年月の手取り収入は
1件のみ管理する。

複数件登録できるようにすると、
平均手取り収入の算出基準が曖昧になり、
業務ルールが複雑になる。

そのため、
以下の組み合わせで
UNIQUE制約を設ける。

```text
user_id
target_year_month
```

---

### 25.4 手取り収入がない場合は0円で登録する理由

対象年月に手取り収入が発生しなかった場合も、
対象年月の実績として管理する。

レコードを登録しない場合と
区別できるようにするため、
金額を`0円`として登録する。

これにより、
以下を明確に区別できる。

```text
レコードなし
    → 未入力

amount = 0
    → 手取り収入なし
```

---

### 25.5 論理削除を採用しない理由

手取り収入は、
履歴管理ではなく、
対象年月ごとの確定した実績値を管理する。

登録内容に誤りがある場合は、
同一レコードを更新して修正する。

そのため、
論理削除および取消状態は採用しない。

---

### 25.6 平均手取り収入を登録時に更新しない理由

本APIでは、
平均手取り収入を保存しない。

平均手取り収入は、
判定対象年月以前の連続する3か月の手取り収入から
都度算出する。

そのため、
登録APIでは
平均値の更新処理を行わない。

---

### 25.7 判定履歴を登録しない理由

手取り収入登録は、
目的達成判定とは独立した業務である。

本APIでは、
判定履歴を作成しない。

判定履歴は、
目的達成判定API実行時のみ登録する。

---

### 25.8 201 Createdを返却する理由

登録成功時は、
新しいリソースが作成されたことを示すため、
`201 Created`を返却する。

登録後のリソースも返却することで、
フロントエンドは
再取得せずに一覧や詳細画面を更新できる。

---

### 25.9 冪等性キーを採用しない理由

Phase1では、
Idempotency-Keyを採用しない。

同一対象年月への重複登録は、
業務ルールおよび
データベースのUNIQUE制約で防止する。

決済APIのような
通信再送対策は
Phase1では不要と判断した。

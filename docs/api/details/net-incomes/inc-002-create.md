# INC-002 手取り収入登録

## 1. 概要

操作対象となる利用者に対して、
対象年月の手取り収入を新規登録する。

手取り収入は、
対象年月ごとに1件のみ登録できる。

対象年月に手取り収入が発生しなかった場合は、
未登録のままにせず、
金額を`0円`として登録する。

登録した手取り収入は、
平均手取り収入の算出および
目的達成判定に利用する。

---

## 2. ユースケース

利用者は、
対象年月の手取り収入実績を登録する。

例えば、
以下のような場合に使用する。

- 当月の手取り収入を登録する
- 過去の対象年月の手取り収入を登録する
- 手取り収入がなかった対象年月を0円として登録する
- 平均手取り収入の算出に必要な実績値を登録する

登録内容に誤りがある場合は、
新しいレコードを登録せず、
INC-004 手取り収入更新APIで修正する。

---

## 3. エンドポイント

```http
POST /api/v1/net-incomes
```

---

## 4. HTTPメソッド

`POST`

本APIは、新しい手取り収入リソースを作成する。

---

## 5. 認証・利用者の扱い

Phase1では、認証機能を実装しない。

操作対象となる利用者は、`X-User-Id` リクエストヘッダーで指定する。

```http
X-User-Id: 1
```

指定された利用者の手取り収入として登録する。

リクエストボディでは、利用者IDを受け付けない。

## 9. リクエストボディ

```json
{
  "targetYearMonth": "2026-08",
  "amount": 325000,
  "memo": "残業代を含む"
}
```

手取り収入が発生しなかった場合は、`amount` に `0` を指定する。

```json
{
  "targetYearMonth": "2026-08",
  "amount": 0,
  "memo": "休職により収入なし"
}
```

---

## 10. リクエスト項目

| 項目 | 型 | 必須 | NULL | 説明 |
|---|---|:---:|:---:|---|
| `targetYearMonth` | string | ○ | × | 対象年月（YYYY-MM形式） |
| `amount` | integer | ○ | × | 手取り収入金額（日本円の整数値） |
| `memo` | string | × | ○ | 備考 |

### 10.1 targetYearMonth

手取り収入を記録する対象年月を指定する。

形式は、`YYYY-MM` とする。

```json
{
  "targetYearMonth": "2026-08"
}
```

同一利用者について、同じ対象年月の手取り収入を複数登録することはできない。

### 10.2 amount

対象年月の手取り収入金額を、日本円の整数値で指定する。

小数は受け付けない。

手取り収入が発生しなかった場合は、`0` を指定する。

```json
{
  "amount": 0
}
```

負の金額は指定できない。

### 10.3 memo

手取り収入に関する任意の備考を指定する。

未入力の場合は、`null` として扱う。

```json
{
  "memo": null
}
```

空文字または空白文字のみが指定された場合は、`null` へ正規化する。

## 11. 更新対象外項目

以下の項目は、本APIのリクエストでは受け付けない。

- `id`
- `userId`
- `createdAt`
- `updatedAt`
- `deletedAt`

利用者IDは、`X-User-Id` から取得する。

更新対象外項目が含まれている場合は、バリデーションエラーとする。

---

## 12. バリデーション

### 12.1 X-User-Id

以下を検証する。

- 指定されていること
- API共通方針で定めたID形式であること
- 指定された利用者が存在すること
- 指定された利用者が論理削除されていないこと

### 12.2 リクエストボディ

以下を検証する。

- JSONオブジェクトであること
- 必須項目が指定されていること
- 定義されていない項目が含まれていないこと
- 更新対象外項目が含まれていないこと

空のJSONオブジェクトは、バリデーションエラーとする。

```json
{}
```

### 12.3 targetYearMonth

以下を検証する。

- 必須であること
- 文字列であること
- `null` でないこと
- `YYYY-MM` 形式であること
- 実在する年月であること

以下は、不正な値として扱う。

- `2026-8`
- `2026/08`
- `2026-13`
- `202608`

### 12.4 amount

以下を検証する。

- 必須であること
- 整数であること
- `null` でないこと
- `0` 以上であること
- テーブル定義で許容する金額範囲内であること

以下は、不正な値として扱う。

- `-1`
- `325000.5`
- `"325000"`

`0` は、有効な手取り収入金額として受け付ける。

### 12.5 memo

`memo` が指定された場合は、以下を検証する。

- 文字列または `null` であること
- テーブル定義で定めた最大文字数以内であること

空文字または空白文字のみの場合は、`null` へ正規化する。

### 12.6 対象年月の重複

同一利用者について、指定された対象年月の手取り収入がすでに登録されていないことを検証する。

以下の組み合わせで、重複を判定する。

- `user_id`
- `target_year_month`

同じ対象年月の手取り収入が存在する場合は、重複エラーとする。

登録済みデータを修正する場合は、INC-004 手取り収入更新APIを使用する。

## 13. 業務ルール

- 操作対象利用者の手取り収入として登録する。
- 手取り収入は対象年月ごとに1件のみ登録できる。
- 同一利用者について、同一対象年月の手取り収入を重複登録できない。
- 手取り収入が発生しなかった対象年月は、金額を`0円`として登録する。
- 手取り収入は対象年月単位で管理する。
- 手取り収入は平均手取り収入の算出に利用する。
- 登録後に内容を変更する場合は、INC-004 手取り収入更新APIを使用する。
- 手取り収入は論理削除を行わない。

以下を1トランザクションで実行する。

- 対象年月重複確認

途中で例外が発生した場合は、
ロールバックする。

---

## 16. 排他制御

同一利用者について、
同一対象年月へ同時登録された場合は、
データベースのUNIQUE制約により
重複登録を防止する。

対象制約は、
以下とする。

```text
user_id
target_year_month
```

UNIQUE制約違反となった場合は、
業務エラーへ変換し、
重複登録エラーを返却する。

## 22. 冪等性

本APIはPOSTによる新規登録APIであるため、
冪等ではない。

同一リクエストを複数回送信した場合は、
2回目以降は同一対象年月の重複登録となり、
`409 Conflict`を返却する。

Phase1では、
冪等性キー（Idempotency-Key）は採用しない。

同一対象年月への二重登録は、
業務ルールおよびデータベースのUNIQUE制約によって防止する。

## 25. テスト観点

### 25.1 正常系

- 手取り収入を登録できること
- 金額が0円でも登録できること
- 備考なしで登録できること
- 備考ありで登録できること
- `201 Created`で返却されること
- 登録後の内容がレスポンスへ返却されること

### 25.2 利用者境界

- 操作対象利用者の手取り収入として登録されること
- 他利用者の手取り収入として登録されないこと
- userIdをリクエストから指定できないこと

### 25.3 対象年月

- 新しい対象年月を登録できること
- 同一対象年月は登録できないこと
- 同一利用者で対象年月重複時は409となること

### 25.4 金額

- 正常な整数値を登録できること
- 0円を登録できること
- 負数でエラーとなること
- 小数でエラーとなること
- 最大値を超える場合にエラーとなること

### 25.5 備考

- 最大文字数以内なら登録できること
- 最大文字数超過でエラーとなること
- 空文字がNULLへ正規化されること

### 25.6 リクエストボディ

- 必須項目不足でエラーとなること
- 未定義項目を指定するとエラーとなること
- idを指定するとエラーとなること
- userIdを指定するとエラーとなること
- createdAtを指定するとエラーとなること
- updatedAtを指定するとエラーとなること

### 25.7 ヘッダー

- X-User-Id未指定でエラーとなること
- 利用者ID形式不正でエラーとなること
- 存在しない利用者IDでエラーとなること
- 論理削除済み利用者でエラーとなること

### 25.8 トランザクション

- 登録途中で例外が発生した場合にロールバックされること
- 重複登録時に登録されないこと

### 25.9 同時実行

- 同一対象年月へ同時登録した場合に1件のみ成功すること
- 後続リクエストが409となること

### 25.10 レスポンス契約

- JSONフィールド名がcamelCaseであること
- 手取り収入IDが文字列で返却されること
- 対象年月がYYYY-MM形式で返却されること
- 金額が整数で返却されること
- memoがNULLを許容すること
- userIdがレスポンスへ含まれないこと
- createdAtがレスポンスへ含まれないこと
- updatedAtがレスポンスへ含まれないこと

### 25.11 異常系

- 想定外の例外で500となること
- 共通エラーレスポンス形式で返却されること
- リクエストIDがレスポンスとログで一致すること
- SQLやスタックトレースがレスポンスへ含まれないこと

## 26. Laravel実装方針

### 26.1 Action

HTTPリクエストを受け付け、
入力値および利用者コンテキストを取得する。

Form Requestまたは入力用DTOから
登録内容を受け取り、
手取り収入登録UseCaseを呼び出す。

UseCaseから受け取った処理結果を、
Responderへ渡す。

以下の処理は、
Actionへ直接記述しない。

- 入力値の単項目バリデーション
- 対象年月の重複確認
- 手取り収入の登録処理
- トランザクション制御
- レスポンス生成処理

---

### 26.2 UseCase

手取り収入登録の
ユースケース処理を担当する。

主な処理は、
以下とする。

- 操作対象利用者を受け取る
- 登録内容を受け取る
- 同一対象年月の登録有無を確認する
- 手取り収入を登録する
- 登録結果を返却する

登録処理は、
データベーストランザクション内で実行する。

同一利用者について、
同一対象年月の手取り収入がすでに存在する場合は、
`NET_INCOME_ALREADY_EXISTS`として扱う。

---

### 26.3 Form Request / DTO

入力値の形式および
単項目バリデーションを担当する。

主な検証対象は、
以下とする。

- `targetYearMonth`
- `amount`
- `memo`

Form Requestでは、
以下を検証する。

- 必須項目
- データ型
- NULL可否
- 文字数
- 数値範囲
- 対象年月の形式
- 未定義項目の有無

同一対象年月の登録有無など、
データベースの状態に依存する業務ルールは、
Form Requestへ記述しない。

検証済みの入力値は、
登録用DTOへ変換してUseCaseへ渡す。

DTOの例：

```php
final readonly class CreateNetIncomeInput
{
    public function __construct(
        public string $targetYearMonth,
        public int $amount,
        public ?string $memo,
    ) {
    }
}
```

## 26.4 Query

同一利用者について、指定された対象年月の手取り収入がすでに存在するかを確認する。

検索条件には、必ず操作対象利用者IDを含める。

確認例：

```php
$exists = NetIncome::query()
    ->where('user_id', $userId)
    ->where('target_year_month', $targetYearMonth)
    ->exists();
```

Queryによる事前確認だけでなく、データベースのUNIQUE制約を最終的な重複防止手段として使用する。

---

## 26.5 Repository

手取り収入の永続化を担当する。

Repositoryは、UseCaseから受け取った利用者IDおよび登録内容を使用して、`net_incomes` へ新しいレコードを登録する。

登録例：

```php
$netIncome = NetIncome::query()->create([
    'user_id' => $userId,
    'target_year_month' => $input->targetYearMonth,
    'amount' => $input->amount,
    'memo' => $input->memo,
]);
```

以下の項目は、クライアントから受け取らない。

- `id`
- `user_id`
- `created_at`
- `updated_at`

`user_id` は、利用者コンテキストから設定する。

`id`、`created_at` および `updated_at` は、データベースまたはLaravelによって自動設定する。

---

## 26.6 トランザクション

以下の処理を、1つのデータベーストランザクション内で実行する。

- 対象年月の重複確認
- 手取り収入の登録

実装例：

```php
$netIncome = DB::transaction(
    function () use ($userId, $input): NetIncome {
        if ($this->query->existsByUserAndYearMonth(
            $userId,
            $input->targetYearMonth,
        )) {
            throw new NetIncomeAlreadyExistsException();
        }

        return $this->repository->create(
            $userId,
            $input,
        );
    },
);
```

処理途中で例外が発生した場合は、登録内容をロールバックする。

同時登録によってUNIQUE制約違反が発生した場合は、内部例外をそのまま返却せず、`NET_INCOME_ALREADY_EXISTS` へ変換する。

---

## 26.7 Responder

UseCaseから受け取った登録結果を、API共通方針に従ったHTTPレスポンスへ変換する。

正常終了時は、`201 Created` とともに登録した手取り収入を `data` オブジェクトで返却する。

対象年月の重複、バリデーションエラーまたは予期しない例外が発生した場合は、共通エラーレスポンス形式へ変換する。

Responderは、業務ルールの判定やデータベース操作を行わない。

---

## 26.8 API Resource

データベースカラムを直接返却せず、API Resourceを利用してAPIレスポンス形式へ変換する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'targetYearMonth' => $this->target_year_month,
    'amount' => $this->amount,
    'memo' => $this->memo,
];
```

手取り収入IDは、API共通方針に従って文字列として返却する。

金額は、日本円の整数値として返却する。

以下の項目は、レスポンスへ含めない。

- `userId`
- `createdAt`
- `updatedAt`

API Resourceは、Responderから利用する。

---

## 26.9 Middleware

以下の共通ミドルウェアを適用する。

- 利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

利用者コンテキスト設定ミドルウェアでは、`X-User-Id` を検証し、操作対象利用者を特定する。

Action以降の処理では、検証済みの利用者コンテキストを使用する。

---

## 26.10 例外変換

LaravelおよびPostgreSQLの内部例外は、そのままAPIレスポンスへ公開しない。

主な例外変換は、以下とする。

| 内部状態 | 独自エラーコード |
|---|---|
| 同一対象年月が登録済み | `NET_INCOME_ALREADY_EXISTS` |
| 入力値不正 | `VALIDATION_ERROR` |
| 利用者未指定 | `USER_CONTEXT_REQUIRED` |
| 利用者ID形式不正 | `INVALID_USER_ID` |
| 利用者不存在 | `USER_NOT_FOUND` |
| 想定外例外 | `INTERNAL_SERVER_ERROR` |

UNIQUE制約違反については、対象となった制約を判別し、`NET_INCOME_ALREADY_EXISTS` へ変換する。

SQL、スタックトレースおよび内部例外メッセージは、APIレスポンスへ含めない。

---## 28. 設計上の補足

### 28.1 POSTを採用する理由

手取り収入登録は、
新しい手取り収入リソースを作成する操作である。

そのため、
HTTPメソッドには
`POST`を採用する。

```http
POST /api/v1/net-incomes
```

---

### 28.2 対象年月単位で管理する理由

手取り収入は、
現在の収入ではなく、
対象年月時点の実績値を記録する。

対象年月ごとに管理することで、
将来の平均手取り収入算出、
目的達成判定および
過去データの再現性を維持できる。

---

### 28.3 同一対象年月を重複登録できない理由

同一利用者について、
同一対象年月の手取り収入は
1件のみ管理する。

複数件登録できるようにすると、
平均手取り収入の算出基準が曖昧になり、
業務ルールが複雑になる。

そのため、
以下の組み合わせで
UNIQUE制約を設ける。

```text
user_id
target_year_month
```

---

### 28.4 手取り収入がない場合は0円で登録する理由

対象年月に手取り収入が発生しなかった場合も、
対象年月の実績として管理する。

レコードを登録しない場合と
区別できるようにするため、
金額を`0円`として登録する。

これにより、
以下を明確に区別できる。

```text
レコードなし
    → 未入力

amount = 0
    → 手取り収入なし
```

---

### 28.5 論理削除を採用しない理由

手取り収入は、
履歴管理ではなく、
対象年月ごとの確定した実績値を管理する。

登録内容に誤りがある場合は、
同一レコードを更新して修正する。

そのため、
論理削除および取消状態は採用しない。

---

### 28.6 平均手取り収入を登録時に更新しない理由

本APIでは、
平均手取り収入を保存しない。

平均手取り収入は、
判定対象年月以前の連続する3か月の手取り収入から
都度算出する。

そのため、
登録APIでは
平均値の更新処理を行わない。

---

### 28.7 判定履歴を登録しない理由

手取り収入登録は、
目的達成判定とは独立した業務である。

本APIでは、
判定履歴を作成しない。

判定履歴は、
目的達成判定API実行時のみ登録する。

---

### 28.8 201 Createdを返却する理由

登録成功時は、
新しいリソースが作成されたことを示すため、
`201 Created`を返却する。

登録後のリソースも返却することで、
フロントエンドは
再取得せずに一覧や詳細画面を更新できる。

---

### 28.9 冪等性キーを採用しない理由

Phase1では、
Idempotency-Keyを採用しない。

同一対象年月への重複登録は、
業務ルールおよび
データベースのUNIQUE制約で防止する。

決済APIのような
通信再送対策は
Phase1では不要と判断した。

# INC-001 手取り収入一覧取得

## 1. 概要

操作対象となる利用者に登録された
手取り収入一覧を取得する。

手取り収入は、
対象年月単位で管理する。

一覧取得では、
対象年月ごとの手取り収入、
備考および対象年月を取得できる。

本APIは、
手取り収入一覧画面および
平均手取り収入の確認時に利用する。

---

## 2. ユースケース

利用者は、
登録済みの手取り収入を一覧で確認する。

例えば、
以下のような場合に使用する。

- 手取り収入一覧を表示する
- 対象年月ごとの登録内容を確認する
- 編集対象を選択する
- 平均手取り収入算出前に入力内容を確認する

---

## 3. エンドポイント

```http
GET /api/v1/net-incomes
```

---

## 4. HTTPメソッド

```http
GET
```

本APIは、
手取り収入一覧を取得する。

データの登録、
更新、
削除および状態変更は行わない。

---

## 5. 認証・利用者の扱い

Phase1では、
認証機能を実装しない。

操作対象となる利用者は、
`X-User-Id`リクエストヘッダーで指定する。

```http
X-User-Id: 1
```

指定された利用者に登録された
手取り収入のみ取得する。

他の利用者の手取り収入は取得できない。

---

なし。

- 指定されていること

`page`が指定された場合は、

- 整数であること

未指定の場合は、

---

### 11.3 perPage

`perPage`が指定された場合は、
以下を検証する。

- 整数であること
- 1以上であること
- API共通方針で定めた最大件数以下であること

未指定の場合は、
API共通方針で定めたデフォルト値を使用する。

---

### 11.4 sort

`sort`が指定された場合は、
以下を検証する。

- 文字列であること
- 指定可能な並び順であること

指定可能な値は、
以下とする。

| 値 | 説明 |
|---|---|
| `targetYearMonth` | 対象年月 |

未指定の場合は、
`targetYearMonth`を使用する。

---

### 11.5 order

`order`が指定された場合は、
以下を検証する。

- 文字列であること
- 以下のいずれかであること

| 値 | 説明 |
|---|---|
| `asc` | 昇順 |
| `desc` | 降順 |

未指定の場合は、

## 12. 業務ルール

- 操作対象利用者に帰属する手取り収入のみ取得する。
- 他の利用者の手取り収入は取得しない。
- 手取り収入は対象年月ごとに1件のみ存在する。
- 手取り収入は対象年月の昇順または降順で取得する。
- 並び順はクエリパラメータで指定できる。
- 対象年月が同一の手取り収入を複数登録することはできない。
- 金額が`0円`であっても有効な手取り収入として扱う。
- 手取り収入は論理削除を行わない。
- 手取り収入一覧には、登録済みデータのみ含める。

## 24. テスト観点

### 24.1 正常系

- 手取り収入一覧を取得できること

- 備考が未設定でも取得できること

### 24.2 利用者境界

- 1ページ目を取得できること

- `page`が不正な場合にエラーとなること

## 25. Laravel実装方針

### 25.1 Action

HTTPリクエストを受け付け、
ページネーション条件、
並び順および
利用者コンテキストを取得する。

Form Requestまたは入力用DTOを利用して
クエリパラメータを受け取り、
手取り収入一覧取得UseCaseを呼び出す。

UseCaseから受け取った処理結果を、
Responderへ渡す。

検索条件、
並び替え、
ページネーション処理および
レスポンス生成処理は、
Actionへ直接記述しない。

---

### 25.2 UseCase

手取り収入一覧取得の
ユースケース処理を担当する。

主な処理は、
以下とする。

- 操作対象利用者を受け取る
- ページ番号を受け取る
- 1ページ当たりの取得件数を受け取る
- 対象年月の並び順を受け取る
- Queryを呼び出して手取り収入一覧を取得する
- 取得結果とページネーション情報を返却する

本APIは参照処理のみであるため、
データの登録および更新は行わない。

---

### 25.3 Form Request / DTO

クエリパラメータの形式および
単項目バリデーションを担当する。

主な検証対象は、
以下とする。

- `page`
- `perPage`
- `order`

未指定の場合は、
以下の値を使用する。

- `page`
  - `1`
- `perPage`
  - API共通方針で定めた既定値
- `order`
  - `desc`

操作対象利用者の存在確認は、
利用者コンテキスト設定ミドルウェアで行う。

---

### 25.4 Query

操作対象利用者に帰属する
手取り収入一覧を取得する。

取得条件には、
必ず操作対象利用者IDを含める。

```php
NetIncome::query()
    ->where('user_id', $userId)
    ->orderBy(
        'target_year_month',
        $order,
    )
    ->paginate(
        perPage: $perPage,
        page: $page,
    );

---取得対象となる主なカラムは、以下とする。

- `id`
- `target_year_month`
- `amount`
- `memo`

利用者ID、登録日時および更新日時など、レスポンスに使用しない項目は必要に応じて取得対象から除外する。

手取り収入は論理削除を採用しないため、SoftDeletesに関する検索条件は使用しない。

### 25.5 Responder

UseCaseから受け取った一覧取得結果を、API共通方針に従ったHTTPレスポンスへ変換する。

正常終了時は、`200 OK` とともに手取り収入一覧を `data` 配列で返却する。

ページネーション情報は、`meta` オブジェクトとして返却する。

手取り収入が存在しない場合も、`200 OK` と空配列を返却する。

```json
{
  "data": [],
  "meta": {
    "currentPage": 1,
    "perPage": 20,
    "total": 0,
    "lastPage": 0
  }
}
```

エラー発生時は、共通エラーレスポンス形式へ変換する。

### 25.6 API Resource

データベースカラムを直接返却せず、API Resourceを利用してレスポンス形式へ変換する。

変換例：

```php
return [
    'id' => (string) $this->id,
    'targetYearMonth' => $this->target_year_month,
    'amount' => $this->amount,
    'memo' => $this->memo,
];
```

手取り収入IDは、API共通方針に従って文字列として返却する。

金額は、日本円の整数値として返却する。

API Resourceは、Responderから利用する。

以下の共通ミドルウェアを適用する。

- 利用者コンテキスト設定
- リクエストID生成
- JSONリクエスト・レスポンス共通処理
- 共通例外処理
- ログコンテキスト設定

利用者コンテキスト設定ミドルウェアでは、`X-User-Id` を検証し、操作対象利用者を特定する。

## 27. 設計上の補足

### 27.1 ページネーションを採用する理由

手取り収入は、対象年月ごとに継続して登録するため、利用期間に応じて件数が増加する。

Phase1時点では件数が少ないものの、長期間利用した場合でも一覧取得件数が無制限にならないよう、ページネーションを採用する。

ページネーション方式は、API共通方針に従う。

### 27.2 並び替え項目を対象年月に限定する理由

Phase1の一覧表示では、対象年月順で手取り収入を確認できれば十分である。

金額順、登録日時順および更新日時順による並び替えは提供しない。

並び替え対象を限定することで、API仕様およびフロントエンド実装を簡潔に保つ。

### 27.3 対象年月降順を既定とする理由

利用者が確認する可能性が高いのは、直近の手取り収入である。

そのため、`order` が指定されていない場合は、対象年月の降順で返却する。

古い対象年月から確認する必要がある場合は、`order=asc` を指定する。

### 27.4 金額0円を一覧へ含める理由

金額が0円の手取り収入は、未入力ではなく、対象年月の手取り収入が発生しなかったことを示す有効な業務データである。

そのため、金額が0円であっても一覧取得の対象から除外しない。

これにより、以下を明確に区別できる。

```text
対象年月のレコードが存在しない
    → 未入力

対象年月のレコードが存在し、
amountが0
    → 手取り収入なし
```

### 27.5 論理削除を採用しない理由

手取り収入は、登録内容に誤りがある場合、同一レコードを更新して修正する。

手取り収入が存在しない対象年月は、金額を0円として登録する。

そのため、取消状態や無効化状態を管理する必要がなく、`deleted_at` による論理削除を採用しない。

### 27.6 登録日時と更新日時を返却しない理由

一覧画面で必要となる情報は、対象年月、手取り収入額および備考である。

登録日時および更新日時は、Phase1の画面表示や業務判断には使用しない。

そのため、APIレスポンスへ含めない。

将来、更新履歴や最終更新日時を表示する要件が追加された場合に、レスポンスへの追加を再検討する。

### 27.7 平均手取り収入を本APIで返却しない理由

平均手取り収入は、単純な一覧データではなく、判定対象年月以前の連続する3か月を用いて算出する業務上の計算結果である。

そのため、一覧取得APIのレスポンスには含めず、INC-005 平均手取り収入取得APIで提供する。

これにより、一覧取得と平均値算出の責務を分離する。

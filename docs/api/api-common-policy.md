# API共通方針

## 1. 目的

本書では、
Life Plannerの各APIに共通して適用する設計方針を定義する。

個別APIは、
本書で定義した共通方針に従って設計する。

---

## 2. 利用者切替方式

### 2.1 概要

Life Plannerでは、
あらかじめ登録されたデモ利用者を切り替えて利用できる。

利用者切替は、
ポートフォリオ確認者が異なる資産状況や目的達成判定のパターンを
短時間で確認できるようにすることを目的とする。

Phase1では、
ログイン認証によって利用者を特定するのではなく、
フロントエンドで選択されたデモ利用者を
APIリクエストごとに指定する。

---

### 2.2 採用方式

操作対象の利用者は、
HTTPリクエストヘッダーで指定する。

使用するヘッダー名は、
以下とする。

```http
X-Demo-User-Id: 1
```

---

### 2.3 利用者一覧の取得

フロントエンドで選択可能な利用者を表示するため、
登録済みデモ利用者の一覧を取得するAPIを提供する。

```http
GET /api/v1/users
```

利用者一覧取得APIでは、
X-Demo-User-Idヘッダーを必須としない。

レスポンスには、
利用者切替画面で必要となる以下の情報を含める。

利用者ID
表示名
デモシナリオの説明

レスポンス例は、
以下とする。

```json
{
  "data": [
    {
      "id": "1",
      "name": "標準ケース",
      "description": "資産情報と手取り収入が登録済みの基本的な利用者です。"
    },
    {
      "id": "2",
      "name": "達成困難ケース",
      "description": "目的達成後の残余資金が不足する利用者です。"
    },
    {
      "id": "3",
      "name": "判定不可ケース",
      "description": "手取り収入が不足しており、目的達成判定を実行できない利用者です。"
    }
  ]
}
```

---

### 2.4 利用者切替処理

利用者切替専用のAPIは提供しない。

利用者切替は、
フロントエンドで現在選択している利用者IDを変更することで実現する。

```text
利用者一覧を取得
    ↓
利用者を選択
    ↓
フロントエンドが選択中の利用者IDを保持
    ↓
各APIリクエストへX-Demo-User-Idを付与
```
以下のような利用者切替APIは作成しない。

```http
POST /api/v1/users/{userId}/switch
```

切替状態をバックエンドのセッションへ保存せず、
APIリクエストごとに操作対象の利用者を明示する。

---

### 2.5 フロントエンドでの保持

選択中のデモ利用者IDは、
フロントエンドの共通状態として管理する。

画面ごとのローカルな状態として管理せず、
すべての画面から同じ利用者コンテキストを参照できるようにする。

選択した利用者IDは、
画面を再読み込みした後も維持できるよう、
localStorageへ保存する。

保存キーは、
以下とする。

```text
lifePlanner.selectedDemoUserId
```

保存された利用者IDが、
登録済み利用者一覧に存在しない場合は、
初期表示するデモ利用者へ切り替える。

---

### 2.6 APIクライアントでの付与

X-Demo-User-Idは、
各画面や各コンポーネントから個別に指定しない。

フロントエンドの共通APIクライアントで、
すべての利用者依存APIへ自動的に付与する。

```http
GET /api/v1/asset-accounts
X-Demo-User-Id: 2
```

これにより、
ヘッダーの付け忘れや、
画面ごとの実装差異を防止する。

---

### 2.7 バックエンドでの利用者特定

バックエンドは、
共通ミドルウェアでX-Demo-User-Idを検証する。

処理手順は、
以下とする。

```text
X-Demo-User-Idを取得
    ↓
必須チェック
    ↓
形式チェック
    ↓
usersテーブルの存在チェック
    ↓
利用者コンテキストへ設定
    ↓
各APIの処理を実行
```

各コントローラーで個別に
ヘッダーの取得や利用者検索を行わない。

---

### 2.8 利用者境界

利用者に属するデータを取得または更新する場合は、
必ず操作対象の利用者IDを検索条件へ含める。

対象となる主なデータは、
以下とする。

* 資産口座
* 保有商品
* 月末資産状況
* 月末資産残高
* 商品別月末評価額
* 手取り収入
* 目的
* 判定履歴
例えば、
資産口座IDだけを条件として取得してはならない。

```php
// 不採用
AssetAccount::findOrFail($assetAccountId);
```

操作対象の利用者IDを含めて取得する。

```php
AssetAccount::query()
    ->where('id', $assetAccountId)
    ->where('user_id', $currentUserId)
    ->firstOrFail();
```

利用者IDが一致しないデータは、
参照、更新、無効化および取消の対象にできない。

---

### 2.9 エラー

利用者依存APIで
X-Demo-User-Idが指定されていない場合は、
エラーとする。

想定する独自エラーコードは、
以下とする。

| エラーコード                 | 条件                         |
| -------------------------- | --------------------------- |
| DEMO_USER_CONTEXT_REQUIRED | 利用者IDが指定されていない      |
| INVALID_DEMO_USER_ID       | 利用者IDの形式が不正           |
| DEMO_USER_NOT_FOUND        | 指定された利用者が存在しない     |

HTTPステータスおよび共通エラーレスポンス形式は、
後続のAPI共通方針で決定する。

---

### 2.10 対象外

Phase1では、
以下を対象外とする。

* 利用者の新規登録
* 利用者情報の編集
* 利用者の削除
* ログイン・ログアウト
* パスワード管理
* メール認証
* 認証済み利用者の特定
* ロールおよび権限管理
* 一般利用者向けのアカウント管理

---

### 2.11 セキュリティ上の位置づけ

X-Demo-User-Idは、
認証情報として扱わない。

利用者は任意のデモ利用者IDを指定できるため、
一般公開サービスの利用者特定方式としては使用できない。

本方式は、
ポートフォリオ用ステージング環境で
デモデータを切り替えるための方式とする。

ステージング環境には、
開発者本人の実際の資産情報を登録しない。

将来、認証機能を追加する場合は、
X-Demo-User-Idによる利用者特定を廃止し、
認証された利用者情報から操作対象を特定する方式へ変更する。

---

### 2.12 採用理由

本方式を採用する理由は、
以下のとおりとする。

* 認証機能を実装せずに複数のデモシナリオを確認できる
* ポートフォリオ確認者が短時間で表示内容を切り替えられる
* バックエンドがセッション状態を保持する必要がない
* APIリクエスト単位で操作対象の利用者が明確になる
* 将来、認証による利用者特定方式へ差し替えやすい

---

## 3. 共通レスポンス形式

### 3.1 概要


[GEMINIヒント]
* APIが返却するレスポンスの全体的な方針を記述します。
* 記述内容: 「当APIはすべてのレスポンスをJSON形式で返却します」「HTTPステータスコードを正しく活用し、ボディのメタ情報と連動させます」といった基本方針。

---

### 3.2 基本構造


[GEMINIヒント]
* すべてのAPIで共通して保持する最上位（ルート）のキーを定義します。
* 記述内容: success（成否）、data（データ本体）、error（エラー情報）、meta（付加情報）の4つを基本構造とするルール。

---

### 3.3 正常時レスポンス


[GEMINIヒント]
* リクエストが成功した場合（HTTP 2xx）の共通パターンです。
* 記述内容: success: true とし、error は null にするか、キー自体を含めないというルール。

---

### 3.4 単一リソースのレスポンス


[GEMINIヒント]
* ユーザー情報や記事詳細など、1つのデータを取得する場合の形式です。
* 記述内容: data の直下にオブジェクト（{}）を配置するルールとサンプル。

---

### 3.5 複数リソースのレスポンス


[GEMINIヒント]
* 一覧画面など、複数のデータを取得する場合の形式です。
* 記述内容: data の直下に配列（[]）を配置し、件数やページネーション情報は meta に逃がすというルール。

---

### 3.6 登録・更新時のレスポンス


[GEMINIヒント]
* POST（新規登録）やPUT/PATCH（更新）が成功した際の内容です。
* 記述内容: ステータスコード（201 Created や 200 OK）の使い分け。data には登録・更新された最新のリソース（IDやタイムスタンプを含む）を丸ごと返却するルール。 [1, 2]

---

### 3.7 削除・無効化・取消時のレスポンス


[GEMINIヒント]
* DELETEや、論理削除などの処理が成功した際の内容です。
* 記述内容: ステータスコード 204 No Content（ボディなし）にするか、200 OK で {"success": true}のみを返却するかの選択と定義。

---

### 3.8 エラーレスポンス


[GEMINIヒント]
* サーバーエラー（5xx）やクライアントエラー（4xx）の基本形です。
* 記述内容: success: false、data: null とし、error オブジェクトの中に code（固有のエラーコード）と message（開発者向けメッセージ）を必須とするルール。

---

### 3.9 バリデーションエラー


[GEMINIヒント]
* 入力値チェック（422 Unprocessable Entity など）で落とされた場合の詳細な形式です。
* 記述内容: error の中に details 配列を持たせ、どのフィールド（field）が、どんな理由（reason）でエラーになったかを画面側でマッピングしやすい形で返却するルール。

---

### 3.10 データが存在しない場合


[GEMINIヒント]
* ID指定での取得などで、対象が見つからなかった場合（404 Not Found）の振る舞いです。
* 記述内容: 「一覧で0件の場合は 200 OK で空配列 [] を返すが、単一リソース取得で存在しない場合は 404 エラーとする」という明確な境界線の定義

---

### 3.11 メタ情報


[GEMINIヒント]
* ページネーション、APIのバージョン、リクエスト日時などの付加情報です。
* 記述内容: meta オブジェクトの構造定義。具体的には current_page、per_page、total_count などのキー名と型の定義。

---

### 3.12 フィールド命名規則


[GEMINIヒント]
* JSONのキーの書き方の統一ルールです。
* 記述内容: 「原則としてスネークケース（user_id）とする」または「キャメルケース（userId）とする」の宣言。JavaScriptとの親和性を考慮してチームで統一します。

---

### 3.13 NULL・空配列・空文字の扱い


[GEMINIヒント]
* データがない、または未入力の項目をどう表現するかです。
* 記述内容:
    * 値がない場合はキーごと削除するのか、null として残すのかの統一。
    * 配列がない場合は null ではなく空配列 [] を徹底するルール。

---

### 3.14 レスポンスに含めない情報


[GEMINIヒント]
* セキュリティやパフォーマンスの観点から除外すべきデータです。
* 記述内容: パスワードのハッシュ値、クレジットカード情報、内部向けのスタックトレース、不要なデバッグ情報などを絶対に含めないという禁止事項。

---

### 3.15 共通ルール


[GEMINIヒント]
* 上記に収まらない、全体に適用する細かな約束事です。
* 記述内容: 日時のフォーマット（ISO 8601形式：YYYY-MM-DDTHH:mm:ssZ で統一）、文字コード（UTF-8指定）などの標準化

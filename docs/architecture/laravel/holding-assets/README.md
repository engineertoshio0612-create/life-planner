# 保有商品 Laravelアーキテクチャ設計

## 1. 概要

本ディレクトリでは、保有商品に関するAPIをLaravelで実装する際のアーキテクチャおよび責務分離方針を定義する。

対象APIは以下とする。

* HLD-001 保有商品一覧取得
* HLD-002 保有商品登録
* HLD-003 保有商品詳細取得
* HLD-004 保有商品更新
* HLD-005 保有商品無効化

保有商品は利用者の資産口座に所属し、商品単位で残高を記録する資産口座における資産管理の単位として扱う。

各APIでは、操作対象利用者に帰属するデータのみを操作対象とし、Queryによる取得時点から利用者条件を含めることで利用者境界を保証する。

## 2. アーキテクチャ方針

Laravel実装では、APIの特性に応じて以下の責務を分離する。

```text
Middleware
    ↓
Action
    ↓
Form Request / DTO
    ↓
UseCase
    ↓
Query / Repository
    ↓
DTO / API Resource
    ↓
Responder
```

ActionはHTTPリクエストの受付とUseCaseの呼び出しに責務を限定する。

UseCaseは、利用者境界、資産口座の状態、残高記録単位、重複確認など、各APIに必要な業務ルールと処理フローを制御する。

Queryは利用者境界を考慮したデータ取得を担当し、Repositoryは登録・更新・無効化などの永続化を担当する。

API ResourceおよびResponderは、内部のModelやDTOをAPI共通方針に従ったHTTPレスポンスへ変換する。

## 3. 無効化方針

保有商品の無効化は物理削除ではなく、LaravelのSoftDeletesを利用した論理削除として扱う。

無効化済み保有商品は以降の登録・更新対象から除外する一方、過去の商品別月末評価額、月末資産状況および目的達成判定履歴は保持する。

通常属性の更新と無効化は異なる業務操作として扱い、HLD-004とHLD-005ではRoute、ActionおよびUseCaseを分離する。

## 4. 個別設計

各API固有の業務ルール、Query、Repository、DTO、レスポンスおよびテスト実装方針については、各APIのLaravelアーキテクチャ設計を参照する。

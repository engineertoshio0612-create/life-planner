# 目的達成判定API テスト設計

## 1. 概要

本ディレクトリでは、
目的達成判定に関連するAPIの
バックエンドテスト設計を管理する。

対象となるAPIは、
目的達成判定の実行、
目的達成判定履歴の一覧取得、
目的達成判定履歴の詳細取得などである。

目的達成判定では、
目的、
月末資産状況、
月末資産残高、
商品別月末評価額、
利用可能資産設定、
手取り収入など、
複数の業務データをもとに
判定処理を行う。

そのため、
単純なAPI入出力だけではなく、

```text
利用者境界
+
判定対象データの選択
+
資産額の集計
+
手取り収入の算出
+
目的達成判定
+
判定履歴
```

まで含めて、
業務ルールが正しく実装されていることを確認する。

## 4. 共通テスト方針

### 4.1 利用者境界

すべての目的達成判定APIでは、
`X-User-Id`によって確定した
操作対象利用者のデータのみを扱う。

テストでは、
少なくとも以下を確認する。

* `X-User-Id`未指定
* `X-User-Id`形式不正
* 利用者不存在
* 論理削除済み利用者
* 他利用者の目的を操作できないこと
* 他利用者の判定履歴を取得できないこと
* 他利用者の資産情報や手取り収入が判定へ混入しないこと

他利用者のリソースを指定した場合は、
そのリソースが存在すること自体を
外部から判別できないようにする。

---

### 4.2 判定不可とAPIエラーを区別する

目的達成判定では、

```text
判定不可
```

と

```text
APIエラー
```

を明確に区別する。

判定に必要な業務データが不足している場合は、
API処理そのものの失敗とはせず、
業務上の判定結果として
「判定不可」を扱う。

一方、

* 利用者コンテキスト不正
* 利用者不存在
* パラメータ形式不正
* 目的不存在
* 判定履歴不存在
* 内部データ不整合

などはAPIエラーとして扱う。

テストでは、
この境界が崩れていないことを確認する。

---

### 4.3 保存済み判定履歴を正とする

判定履歴を参照するAPIでは、
`assessment_histories`へ保存された
判定結果および計算根拠を正とする。

履歴取得時に、

* 現在の目的
* 現在の月末資産状況
* 現在の月末資産残高
* 現在の商品別月末評価額
* 現在の利用可能資産設定
* 現在の手取り収入

などを使用して
過去の判定結果を再計算しない。

概念的には、

```text
判定実行
    ↓
判定結果・計算根拠を保存
    ↓
assessment_histories
    ↓
履歴参照API
    ↓
保存済み情報を返却
```

とする。

---

### 4.4 過去履歴を変更しない

目的達成判定履歴は、
判定を実行した時点の結果を
後から確認するための履歴として扱う。

そのため、
判定後に元となる業務データが変更されても、
既存の判定履歴を自動更新しない。

再判定が必要な場合は、
新しい判定を実行し、
新しい履歴として扱う。

---

### 4.5 副作用

参照専用APIでは、
実行によって業務データが
変更されないことを確認する。

特に、

```text
users
objectives
assessment_histories
month_end_asset_snapshots
month_end_asset_balances
month_end_holding_values
asset_accounts
asset_account_available_settings
holding_assets
net_incomes
```

などについて、
意図しないINSERT、UPDATE、DELETEが
発生していないことを確認する。

判定実行APIについても、
仕様上必要な判定履歴の登録以外に
不要な副作用が発生していないことを確認する。

---

### 4.6 レスポンス契約

正常レスポンスについて、
API共通方針で定めた
Envelope形式に従っていることを確認する。

また、

```text
DB
snake_case
    ↓
API
camelCase
```

へ適切に変換されていることを確認する。

DB上で`bigint`として管理するIDについては、
APIレスポンスではstringとして返却する。

金額については、
表示用文字列へ変換せず
integerとして返却する。

---

### 4.7 エラーレスポンス

APIエラーについて、
API共通方針で定めた
共通エラーレスポンス形式に従っていることを確認する。

主に以下を確認する。

* `error.code`
* `error.message`
* `error.details`
* `error.requestId`

また、

* SQL
* SQLSTATE
* PostgreSQLの制約名
* Laravelの内部例外
* スタックトレース
* サーバー内部のファイルパス

などの内部情報を
レスポンスへ含めないことを確認する。

---

### 4.8 冪等性

GETによる参照APIについては、
同一のデータ状態で
同一リクエストを複数回実行しても、
業務データが変更されないことを確認する。

一方、
判定実行によって
新しい判定履歴を作成するAPIについては、
APIごとに定義された冪等性の仕様に従って
テストする。

---

## 5. テストレベル

### 5.1 Feature Test

API全体の振る舞いについて、
LaravelのFeature Testを中心に確認する。

主な対象は、

* HTTPステータス
* レスポンスJSON
* バリデーション
* 利用者コンテキスト
* 利用者境界
* 業務ルール
* データベース登録・非更新
* エラーレスポンス
* API Resourceによる変換

とする。

---

### 5.2 Domain / Unit Test

目的達成判定に関する
計算および判定ロジックを
ActionやHTTP層から分離している場合は、
Unit Testによって個別に確認する。

主な対象は、

* 利用可能資産額の算出
* 平均手取り収入の算出
* 必要生活防衛資金の算出
* 目的達成可否の判定
* 判定不可条件
* 判定結果の生成

とする。

APIのFeature Testだけに
複雑な判定ロジックの検証を集中させない。

---

### 5.3 Query / Repository Test

QueryまたはRepositoryへ
データ取得処理を分離する場合は、
必要に応じて個別テストを行う。

特に、

```text
リソースID
+
UserContext.userId
```

によって利用者境界が
取得条件へ適切に含まれていることを確認する。

---

### 5.4 Resource Test

API Resourceについて、
DB、Entity、DTOなどの値が
API仕様どおりに変換されることを確認する。

主に、

```text
bigint ID
    ↓
string

snake_case
    ↓
camelCase

金額
    ↓
integer

日時
    ↓
API共通日時形式
```

を確認する。

---

## 6. テストデータ方針

目的達成判定では、
複数の業務データを組み合わせるため、
テストケースごとに
必要最小限のデータを明示的に用意する。

例えば、

```text
User
    ↓
Objective
    ↓
MonthEndAssetSnapshot
    ├─ MonthEndAssetBalance
    └─ MonthEndHoldingValue

NetIncome

AssessmentHistory
```

などの関係を、
テスト目的に応じて構築する。

テストケース間で
不要な状態を共有せず、
各テストが独立して実行できるようにする。

また、
利用者境界を確認するテストでは、
User AとUser Bのように
複数利用者のデータを明示的に作成する。

---

## 7. テストで重視する境界

目的達成判定APIでは、
特に以下の境界を重視する。

```text
判定可能
    ↕
判定不可

判定不可
    ↕
APIエラー

現在状態
    ↕
保存済み履歴

操作対象利用者
    ↕
他利用者

判定実行
    ↕
履歴参照

業務ロジック
    ↕
HTTP / API表現
```

これらの責務や状態が
混在していないことを
テストによって確認する。
